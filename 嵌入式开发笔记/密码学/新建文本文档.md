  逐术语解释

  对称加密 vs 非对称加密

  ┌────────────┬──────────────────────────────────────────────────────────┬────────────────────────────────┐
  │    概念    │                         通俗类比                         │            DLMS 中             │
  ├────────────┼──────────────────────────────────────────────────────────┼────────────────────────────────┤
  │ 对称加密   │ 一把钥匙，既能锁也能开。双方必须都有同一把钥匙           │ AES-GCM，Suite 0               │
  │            │                                                          │ 用的就是纯对称                 │
  ├────────────┼──────────────────────────────────────────────────────────┼────────────────────────────────┤
  │ 非对称加密 │ 公钥=公开的锁（谁都能锁），私钥=唯一的钥匙（只有你能开） │ ECDSA/ECDH，Suite 1/2 才有     │
  └────────────┴──────────────────────────────────────────────────────────┴────────────────────────────────┘

  为什么 Suite 0 够用但不够安全？

  对称密钥一旦泄露，攻击者能解密所有历史通信。非对称（Suite
  1/2）的私钥从不传输，即使服务器被黑也无法解密历史数据——这叫前向保密。

---
  AES-GCM

  三个字母拆开：

  ┌──────┬──────────────────────────────┬────────────────────────────┐
  │ 缩写 │             全称             │           干什么           │
  ├──────┼──────────────────────────────┼────────────────────────────┤
  │ AES  │ Advanced Encryption Standard │ 加密算法本身，把明文变密文 │
  ├──────┼──────────────────────────────┼────────────────────────────┤
  │ GCM  │ Galois/Counter Mode          │ 运行模式，决定 AES 怎么用  │
  └──────┴──────────────────────────────┴────────────────────────────┘

  一句话：AES-GCM = 加密 + 防篡改，一次运算同时做到两件事。

  传统做法要两步：先 AES 加密、再 HMAC 签名。AES-GCM 一步搞定，速度快、省硬件。

  AEAD（Authenticated Encryption with Associated Data）就是对这个"一步搞定"的学术叫法。

---
  Nonce（也叫 IV，初始向量）

  Nonce = System Title(8字节) + Invocation Counter(4字节) = 12 字节

  一句话：Nonce 是加密的"一次性编号"，保证同样的明文每次加密结果不同。

  如果 Nonce 重复会怎样？ 攻击者可以破解密文。所以 Invocation Counter 必须每次严格递增。"IV 重用攻击"就是指
  Nonce 重复利用导致的漏洞。

---
  AAD（附加认证数据）

  AAD = Security Control Byte + Auth Key + System Title + Invocation Counter

  一句话：AAD 是"不加密但要防篡改"的字段。

  类比快递：箱子里的东西加密（Ciphertext），快递单不加密（AAD——寄件人、收件人、单号），但快递单被涂改你就能发
  现（认证标签不匹配）。AES-GCM 保证 AAD 一旦被篡改，接收方立即能检测到。

---
  Auth Tag（认证标签）

  Auth Tag = GHASH(AAD, Ciphertext) XOR AES(Key, J0)
  长度 = 12 字节

  一句话：Auth Tag 是数据的"防伪码"。发送方算一遍附在密文末尾，接收方算一遍对比。不匹配 → 数据被篡改过 →
  直接丢弃。

  之前 DLMS证书测试问题汇总.md 里 §10.4 的 bug 就是 Auth Tag 校验写的 ret = 0 而不是 return
  ret，校验失败也返回成功。这就是 Tag 校验的重要性。

---
  GHASH / GF(2^128) 伽罗瓦域

  一句话：GHASH 是一种特殊的哈希算法，在二进制硬件上极快。不需要理解 GF(2^128)
  的数学——这是芯片厂商的事。结论：AES-GCM 在电表这种低功耗硬件上跑起来比传统 HMAC 快。

---
  密钥体系

  DLMS 定义这么多密钥名字，本质就三层：

  第一层: KEK (Master Key, 密钥加密密钥)
           │
           │  用 KEK 加密传输其他密钥（Key Wrapping）
           │
  第二层:  ├─ GUEK (全局单播加密密钥) — 保护点对点通信
           ├─ GBEK (全局广播加密密钥) — 保护广播消息
           └─ GAK  (全局认证密钥)      — 用于 GMAC 认证
           │
  第三层:  ├─ Dedicated Key — 客户端连接时指定，每次可以不同
           └─ Ephemeral Key — ECDH 协商的一次性密钥（Suite 1/2）

  ┌───────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │     术语      │                                  通俗解释                                   │
  ├───────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ KEK           │ "钥匙箱的钥匙"。KEK 不直接加密数据，用它加密/传输 GUEK 等实际加密数据的密钥 │
  ├───────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ GUEK          │ "打电话用的密钥"。点对点，你和对方各一把，保护日常通信                      │
  ├───────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ GBEK          │ "广播喇叭的密钥"。一对多，比如固件升级通知发给所有表                        │
  ├───────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ GAK           │ "身份证"。只认证不加密，验证对方身份                                        │
  ├───────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ Dedicated Key │ 客户端自带钥匙，每次连接可以换。比如 HES 给每个抄表任务随机生成一把         │
  ├───────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ Ephemeral Key │ "一次性钥匙"，用后即弃。ECDH 临时协商，会话结束就扔，安全级别最高           │
  ├───────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ Key Wrapping  │ 把密钥锁进另一个密钥里再传输。类比：把钥匙放进密码箱快递给对方              │
  └───────────────┴─────────────────────────────────────────────────────────────────────────────┘

  认证级别（LLS vs HLS）

  ┌──────────────────┬─────────────────────────────────────────────────────────────┬──────────────────────┐
  │       级别       │                           怎么做                            │       安全程度       │
  ├──────────────────┼─────────────────────────────────────────────────────────────┼──────────────────────┤
  │ 无认证 (Public   │ 客户端声明地址=16                                           │ 任何人都能读基本数据 │
  │ Client)          │                                                             │                      │
  ├──────────────────┼─────────────────────────────────────────────────────────────┼──────────────────────┤
  │ LLS              │ 客户端把密码明文发给电表                                    │ 弱——密码在传输中可见 │
  ├──────────────────┼─────────────────────────────────────────────────────────────┼──────────────────────┤
  │ HLS              │ 双方互出"考题"（challenge），用密钥算出答案（GMAC           │ 强——密码从不传输     │
  │                  │ tag），验证答案                                             │                      │
  └──────────────────┴─────────────────────────────────────────────────────────────┴──────────────────────┘

  HLS 的 Challenge-Response 机制：

  HES: "你用密钥算一下这个随机数 0xA3F1...，告诉我结果"
  Meter: "结果是 0x8B2C..."
  HES: （自己也用密钥算一遍，对比结果，一致 → Meter 确实持有密钥）
  Meter: "轮到你了，算一下这个随机数 0x7D04..."
  HES: "结果是 0xE91A..."
  Meter: （对比，一致 → HES 确实持有密钥）

  全程密钥不传输，只传随机数和计算结果。即使被窃听，攻击者也推导不出密钥。

  ▎ 文档里的"challenge"翻译成"挑战"不太直观，把它理解为 随机验证数 或 考题 更好理解。

---
  ECDSA / ECDH（Suite 1/2 才有的非对称部分）

  缩写: ECDSA
  全称: Elliptic Curve Digital Signature Algorithm
  干什么: 数字签名——证明"这消息是我发的"
  类比: 手写签名，但数学上不可伪造
  ────────────────────────────────────────
  缩写: ECDH
  全称: Elliptic Curve Diffie-Hellman
  干什么: 密钥协商——双方在不安全信道上商定一把共享密钥
  类比: 双方各自算一半，拼出完整密钥，偷听者拼不出来

  不可否认性：用 ECDSA 签名后，发送方不能抵赖"这不是我发的"。Suite
  0（纯对称）做不到这点——双方都有同一把密钥，无法证明到底是谁发的。

---
  Invocation Counter（调用计数器）

  一句话：消息的流水号，每次加密 +1。防止攻击者录下你的密文然后重放。

  接收方记录上一次收到的计数器值。如果新消息的计数器 ≤ 旧值 → 是重放攻击 → 丢弃。这就是 §三
  里"防重放"的实现方式。

---
  HSM / Secure Element（安全芯片）

  一句话：把密钥存在独立硬件芯片里，而不是代码里（代码可被读取）。

  代码里写 uint8_t key[] = {0x00,0x01,...} → 固件被 dump 密钥就泄露。安全芯片（如 NXP
  SE05x）密钥写入后物理不可读出，只能通过芯片接口调用"用这个密钥加密这段数据"，攻击者碰不到密钥本身。

❯ Galois/Counter是啥

  Thought for 8s (ctrl+o to expand)

● GCM 的两个词各自负责一件事：

  GCM = Galois（认证） + Counter（加密）
        GHASH 哈希校验        AES-CTR 流加密

  Counter — 加密部分

  Counter 模式把 AES 当"密钥流生成器"用：

  Counter=1  Counter=2  Counter=3
     │          │          │
  AES(Key)   AES(Key)   AES(Key)    ← 每个 Counter 用 AES 加密一次
     │          │          │
    K1         K2         K3         ← 生成"密钥流"
     ⊕          ⊕          ⊕
   明文字节   明文字节   明文字节     ← XOR
     ↓          ↓          ↓
   密文字节   密文字节   密文字节

  最终: Ciphertext = Plaintext XOR AES(Key, Counter)

  好处：可以随机访问——解密第 1000 个字节不需要先解前 999 个。Counter 模式不需要明文是整块（16
  字节对齐），流式处理任意长度。

  Galois — 认证部分

  命名来自数学家埃瓦里斯特·伽罗瓦（Évariste Galois，1811-1832）。他发明的伽罗瓦域（Galois
  Field，GF）是一种有限数域，加减乘除规则与普通数学不同，但在二进制硬件上极其高效。

  GHASH 就是基于 GF(2^128) 乘法：

  GHASH = 在 GF(2^128) 域上，
          AAD 和 Ciphertext 逐块与哈希子密钥 H 相乘累加

  H = AES(Key, 0^128)   ← 全零块用 AES 加密一次得到 H

  为什么用 Galois 域？ GHASH 在硬件上可用几个门电路实现，比 SHA-256 便宜得多。电表 MCU 算得动。

  合在一起

  输入: Plaintext + AAD + Nonce + Key
          │           │       │
          ▼           │       ▼
     AES-CTR          │   构造 J0 = Nonce || Counter=1
     Counter模式      │       │
     加密明文          │   AES(Key, J0)
          │           │       │
          ▼           │       ▼
      Ciphertext ─────┼─→ GHASH(AAD, Ciphertext) XOR AES(Key, J0)
                      │              │
                      └──────────────┘
                             │
                             ▼
                        Auth Tag (12字节)

  Counter 负责把明文变密文。Galois 负责给 AAD+密文算一个哈希校验码。一个算法同时输出两样东西——这就是 AEAD。

❯ BLOCKCIPHERKEY是啥

  Thought for 2s (ctrl+o to expand)

● 就是 AES 加密用的那 16 字节密钥。

  在 AES-GCM 里，Block Cipher Key = AES 的原材料。AES 本身是分组密码（Block Cipher），每次处理 16
  字节一块，所以叫 Block Cipher Key。

---
  一个密钥，两个用途

  AES-GCM 从 Block Cipher Key 派生出两个子密钥：

  Block Cipher Key (16字节)
          │
          ├─→ AES(Key, Counter) → 密钥流 → XOR 明文 → 密文    (加密)
          │
          └─→ AES(Key, 0^128) → H → GHASH → Auth Tag          (认证)

  同一把 Key，Counter 模式拿它生成密钥流，Galois 模式拿它算 H 做哈希。

---
  DLMS 里 Block Cipher Key 具体是什么

  取决于场景：

  ┌────────────────────────────┬─────────────────────────────┐
  │            场景            │ Block Cipher Key 实际用的是 │
  ├────────────────────────────┼─────────────────────────────┤
  │ 常规通信加密               │ GUEK（全局单播加密密钥）    │
  ├────────────────────────────┼─────────────────────────────┤
  │ 客户端指定了 Dedicated Key │ Dedicated Key               │
  ├────────────────────────────┼─────────────────────────────┤
  │ Suite 1/2 ECDH 协商后      │ Ephemeral Key（临时密钥）   │
  └────────────────────────────┴─────────────────────────────┘

  GAK 不是 Block Cipher Key。GAK 只做认证（GMAC），不做加密。GMAC 本质就是 GCM 的认证部分——只算
  Tag、不加密数据。

---
  还有 Authentication Key

  GMAC 计算也需要 Key，但那是 GAK，16 字节。加密文档里 AAD 那行写的 Auth Key 就是 GAK：

  AAD = Security Control Byte || Auth Key || System Title || Invocation Counter
                                  ↑
                                 GAK

---
  简记：Block Cipher Key = AES 加密用的那把钥匙，DLMS 里通常是 GUEK，16
  字节。加密和认证两件事用的同一把钥匙的不同派生方式。

❯ Block Cipher Key就是对称加密的密钥？双方协商一致的密钥？

  Thought for 4s (ctrl+o to expand)

● 对，但有细节要纠正。

  是，但是

  Block Cipher Key 是对称密钥没错——加密和解密用同一把。但"协商"这个词取决于 Suite：

  ┌───────────┬──────────────────────────────────────────────┬──────────────────────┐
  │   Suite   │                  密钥怎么来                  │       有协商吗       │
  ├───────────┼──────────────────────────────────────────────┼──────────────────────┤
  │ Suite 0   │ 预先配置，双方出厂就写好同一把 GUEK          │ ❌ 无协商，纯预共享  │
  ├───────────┼──────────────────────────────────────────────┼──────────────────────┤
  │ Suite 1/2 │ ECDH 协商出 Ephemeral Key，或用预配置的 GUEK │ ✅ ECDH 是真正的协商 │
  └───────────┴──────────────────────────────────────────────┴──────────────────────┘

  Suite 0 下双方没有"协商"过程——密钥是烧录进去的，或者通过 Key Wrapping 远程下发（用 KEK 加密传输）。HLS 的
  Challenge-Response 是验证对方有没有这把钥匙，不是协商钥匙本身。

  所以准确说法

  ▎ Block Cipher Key = AES 对称加密用的密钥。DLMS 中通常是 GUEK（预共享），特殊场景可以是 Dedicated Key 或
  ▎ ECDH 协商的 Ephemeral Key。加密和解密用同一把。

❯ ssh用的是什么加密

  Thought for 5s (ctrl+o to expand)

● SSH 是混合模式，比 Suite 0 高级、跟 Suite 1/2 同套路：

  连接时（非对称）:
      ECDH (Curve25519) → 双方在不安全网络上协商出一把 Session Key
                          偷听者算不出来

  传输时（对称）:
      AES-GCM 或 ChaCha20-Poly1305 → 用 Session Key 加密实际数据

  SSH vs DLMS 对比

  ┌────────────────┬────────────────────┬─────────────────┬────────────────────────────┐
  │      阶段      │        SSH         │  DLMS Suite 0   │       DLMS Suite 1/2       │
  ├────────────────┼────────────────────┼─────────────────┼────────────────────────────┤
  │ 密钥怎么来     │ ECDH 实时协商      │ 出厂预写 GUEK   │ ECDH 协商或预写            │
  ├────────────────┼────────────────────┼─────────────────┼────────────────────────────┤
  │ 实际加密       │ AES-GCM / ChaCha20 │ AES-GCM         │ AES-GCM                    │
  ├────────────────┼────────────────────┼─────────────────┼────────────────────────────┤
  │ 密钥丢了会怎样 │ 只影响当前会话     │ 历史+未来全暴露 │ 只影响当前会话（前向保密） │
  └────────────────┴────────────────────┴─────────────────┴────────────────────────────┘

  Suite 0 相当于 SSH 去掉了 ECDH 协商那一步——双方直接用预配置的密钥加密。所以 Suite 0
  没有前向保密，密钥泄露=历史全解密。SSH 和 Suite 1/2 有 ECDH，每次连接换新密钥。

❯ 用通俗易懂的例子说说对称加密和非对称加密分别是啥，流程是啥，区别何在

  Thought for 2s (ctrl+o to expand)

● 对称加密 — 一把锁，两把一样的钥匙

  例子：快递保险箱

  张三要寄一份合同给李四。

  前提：两人事先约好见面，各拿一把一模一样的钥匙。

  张三:  合同放保险箱 → 用自己的钥匙锁上 → 寄出
                                               ↓
  李四:  收到保险箱 → 用自己的钥匙开锁 → 拿出合同

  偷快递的人: 看到保险箱，没有钥匙，打不开。

  流程：

  非对称加密 — 公开的锁 + 私藏的钥匙

  张三要寄信给李四。

  实际应用 — SSH 的做法（混合）

  非对称安全但慢，对称快但钥匙分发难。实际都用混合：

  例子：还是送快递，但优化一下

  李四:  公开信箱（公钥）。信箱里附一张便利贴：专用保险箱的钥匙。

  张三:  1. 拿到公开信箱
         2. 自己新买一个保险箱+一把钥匙   ← 对称密钥，现买现用
         3. 把保险箱钥匙放进信箱、关上    ← 用公钥加密钥匙
         4. 合同放保险箱、用钥匙锁上      ← 用对称密钥加密合同
         5. 信箱 + 保险箱 一起寄出

  李四:  1. 用私钥打开信箱 → 拿到保险箱钥匙
         2. 用钥匙打开保险箱 → 拿到合同

  偷快递的人: 能开信箱吗？不能，没有私钥。
              没有保险箱钥匙 → 也打不开保险箱。

  这就是 SSH 和 Suite 1/2 的做法：用非对称（ECDH）安全传输一把临时的对称密钥，然后全程用这把对称密钥（AES-GCM
  ）加解密实际数据。非对称只在开头用一下。

❯ 那请你举些简单的算法说明对称加密和解密的具体流程

  Thought for 2s (ctrl+o to expand)

● 先用最简单的 XOR 理解原理，再看真正的 AES。

---
  XOR 加密 — 最简对称加密

  加密：明文 ⊕ 密钥 = 密文

  明文:  H    e    l    l    o
  Hex:  0x48 0x65 0x6C 0x6C 0x6F
  密钥: 0x42 0x42 0x42 0x42 0x42   ← 同一个字节重复
        ⊕    ⊕    ⊕    ⊕    ⊕
  密文: 0x0A 0x27 0x2E 0x2E 0x2D

  解密: 密文 ⊕ 同一个密钥 = 明文
  密文: 0x0A 0x27 0x2E 0x2E 0x2D
  密钥: 0x42 0x42 0x42 0x42 0x42   ← 同一把密钥
        ⊕    ⊕    ⊕    ⊕    ⊕
  明文: 0x48 0x65 0x6C 0x6C 0x6F  =  "Hello"

  XOR 的妙处：(A ⊕ B) ⊕ B = A。加密和解密完全一样——这就是"对称"。

  但 XOR 单字节循环太弱。明文有规律，直接暴漏。所以实际用 AES。

---
  AES — 把搅碎过程复杂化

  AES 本质：字节搅碎 + 替换 + 再来一遍 + 重复 N 轮。每轮都需要密钥参与。

  输入一坨 16 字节，输出一坨 16 字节，看起来完全随机。

  输入:  48 65 6C 6C 6F 20 57 6F 72 6C 64 21 0A 00 00 00  ("Hello World!\n...")
  密钥:  2B 7E 15 16 28 AE D2 A6 AB F7 15 88 09 CF 4F 3C  (16字节随机密钥)
         │
         ▼
  Round 1:  字节替换 → 行移位 → 列混合 → 轮密钥 ⊕
  Round 2:  字节替换 → 行移位 → 列混合 → 轮密钥 ⊕
  Round 3:  字节替换 → 行移位 → 列混合 → 轮密钥 ⊕
   ...
  Round 10: 字节替换 → 行移位 →          轮密钥 ⊕
         │
         ▼
  输出:  47 B1 1F E6 84 F3 9A 9D B3 E3 11 0F 12 3F 99 C1  (一堆乱码)

  逐操作解释：

  ┌──────────┬──────────────────────────────────────────────────┬────────────────────────────────┐
  │   操作   │                      干了啥                      │            通俗理解            │
  ├──────────┼──────────────────────────────────────────────────┼────────────────────────────────┤
  │ 字节替换 │ 每个字节查 S 盒表换成另一个字节                  │ 字母表重排，"A"变"Q"、"B"变"X" │
  ├──────────┼──────────────────────────────────────────────────┼────────────────────────────────┤
  │ 行移位   │ 第 1 行不移，第 2 行左移 1 格，第 3 行左移 2 格… │ 把字母串里的东西换位置         │
  ├──────────┼──────────────────────────────────────────────────┼────────────────────────────────┤
  │ 列混合   │ 列内字节做矩阵乘法（GF(2^8) 代数）               │ 4 个字节互相搅和，一个改全改   │
  ├──────────┼──────────────────────────────────────────────────┼────────────────────────────────┤
  │ 轮密钥 ⊕ │ 用"当前轮的密钥"XOR 整个块                       │ 每一轮混入不同的密钥片段       │
  └──────────┴──────────────────────────────────────────────────┴────────────────────────────────┘

  解密 — 倒着走

  密文:  47 B1 1F E6 84 F3 9A 9D B3 E3 11 0F 12 3F 99 C1
  密钥:  2B 7E 15 16 28 AE D2 A6 AB F7 15 88 09 CF 4F 3C
         │
         ▼
  Round 10: 轮密钥 ⊕ → 行移位逆 → 字节替换逆
  Round  9: 轮密钥 ⊕ → 列混合逆 → 行移位逆 → 字节替换逆
  Round  8: 轮密钥 ⊕ → 列混合逆 → 行移位逆 → 字节替换逆
   ...
  Round  1: 轮密钥 ⊕ → 列混合逆 → 行移位逆 → 字节替换逆
         │
         ▼
  输出:  48 65 6C 6C 6F 20 57 6F 72 6C 64 21 0A 00 00 00  ("Hello World!\n...")

  每一步都有"逆操作"——逆替换、逆移位、逆混合。跟电影倒放一样。

  轮密钥怎么来的

  输入的 16 字节密钥派生成 10 把"子密钥"（AES-128 是 10 轮）：

  原始 Key: 2B 7E 15 16 28 AE D2 A6 AB F7 15 88 09 CF 4F 3C
      │
      ├─ 轮密钥 1:  A0 FA FE 17 88 54 2C B1 23 A3 39 39 2A 6C 76 05
      ├─ 轮密钥 2:  F2 C2 95 F2 7A 96 B9 43 59 35 80 7A 73 59 F6 7F
      ...
      └─ 轮密钥 10: D0 14 F9 A8 C9 EE 25 89 E1 3F 0C C8 B6 63 0C A6

  这叫"密钥扩展"——从一把钥匙派生出 10 把，每轮用不同的。

  为什么解密必须用同一把密钥

  轮密钥的派生顺序加密时正着用（1→10），解密时倒着用（10→1）：

  加密:  明文 ⊕ R1 → 搅碎 → ⊕ R2 → 搅碎 → ... → ⊕ R10 = 密文
  解密:  密文 ⊕ R10 → 搅碎逆 → ⊕ R9 → 搅碎逆 → ... → ⊕ R1 = 明文

  如果用错了密钥 → 轮密钥全错 → 倒放出来的是一坨随机垃圾。

---
  简记

  对称加密 = 搅碎机

  加密:  明文 + 密钥 → [10轮搅碎，每轮加不同调料] → 密文
  解密:  密文 + 同一密钥 → [10轮倒搅，每轮去调料] → 明文

  同一把密钥 → 搅和和还原都能做。
  不同密钥 → 还原出垃圾。

❯ S盒怎么生成的

  Thought for 1s (ctrl+o to expand)

● 两步：先算乘法逆元，再做仿射变换。

  核心公式

  S(x) = AffineTransform(x⁻¹)     x⁻¹ 是 x 在 GF(2⁸) 上的乘法逆元
                                   特殊处理: 0⁻¹ = 0

  具体过程

  Step 1 — 求 GF(2⁸) 乘法逆元

  在 GF(2⁸) 域里：
    对每个输入字节 x (0x00~0xFF)
    找一个 y 使得 (x × y) mod m(x) = 1

    m(x) = x⁸ + x⁴ + x³ + x + 1    ← AES 选定的不可约多项式
    
    比如 x=0x01 → 0x01 × 0x01 = 1 → 逆元是 0x01
         x=0x02 → 要找某个数 y 使 2×y mod m(x) = 1 → 逆元是 0x8D
         x=0x00 → 规定逆元也是 0x00 (0 没有逆元)

  这一步保证了非线性——逆向工程者没法用线性代数反推密钥。

  Step 2 — 仿射变换

  把逆元的 8 个 bit 做固定矩阵乘法，然后 XOR 一个常数：

  ⎡ b₀ ⎤   ⎡1 0 0 0 1 1 1 1⎤ ⎡a₀⎤   ⎡1⎤
  ⎢ b₁ ⎥   ⎢1 1 0 0 0 1 1 1⎥ ⎢a₁⎥   ⎢1⎥
  ⎢ b₂ ⎥   ⎢1 1 1 0 0 0 1 1⎥ ⎢a₂⎥   ⎢0⎥
  ⎢ b₃ ⎥ = ⎢1 1 1 1 0 0 0 1⎥×⎢a₃⎥ + ⎢0⎥
  ⎢ b₄ ⎥   ⎢1 1 1 1 1 0 0 0⎥ ⎢a₄⎥   ⎢0⎥
  ⎢ b₅ ⎥   ⎢0 1 1 1 1 1 0 0⎥ ⎢a₅⎥   ⎢1⎥
  ⎢ b₆ ⎥   ⎢0 0 1 1 1 1 1 0⎥ ⎢a₆⎥   ⎢1⎥
  ⎣ b₇ ⎦   ⎣0 0 0 1 1 1 1 1⎦ ⎣a₇⎦   ⎣0⎦

  a₀~a₇ = 逆元的 8 个 bit  (低位→高位)
  b₀~b₇ = S 盒输出的 8 个 bit

  例子：

  输入 x = 0x53 (字母 'S')
    Step 1: 0x53 在 GF(2⁸) 的乘法逆元 = 0xCA
    Step 2: 0xCA 的 bit 串做仿射变换
    结果 = 0xED
  ⎢ b₆ ⎥   ⎢0 0 1 1 1 1 1 0⎥ ⎢a₆⎥   ⎢1⎥
  ⎣ b₇ ⎦   ⎣0 0 0 1 1 1 1 1⎦ ⎣a₇⎦   ⎣0⎦

  a₀~a₇ = 逆元的 8 个 bit  (低位→高位)
  b₀~b₇ = S 盒输出的 8 个 bit

  例子：

  输入 x = 0x53 (字母 'S')
    Step 1: 0x53 在 GF(2⁸) 的乘法逆元 = 0xCA
    Step 2: 0xCA 的 bit 串做仿射变换
    结果 = 0xED

  所以 S(0x53) = 0xED，在 S 盒里 第 5 行第 3 列 的值是 0xED

  为什么这样设计

  ┌──────────────────────┬───────────────────────────────────────────────────────────┐
  │         设计         │                           作用                            │
  ├──────────────────────┼───────────────────────────────────────────────────────────┤
  │ 乘法逆元             │ 高度非线性——输入和输出关系像乱码。阻断了差分/线性密码分析 │
  ├──────────────────────┼───────────────────────────────────────────────────────────┤
  │ 仿射变换             │ 抹掉 GF(2⁸) 的代数结构。防止攻击者利用域运算的特性反推    │
  ├──────────────────────┼───────────────────────────────────────────────────────────┤
  │ 常数 63 (0x01100011) │ 保证没有定点（S(x)=x）和反向定点（S(x)=NOT x）            │
  └──────────────────────┴───────────────────────────────────────────────────────────┘

  AES 的 S 盒写死在标准里，全世界都一样。256 个值，查表即可，不需要每次实时算。

  前16个值: 63 7C 77 7B F2 6B 6F C5 30 01 67 2B FE D7 AB 76 ...

  不是随机生成的——是数学推导出来的。正因为固定、公开、经过全世界密码学家审查了二十多年，才值得信赖。

❯ 为啥要叫S-BOX

  Thought for 5s (ctrl+o to expand)

● S = Substitution（替换），Box = 盒子。

  就是一个查表替换盒

  输入一个字节 → 查表 → 输出另一个字节

        ┌──────────────────────┐
  0x00→│                      │→ 0x63
  0x01→│                      │→ 0x7C
  0x02→│       S - B O X      │→ 0x77
   ... →│     (替换盒)          │→ ...
  0x53→│                      │→ 0xED
   ... →│                      │→ ...
  0xFF→│                      │→ 0x16
        └──────────────────────┘

  跟小时候"密码本"一个原理：

  密码本（S-Box）:
    A → Q
    B → X
    C → A
    ...

  明文: C A B  → 查密码本 → 密文: A Q X

  AES S 盒就是 256 个条目的密码本，把 0x00~0xFF 一对一映射到另一套 0x00~0xFF。

  名字来自香农

  1949 年香农在《保密系统的通信理论》里提出加密要两步：混淆 + 扩散。

  ┌──────────────────┬─────────────────────────────┬─────────────────────────┐
  │       概念       │           干什么            │       AES 里对应        │
  ├──────────────────┼─────────────────────────────┼─────────────────────────┤
  │ 混淆 (Confusion) │ 搞乱明文和密文的对应关系    │ S-Box（替换）           │
  ├──────────────────┼─────────────────────────────┼─────────────────────────┤
  │ 扩散 (Diffusion) │ 一个 bit 的改动影响整个输出 │ 行移位 + 列混合（置换） │
  └──────────────────┴─────────────────────────────┴─────────────────────────┘

  S-Box 就是"混淆"的具体实现。后来所有对称加密算法都沿用这个名字——DES 有 8 个 S-Box，AES 有 1 个大 S-Box。设计 S-Box 是块密码的核心难点，一个坏的 S-Box 会让整个算法被攻破。

● 这是标准 AES-128 加密，10 轮，处理单个 16 字节块。逐层拆解。

---
  数据布局

  输入的 16 字节按列优先排列成 4×4 矩阵：

  输入字节:  d₀  d₁  d₂  d₃  d₄  d₅  d₆  d₇  d₈  d₉  d₁₀ d₁₁ d₁₂ d₁₃ d₁₄ d₁₅

  矩阵:  ┌              ┐
         │ d₀  d₄  d₈  d₁₂ │  列0
         │ d₁  d₅  d₉  d₁₃ │  列1
         │ d₂  d₆  d₁₀ d₁₄ │  列2
         │ d₃  d₇  d₁₁ d₁₅ │  列3
         └              ┘

  代码里 data[0]、data[1]、data[2]、data[3] 是第一列，data[4..7] 第二列，以此类推。

---
  10 轮主循环，逐行解说

  第 1 步：AddRoundKey + SubBytes（合并）

  data[i + offset] = S_BOX[(data[i + offset] ^ key[i]) & 0xFF];

  先 XOR 轮密钥，再查 S 盒替换。标准 AES 里这是两步，这里合并成一步——结果一样：

  data[i] XOR key[i] → 查 S 盒 → 替换后的值写回 data[i]

  轮 0 用的是原始密钥，后续轮用的是上一轮末尾 KeyExpansion 生成的新密钥。

  第 2 步：ShiftRows（行移位）

  // 第 1 行 (索引 1,5,9,13): 左移 1 列
  buf1 = data[1];        // 暂存 data[1]
  data[1]  = data[5];    // data[5] → data[1]
  data[5]  = data[9];    // data[9] → data[5]
  data[9]  = data[13];   // data[13] → data[9]
  data[13] = buf1;       // 原 data[1] → data[13]

  图解：

  移位前:           移位后:
  ┌           ┐    ┌           ┐
  │ d₀  d₄  d₈  d₁₂│    │ d₀  d₄  d₈  d₁₂│ ← 第 0 行：不动
  │ d₁  d₅  d₉  d₁₃│    │ d₅  d₉  d₁₃ d₁ │ ← 第 1 行：左移 1
  │ d₂  d₆  d₁₀ d₁₄│    │ d₁₀ d₁₄ d₂  d₆ │ ← 第 2 行：左移 2
  │ d₃  d₇  d₁₁ d₁₅│    │ d₁₅ d₃  d₇  d₁₁│ ← 第 3 行：左移 3 (即右移 1)
  └           ┘    └           ┘

  代码中第 2 行左移 2（交换两对），第 3 行左移 3 等价于右移 1（反向转一圈）。

  第 3 步：MixColumns（列混合，末轮跳过）

  if (round < 9)  // 只有前 9 轮做 MixColumns

  每列 4 个字节在 GF(2⁸) 上做矩阵乘法：

  ┌        ┐   ┌              ┐ ┌     ┐
  │ 新d₀  │   │ 2  3  1  1   │ │ d₀  │
  │ 新d₁  │ = │ 1  2  3  1   │×│ d₁  │   在 GF(2⁸) 域上
  │ 新d₂  │   │ 1  1  2  3   │ │ d₂  │
  │ 新d₃  │   │ 3  1  1  2   │ │ d₃  │
  └        ┘   └              ┘ └     ┘

  代码里的实现：

  // 对每列 (i = 0,1,2,3 代表 4 列)
  // col_sum = 列中 4 个字节异或
  buf1 = data[buf4] ^ data[buf4+1] ^ data[buf4+2] ^ data[buf4+3];

  // data[0] 新值 = data[0] ^ GaloisMultiply(data[0] ^ data[1]) ^ col_sum
  // 等价于 2×data[0] + 3×data[1] + data[2] + data[3]

  为什么用 XOR 和 GaloisMultiply？因为在 GF(2⁸) 上：2×a = GaloisMultiply(a)，3×a = a ⊕ 2×a。乘法变成了 GaloisMultiply + XOR 的组合。GaloisMultiply 做的是 GF(2⁸) 上的 ×2
  运算（左移 1 位，若溢出则 XOR 0x1B）。

  第 4 步：KeyExpansion（密钥扩展）

  // 生成下一轮密钥的前 4 字节 (第 0 列)
  key[0] = S_BOX[key[13]] ^ key[0] ^ R_CON[round];  // RotWord + SubWord + Rcon + XOR
  key[1] = S_BOX[key[14]] ^ key[1];
  key[2] = S_BOX[key[15]] ^ key[2];
  key[3] = S_BOX[key[12]] ^ key[3];   // key[12] 而非 key[16%16] - RotWord 效果

  // 后续 12 字节：直接 XOR 前 4 字节对应的位置
  for (i = 4; i < 16; i++)
      key[i] = key[i] ^ key[i - 4];

  key[12..15] 被 RotWord 旋转后映射到 key[13,14,15,12]（顺序变了），查 S 盒，XOR R_CON[round]，再 XOR 上一轮 key 的前 4 字节。后面 12 字节简单 XOR。

---
  末轮后的 AddRoundKey

  for (i = 0; i < 16; i++)
      data[i + offset] = data[i + offset] ^ key[i];

  10 轮循环结束，最后 XOR 一次第十一轮密钥（第 10 轮扩展出来的）。标准 AES 的最后一轮没 MixColumns，但 AddRoundKey 必须做。

  │  轮次   │  AddRoundKey   │ SubBytes  │ ShiftRows │ MixColumns │ KeyExpansion │
  ├─────────┼────────────────┼───────────┼───────────┼────────────┼──────────────┤
  │ Round 0 │ ✅ (合并)      │ ✅ (合并) │ ✅        │ ✅         │ ✅→K1        │
  ├─────────┼────────────────┼───────────┼───────────┼────────────┼──────────────┤
  │ Round 1 │ ✅ (用K1,合并) │ ✅ (合并) │ ✅        │ ✅         │ ✅→K2        │
  ├─────────┼────────────────┼───────────┼───────────┼────────────┼──────────────┤
  │ ...     │ ...            │ ...       │ ...       │ ...        │ ...          │
  ├─────────┼────────────────┼───────────┼───────────┼────────────┼──────────────┤
  │ Round 8 │ ✅ (用K8,合并) │ ✅ (合并) │ ✅        │ ✅         │ ✅→K9        │
  ├─────────┼────────────────┼───────────┼───────────┼────────────┼──────────────┤
  │ Round 9 │ ✅ (用K9,合并) │ ✅ (合并) │ ✅        │ ❌ 跳过    │ ✅→K10       │
  ├─────────┼────────────────┼───────────┼───────────┼────────────┼──────────────┤
  │ Final   │ ✅ (用K10)     │ —         │ —         │ —          │ —            │
  └─────────┴────────────────┴───────────┴───────────┴────────────┴──────────────┘

  代码跟标准唯一区别：AddRoundKey 和 SubBytes 合并成一步 S_BOX[data ^ key]，其余完全一致。

---
  几个细节

  R_CON[round]：轮常数，10 轮各不同：

  R_CON = { 0x01, 0x02, 0x04, 0x08, 0x10, 0x20, 0x40, 0x80, 0x1B, 0x36 }

  每轮用不同的 R_CON 防止轮密钥之间有对称性。

  GaloisMultiply(x)：GF(2⁸) 上 ×2，等价于 (x << 1) XOR (若溢出则 XOR 0x1B)。

  数据就地修改：加密结果直接写回 buff 的 offset 位置，不分配额外空间。

---
  一句话总结

  这个函数 = 在一个 16 字节的块上做标准 AES-128：10 轮替换→移位→混合→扩展密钥，最后一轮跳过混合，末尾补一次 XOR。AddRoundKey 和 SubBytes 合并为一行 S_BOX[data ^
  key]，逻辑等价于标准 AES。

● 先看标准公式

  MixColumns 对一列 4 个字节做矩阵运算：

  新 d0 = 2d0 ⊕ 3d1 ⊕ 1d2 ⊕ 1d3
  新 d1 = 1d0 ⊕ 2d1 ⊕ 3d2 ⊕ 1d3
  新 d2 = 1d0 ⊕ 1d1 ⊕ 2d2 ⊕ 3d3
  新 d3 = 3d0 ⊕ 1d1 ⊕ 1d2 ⊕ 2d3

  GF(2⁸) 上用 XOR 代替加法：3x = x ⊕ 2x = x ⊕ GaloisMultiply(x)。

  直观理解：MixColumns 就是把一列的 4 个字节互相搅和。每个输出字节 = 每个输入字节的加权和（权重是 1/2/3）。

---
  代码的优化

  代码没有直接算 2d0 ⊕ (d1⊕2d1) ⊕ d2 ⊕ d3，而是先算了一个公共项：

  col_sum = d0 ^ d1 ^ d2 ^ d3          // 列中 4 个字节全 XOR

  然后利用 XOR 的结合律化简。

---
  推导：只看 d0

  标准公式：

  新 d0 = 2d0 ⊕ 3d1 ⊕ d2 ⊕ d3
        = 2d0 ⊕ (d1 ⊕ 2d1) ⊕ d2 ⊕ d3      // 3d1 = d1 ⊕ 2d1

  代码做法：

  tmp  = GaloisMultiply(d0 ^ d1)        // = 2(d0 ⊕ d1) = 2d0 ⊕ 2d1  ← 一次乘法算出两个 2×
  新d0 = d0 ^ tmp ^ col_sum
       = d0 ^ (2d0 ⊕ 2d1) ^ (d0 ^ d1 ^ d2 ^ d3)   // 展开
       = d0 ^ 2d0 ^ 2d1 ^ d0 ^ d1 ^ d2 ^ d3       // 拆括号
       = (d0 ^ d0) ^ 2d0 ^ (2d1 ^ d1) ^ d2 ^ d3   // 重新分组
       = 0 ^ 2d0 ^ 3d1 ^ d2 ^ d3                  // d0^d0=0, 2d1^d1=3d1
       = 2d0 ⊕ 3d1 ⊕ d2 ⊕ d3          ✅

  核心技巧：G(d0^d1) 一次 GaloisMultiply 同时算出 2d0 和 2d1。后面 3d1 不需要额外乘法——2d1 已经有了，再 XOR 一次 d1 就是 3d1。

---
  其余三行同理

  d1: G(d1^d2) → 得到 2d1 和 2d2 → 展开消去 → 1d0 ⊕ 2d1 ⊕ 3d2 ⊕ 1d3
  d2: G(d2^d3) → 得到 2d2 和 2d3 → 展开消去 → 1d0 ⊕ 1d1 ⊕ 2d2 ⊕ 3d3
  d3: G(d3^d0) → 得到 2d3 和 2d0 → 展开消去 → 3d0 ⊕ 1d1 ⊕ 1d2 ⊕ 2d3

  每行只调用一次 GaloisMultiply，4 行共 4 次。

---
  为什么这样写

  ┌──────────────┬─────────────────────────────────────────┬─────────────────────────────┐
  │     方式     │           GaloisMultiply 次数           │          XOR 次数           │
  ├──────────────┼─────────────────────────────────────────┼─────────────────────────────┤
  │ 直接照抄公式 │ 8 次（4 列×需要 2d0~2d3）               │ 多                          │
  ├──────────────┼─────────────────────────────────────────┼─────────────────────────────┤
  │ 代码优化     │ 4 次（4 列×1 次/行，利用 XOR 邻居复用） │ 多几个 XOR，但 XOR 几乎免费 │
  └──────────────┴─────────────────────────────────────────┴─────────────────────────────┘

  GaloisMultiply 比 XOR 慢很多——涉及条件溢出判断（if(x & 0x80) x ^= 0x1B）。用廉价 XOR 换掉昂贵的 GaloisMultiply，嵌入式设备上省明显算力。

---
  一句话：col_sum 把 4 个字节的公共部分提前算好，G(相邻两个字节的 XOR) 一次得出两个 2× 结果，剩下的用 XOR 拼出 3×。数学上跟标准矩阵乘法等价，但乘法次数减半。

● KeyExpansion — 从当前轮密钥生成下一轮密钥。

---
  密钥的矩阵布局

  密钥也是 4×4 列优先：

  ┌                    ┐
  │ key[0]  key[4]  key[8]  key[12] │ ← 第 0 列
  │ key[1]  key[5]  key[9]  key[13] │ ← 第 1 列
  │ key[2]  key[6]  key[10] key[14] │ ← 第 2 列
  │ key[3]  key[7]  key[11] key[15] │ ← 第 3 列（最后一列）
  └                    ┘

---
  生成流程

  只对最后一列做特殊处理，其余列直接 XOR。

  旧密钥最后一列: key[12..15]
           │
      RotWord: key[12]→key[15], key[13]→key[12], key[14]→key[13], key[15]→key[14]
           │
      SubWord: 每个字节查 S_BOX
           │
      XOR R_CON[round]
           │
      XOR 旧密钥第 0 列: key[0..3]
           │
           ▼
      新密钥第 0 列: key[0..3] (新)

      key[4] 新 = key[4] 旧 ^ key[0] 新     ← 后面列直接 XOR
      key[5] 新 = key[5] 旧 ^ key[1] 新
      ...
      key[15] 新 = key[15] 旧 ^ key[11] 新

---
  代码逐行

  // RotWord + SubWord + Rcon + XOR 旧第0列

  key[0] = S_BOX[key[13]] ^ key[0] ^ R_CON[round];  // key[13]=原key[14]=RotWord后第0个
  key[1] = S_BOX[key[14]] ^ key[1];                   // key[14]=原key[15]=RotWord后第1个
  key[2] = S_BOX[key[15]] ^ key[2];                   // key[15]=原key[12]=RotWord后第2个
  key[3] = S_BOX[key[12]] ^ key[3];                   // key[12]=原key[13]=RotWord后第3个

  key[13],key[14],key[15],key[12] 就是 RotWord——最后一列向上旋转一个位置。

  原来的 key[12..15]:  12  13  14  15
  RotWord 后:          13  14  15  12   →  查 S_BOX → XOR key[0..3] → 新第0列

  for (i = 4; i < 16; i++)
      key[i] = key[i] ^ key[i - 4];

  新列直接 = 上一轮同列 XOR 刚才算的左边邻居：

  key[4] ^ key[0]  → key[4]   旧第1列 XOR 新第0列 = 新第1列
  key[5] ^ key[1]  → key[5]
  ...
  key[15] ^ key[11] → key[15]  旧第3列 XOR 新第2列 = 新第3列

  round 0: 0x01
  round 1: 0x02
  round 2: 0x04
  round 3: 0x08
  round 4: 0x10
  round 5: 0x20
  round 6: 0x40
  round 7: 0x80
  round 8: 0x1B

  第一步：数据排成 4×4 矩阵

  16 字节按列优先填：

  data[0..15] = d₀ d₁ d₂ d₃ | d₄ d₅ d₆ d₇ | d₈ d₉ d₁₀ d₁₁ | d₁₂ d₁₃ d₁₄ d₁₅

         │ d₁  d₅  d₉  d₁₃ │  第 1 行

         │ d₃  d₇  d₁₁ d₁₅ │  第 3 行

  ┌                     ┐
  │ k₀  k₄  k₈  k₁₂ │  第 0 行
  │ k₁  k₅  k₉  k₁₃ │  第 1 行
  │ k₂  k₆  k₁₀ k₁₄ │  第 2 行
  │ k₃  k₇  k₁₁ k₁₅ │  第 3 行
  └                     ┘

---
  第二步：AddRoundKey（初始轮密钥加）

  标准步骤：

  每个字节: data[i] = data[i] ⊕ key[i]

  矩阵上：状态矩阵 ⊕ 密钥矩阵，逐字节 XOR。

---
  第三步：9 轮主循环（Round 1~9）

  每轮四个操作：

  3.1 SubBytes（字节替换）

  标准步骤：

  每个字节查 S 盒:  data[i] = S_BOX[ data[i] ]

  是非线性替换，打乱明文和密文的代数关系。

  3.2 ShiftRows（行移位）

  标准步骤：

  第 0 行：不移
  第 1 行：左移 1 列     d₁→d₁₃,  d₅→d₁,  d₉→d₅,  d₁₃→d₉
  第 2 行：左移 2 列     d₂↔d₁₀,  d₆↔d₁₄
  第 3 行：左移 3 列     → 等价于右移 1 列

  每行的字节打散到不同列，让上一列的改动扩散到相邻列。

  3.3 MixColumns（列混合）

  标准公式（GF(2⁸) 上的矩阵乘法）：

  ┌        ┐   ┌              ┐ ┌     ┐
  │ 新 d₀  │   │ 2  3  1  1   │ │ d₀  │
  │ 新 d₁  │ = │ 1  2  3  1   │×│ d₁  │    GF(2⁸) 上运算
  │ 新 d₂  │   │ 1  1  2  3   │ │ d₂  │
  │ 新 d₃  │   │ 3  1  1  2   │ │ d₃  │
  └        ┘   └              ┘ └     ┘

  展开：

  新 d₀ = 2d₀ ⊕ 3d₁ ⊕ 1d₂ ⊕ 1d₃
  新 d₁ = 1d₀ ⊕ 2d₁ ⊕ 3d₂ ⊕ 1d₃
  新 d₂ = 1d₀ ⊕ 1d₁ ⊕ 2d₂ ⊕ 3d₃
  新 d₃ = 3d₀ ⊕ 1d₁ ⊕ 1d₂ ⊕ 2d₃

  ▎ 在 GF(2⁸) 上：加法 = XOR，2x = GaloisMultiply(x)，3x = x ⊕ 2x。

  代码简化推导：

  先算公共项 col_sum = d₀ ⊕ d₁ ⊕ d₂ ⊕ d₃。

  以新 d₀ 为例：

  标准: 新 d₀ = 2d₀ ⊕ (d₁ ⊕ 2d₁) ⊕ d₂ ⊕ d₃

  代码: tmp = GaloisMultiply(d₀ ⊕ d₁) = 2d₀ ⊕ 2d₁    ← 一次乘法，得到两个 2×
        新 d₀ = d₀ ⊕ tmp ⊕ col_sum
             = d₀ ⊕ (2d₀ ⊕ 2d₁) ⊕ (d₀ ⊕ d₁ ⊕ d₂ ⊕ d₃)
             = d₀ ⊕ d₀ ⊕ 2d₀ ⊕ 2d₁ ⊕ d₁ ⊕ d₂ ⊕ d₃
             = 0 ⊕ 2d₀ ⊕ 3d₁ ⊕ d₂ ⊕ d₃
             = 2d₀ ⊕ 3d₁ ⊕ d₂ ⊕ d₃  ✅  与标准一致

  其余三行同理，利用相邻字节配对 (d₁,d₂) (d₂,d₃) (d₃,d₀) 各做一次 GaloisMultiply。

  ┌─────────────────────┬────────────────────────────────────────────────┬───────────────────────────────────┐
  │                     │                    标准做法                    │             代码简化              │
  ├─────────────────────┼────────────────────────────────────────────────┼───────────────────────────────────┤
  │ GaloisMultiply 次数 │ 8 次（每列 4 个 2×，但 3× 需额外算 2× 再 XOR） │ 4 次（每行 1 次，用邻居共用结果） │
  ├─────────────────────┼────────────────────────────────────────────────┼───────────────────────────────────┤
  │ XOR 次数            │ 少                                             │ 多几个（XOR 极便宜）              │
  └─────────────────────┴────────────────────────────────────────────────┴───────────────────────────────────┘

  3.4 AddRoundKey（轮密钥加）

  标准步骤：

  data[i] = data[i] ⊕ key[i]     key 是当前轮的密钥

---
  第四步：末轮（Round 10）

  与主循环一致，但 跳过 MixColumns：

  SubBytes → ShiftRows → AddRoundKey

  无列混合。末轮后不扩展密钥。

---
  第五步：KeyExpansion（每轮结束时执行）

  从 Kₙ 生成 Kₙ₊₁ 给下一轮用。

  标准步骤：

  设当前密钥 K，按列分成 W₀ W₁ W₂ W₃（每列 4 字节）

  生成下一轮密钥的 4 列：

    W₀_new = W₀ ⊕ SubWord(RotWord(W₃)) ⊕ RCON[round]
    W₁_new = W₁ ⊕ W₀_new
    W₂_new = W₂ ⊕ W₁_new
    W₃_new = W₃ ⊕ W₂_new

  图解：

  Kₙ:   ┌──────┬──────┬──────┬──────┐
        │  W₀  │  W₁  │  W₂  │  W₃  │
        └──┬───┴──┬───┴──┬───┴──────┘
           │      │      │      │
  Kₙ₊₁:   ▼      ▼      ▼      ▼
        ┌──────┬──────┬──────┬──────┐
        │ W₀'  │ W₁'  │ W₂'  │ W₃'  │
        └──────┴──────┴──────┴──────┘

  W₀' = W₀ ⊕ SubWord(RotWord(W₃)) ⊕ RCON      ← 唯一特殊处理
  W₁' = W₁ ⊕ W₀'
  W₂' = W₂ ⊕ W₁'
  W₃' = W₃ ⊕ W₂'

  代码实现：

  // Step A: RotWord + SubWord + RCON + XOR W₀ → 得到 W₀_new
  key[0] = S_BOX[key[13]] ^ key[0] ^ R_CON[round];  // key[13]=原W₃的第1字节(RotWord后变第0)
  key[1] = S_BOX[key[14]] ^ key[1];
  key[2] = S_BOX[key[15]] ^ key[2];
  key[3] = S_BOX[key[12]] ^ key[3];                  // key[12]=原W₃的第0字节(RotWord后变第3)

  // Step B: 后面 3 列直接 XOR 左边新列
  for (i = 4; i < 16; i++)
      key[i] = key[i] ^ key[i - 4];

  RotWord 的体现：不是取 key[12],key[13],key[14],key[15]（原顺序），而是取 key[13],key[14],key[15],key[12]（旋转后顺序）。

---
  代码中的其他简化

  AddRoundKey + SubBytes 合并

  标准（两步）：

  data[i] = data[i] ⊕ key[i];       // AddRoundKey
  data[i] = S_BOX[data[i]];         // SubBytes

  代码（一步）：

  data[i] = S_BOX[data[i] ^ key[i]];

  先 XOR 再查表，跟先查表再 XOR 逻辑等价，省一次写回。每一轮都是先 XOR 上一轮末尾刚扩展出的新密钥，再查 S 盒。

● 传统做法 — 两遍扫描

  方式: AES-CTR 加密 + HMAC-SHA256 认证

  第一遍: 加密
  明文 ──AES-CTR──→ 密文           用 Block Cipher Key

  第二遍: 签名
  密文 ──HMAC-SHA256──→ MAC 标签    用另一把 Auth Key, 再扫一遍整个密文

  发送: 密文 || MAC 标签

  问题：数据要读两遍。电表 MCU 算力有限，两遍 = 两倍时间。而且需要两把独立的密钥。

---
  AES-GCM — 一遍搞定

  方式: AES-GCM

  明文 ──AES-CTR────→ 密文           }
    │                                  }  同一把密钥
  AAD  ──GHASH(GF乘法)──→ Auth Tag   }  一轮遍历同时产出

  发送: 密文 || Auth Tag

  原理：Counter 模式加密的同时，Galois( GHASH ) 一边读密文一边累加哈希值。数据只读一遍，加密和认证两个结果同时出来。

---
  直观对比

  传统:
    读数据 → AES 加密 → 写密文    (第一遍扫描)
    读密文 → SHA-256 → MAC        (第二遍扫描，再读一次)
    两倍内存读写，两把密钥

  GCM:
    读数据 → AES-CTR 加密 → 写密文
          → GHASH 累加    → Auth Tag
    一遍扫描，一把密钥，两个输出同时出来

---
  为什么 GCM 不直接用 HMAC

  HMAC 底层是 SHA-256——对 32 位 CPU 友好，但对电表这种小 MCU 太重。GHASH 只做 GF(2^128) 乘法和 XOR，硬件上几个门电路就实现：

  ┌──────────┬───────────────────┬──────────────────────┐
  │          │    HMAC-SHA256    │     GHASH (GCM)      │
  ├──────────┼───────────────────┼──────────────────────┤
  │ 运算     │ 大量位运算 + 模加 │ GF 乘 + XOR          │
  ├──────────┼───────────────────┼──────────────────────┤
  │ 硬件成本 │ 高                │ 极低                 │
  ├──────────┼───────────────────┼──────────────────────┤
  │ 处理能力 │ MB/s 级（软件）   │ 100MB/s+（硬件加速） │
  └──────────┴───────────────────┴──────────────────────┘

  所以电表芯片基本都带 GCM 硬件加速。传统 AES+HMAC 要么太慢、要么太贵。

  ┌──────────────┬──────────────────────┬──────────────────────────────────┐

  └──────────────┴──────────────────────┴──────────────────────────────────┘

● Counter（计数器模式）。

---
  原理

  拿一个不断 +1 的计数器，每次用 AES 加密计数器的值，产生密钥流，再 XOR 明文。

  Counter=1  Counter=2  Counter=3  Counter=4
     │          │          │          │
  AES(Key)   AES(Key)   AES(Key)   AES(Key)   ← 加密的是计数器，不是明文
     │          │          │          │
     K₁         K₂         K₃         K₄        ← 密钥流
     ⊕          ⊕          ⊕          ⊕
    明文块1    明文块2    明文块3    明文块4     ← XOR
     ↓          ↓          ↓          ↓
    密文块1    密文块2    密文块3    密文块4

  为什么叫 Counter

  计数器从某个初始值开始，每加密一块 +1。解密时同样的 Counter 序列再跑一遍 AES，得到同样的密钥流，XOR 回去就行。

  加密: Ciphertext = Plaintext ⊕ AES(Key, Counter)
  解密: Plaintext  = Ciphertext ⊕ AES(Key, Counter)   ← 完全一样

  加密和解密操作相同，都不需要 AES 的逆向操作。而且可以随机访问——解密第 1000 个字节不需要先算前 999 个字节的密钥流。

● 换个说法

  普通 AES：直接把明文丢进搅碎机。

  明文 ──AES(密钥)──→ 密文

  CTR 模式：明文根本不进 AES。AES 用来生成一串乱码，然后用乱码掩盖明文。

                      ┌─────────────┐
  Counter=1 ──→ AES(密钥) ──→ K₁ (乱码)  │
  Counter=2 ──→ AES(密钥) ──→ K₂ (乱码)  │── 密钥流: 一堆随机字节
  Counter=3 ──→ AES(密钥) ──→ K₃ (乱码)  │
       ...                    └─────────────┘

  加密: 明文 ⊕ 密钥流 = 密文
  解密: 密文 ⊕ 密钥流 = 明文       （同一把密钥流 XOR 回去）

---
  大白话

  把 AES 当成一个乱码生成器。拿计数器 1,2,3... 喂给 AES，它吐出一串看起来完全随机的字节。这串乱码就是"一次性密码本"。

  明文跟乱码 XOR → 密文。解密时：同样的计数器 → 同样的乱码 → XOR 回去 → 明文。

  明文从头到尾没进过 AES。AES 只负责造乱码。 这就是 AES 基础做法和 Counter 做法之间的致命差异。

  普通方式:  Aes1Encrypt(明文,       密钥) → 密文      ← 明文直接进搅碎机
  CTR 方式:  Aes1Encrypt(Counter值,  密钥) → 乱码      ← 计数器进搅碎机

# 加密与认证

## 1.概念区分

加密（Encryption）与认证（Authentication）是两个独立的安全概念，在 DLMS 中由 Security Control Byte 的不同比特位分别控制，可按需独立启用或组合使用。

| 概念 | 英文 | 保护目标 | 说明 |
| :--- | :--: | :--: | :--: |
| **加密** | Encryption | **机密性（Confidentiality）** | 防止数据被窃听，仅持有密钥的通信双方能够解密明文 |
| **认证** | Authentication | **完整性（Integrity）+ 真实性（Authenticity）** | 检测数据是否被篡改，并确认数据来源为持有密钥的合法方 |

- **加密**
  解决"别人看不到"的问题——密文无法被第三方解读
- **认证**
   解决"别人改不了、冒不了"的问题——任何篡改均会导致认证校验失败

---

## 2.Security Control Byte

DLMS 中，Security Control Byte 第 4 位（A 位）控制认证，第 5 位（E 位）控制加密。二者组合产生四种保护模式：

| E 位 | A 位 | 模式 | 效果 |
| :---: | :---: | :--: | :--: |
| 0 | 0 | **None** | 明文传输，无任何保护 |
| 0 | 1 | **Authenticated only** | 不加密，附加认证标签（GMAC）——内容可见，篡改可检测 |
| 1 | 0 | **Encrypted only** | 仅加密，无认证标签——内容不可见，但密文被篡改无法检测 |
| 1 | 1 | **Authenticated + Encrypted** | 同时加密和认证——内容不可见，篡改可检测 |

**推荐配置**：E=1, A=1，即使用 AES-GCM 同时提供加密与认证保护。E=1, A=0 仅加密不认证的模式存在安全隐患，不应在需要数据完整性的场景中使用。

---

## 3.AES-GCM 的工作原理

AES-GCM 属于 **AEAD（Authenticated Encryption with Associated Data）** 算法族，在单次运算中同时完成加密与认证：

```
加密
Ciphertext = AES-CTR(Plaintext, Key, Nonce)
认证
Auth Tag  = GHASH(AAD, Ciphertext) ⊕ AES(Key, J0)
```

各组件职责：

| 组件 | 作用 |
| :--: | :--: |
| **AES-CTR**（计数器模式） | 加密明文，提供机密性 |
| **GHASH**（伽罗瓦域乘法哈希） | 计算认证标签，提供完整性与真实性校验 |
| **AAD**（Additional Authenticated Data） | 仅认证、不加密的附加数据（如 Security Control Byte、System Title 等）；接收方可读取，但任何篡改都会导致认证标签校验失败 |

接收方解密时，首先校验 Auth Tag；校验通过后再解密。若 Tag 不匹配，密文将被丢弃，不会尝试解密——此机制可防止选择密文攻击。

# 数字签名

## 1.与加密、认证的区别

加密和认证均依赖对称密钥（通信双方共享相同的密钥），而数字签名使用非对称密钥（私钥仅签名方持有），由此引入**不可否认性（Non-Repudiation）**：

| 保护机制 | 密钥类型 | 不可否认性 | 原理 |
| :--: | :--: | :---: | :--: |
| **加密（AES-CTR）** | 对称密钥 | ❌ | 双方持有相同密钥，无法区分发送方 |
| **认证（GMAC）** | 对称密钥 | ❌ | 同上，无法证明消息由哪一方生成 |
| **数字签名（ECDSA）** | 非对称密钥（私钥） | ✅ | 仅签名方持有私钥，签名可被公钥公开验证，签名方无法否认 |

> [!IMPORTANT]
>
> 对称密钥场景下，通信双方持有同一把密钥。如果一方事后抵赖说"这条消息不是我发的"，无法查证——因为对方也持有相同密钥，理论上也能生成同样的认证标签。
>
> 数字签名用非对称密钥。签名方用只有自己持有的私钥签名，验证方用公钥验证。私钥没有共享，所以只要能通过公钥验证，就能证明签名一定是私钥持有者做的。
>
> 举例：DCU 发出一条"断开继电器"的指令并签名。事后如果 DCU方否认发过这条指令，主站可以拿出签名——"这是你的私钥签的，别人签不出来。"这就是"赖不掉"的技术含义。

# 安全策略中的三位独立控制

DLMS 安全策略对请求和响应的三种保护分别控制：

```
Bit 2: authenticated request       — 请求启用认证
Bit 3: encrypted request           — 请求启用加密
Bit 4: digitally signed request    — 请求启用数字签名
Bit 5: authenticated response      — 响应启用认证
Bit 6: encrypted response          — 响应启用加密
Bit 7: digitally signed response   — 响应启用数字签名
```

三种保护机制均为独立控制位，可依据应用场景灵活组合。例如，在已建立加密信道的条件下，可仅要求数字签名而无需重复加密；在广播场景中，可仅要求认证而无需加密。

# 本章总结

| 机制 | 保护目标 | 实现方式 | DLMS 控制位 |
| :--: | :--: | :--- | :--: |
| **加密（Encryption）** | 机密性——防止窃听 | AES-CTR（对称加密） | Security Control Byte E 位（bit 5） |
| **认证（Authentication）** | 完整性 + 真实性——防止篡改与冒充 | GMAC（消息认证码） | Security Control Byte A 位（bit 4） |
| **数字签名（Digital Signature）** | 不可否认性——证明消息来源 | ECDSA（非对称签名） | 安全策略 digital_signed 位 |

三者分别解决不同层次的安全需求：

- 加密解决**机密性问题**——确保传输过程中第三方无法解读数据内容
- 认证解决**完整性与真实性问题**——确保数据未被篡改且来源为持有合法密钥的通信方
- 数字签名解决**不可否认性问题**——确保签名方事后无法否认其曾生成并发送该消息，因为仅签名方持有签名私钥

在实际部署中，应根据威胁模型和保护需求选择合适的组合策略，典型实践是 AES-GCM（加密+认证）配合 ECDSA 数字签名同时启用。

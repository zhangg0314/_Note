### 一句话定因：这是 **C/C++ 可变参数函数（LOGDBG/printf）的栈内存读取错位问题** —— 加了 taskid 后，`%d` 和 `%s` 从栈上「读错了内存地址」，导致时间参数被解析成 NULL，和 taskid 本身无关，只和「参数类型 / 栈布局」有关。

### 先看一个 100% 复现你问题的极简例子

假设你的 `LOGDBG` 是这样封装的（所有 C/C++ 日志宏本质都是 printf 封装）：

cpp



运行









```
#define LOGDBG(fmt, ...) printf(fmt, ##__VA_ARGS__)

// 模拟你的场景：
int task_id = 1;
const char* time_str = "2026-03-16 15:00:00"; // 有效时间字符串

// 情况1：不加taskid → 正常
LOGDBG("当前时间: %s\n", time_str); // 输出：当前时间: 2026-03-16 15:00:00

// 情况2：加taskid，但task_id类型不匹配（比如task_id是long，%d读int）→ 时间变成NULL
long task_id_long = 1; // 假设你的task->task_id是long类型
LOGDBG("[Task %d]当前时间: %s\n", task_id_long, time_str); 
// 输出：[Task 1]当前时间: (null)
```

### 底层原理（通俗版）

LOGDBG/printf 是「无类型检查」的可变参数函数，它的工作逻辑是：

1. 按占位符（`%d`/`%s`）的**类型和顺序**，从栈上「按固定大小」读取数据；

2. ```
   %d
   ```

    要求读 

   4 字节（int）

   ，如果你的 

   ```
   task->task_id
   ```

    是 

   ```
   long
   ```

   （8 字节），那么：

   - 第一步：读 `%d` → 从栈上取前 4 字节（正确读到 task_id）；
   - 第二步：读 `%s` → 本该取 time_str 的地址，但因为前一步多占了 4 字节（long 是 8 字节），导致读到的是「time_str 地址的后半段 / 无效内存」→ 解析成 NULL。

   

简单说：**你加的 taskid 参数「类型」和 `%d` 不匹配（比如 task_id 是 long/uint64_t，而 % d 是 int），导致栈读取错位，时间参数的指针被读成了 NULL**。

### 100% 解决的终极方案（两步走）

#### 步骤 1：强制参数类型匹配（核心）

先确认 `task->task_id` 的类型，然后用对应占位符：

表格







| task->task_id 类型 | 正确占位符 | 错误占位符 |
| :----------------: | :--------: | :--------: |
|        int         |     %d     |     无     |
|        long        |    %ld     |     %d     |
| long long/uint64_t |    %lld    |   %d/%ld   |
|    unsigned int    |     %u     |     %d     |

**修改后的日志代码（按类型匹配）**：

cpp



运行









```
// 假设你的task->task_id是long long类型（最常见的错位原因）
std::string tmp = timePointToString(now);
// 用%lld替代%d，匹配long long类型
LOGDBG("[Task %lld]当前时间: %s,任务当天已经执行", 
       (long long)task->task_id, tmp.c_str());

tmp = timePointToString(task->next_execution);
LOGDBG("[Task %lld]下次开始执行时间: %s", 
       (long long)task->task_id, tmp.c_str());
```

#### 步骤 2：额外兜底（避免任何意外）

即使类型匹配，也用临时变量 + 显式判空，彻底杜绝 NULL：

cpp



运行









```
// 最终版代码（直接复制用）
task->ReadRowEndtime = get_today_end(task->next_execution);

// 1. 时间转换（临时变量，避免析构）
std::string now_str = timePointToString(now);
std::string next_str = timePointToString(task->next_execution);

// 2. 显式类型转换+判空兜底
long long task_id = static_cast<long long>(task->task_id); // 统一类型
const char* now_cstr = now_str.empty() ? "[空时间]" : now_str.c_str();
const char* next_cstr = next_str.empty() ? "[空时间]" : next_str.c_str();

// 3. 日志打印（占位符和类型严格匹配）
LOGDBG("[Task %lld]当前时间: %s,任务当天已经执行", task_id, now_cstr);
LOGDBG("[Task %lld]下次开始执行时间: %s", task_id, next_cstr);
```

### 为什么之前 “不加 taskid 就正常”？

不加 taskid 时，只有 `%s` 一个占位符，栈上只需要读一个 `const char*` 类型的参数，没有读取错位的可能；一加 taskid，`%d` 读错了参数的内存大小，导致后续 `%s` 读错地址，时间就成了 NULL。

### 总结

1. 核心本质：不是 taskid 导致 null，是 `%d` 和 task_id 的类型不匹配，引发栈内存读取错位，时间参数的指针被读成 NULL；
2. 解决关键：让占位符类型（% d/% ld/% lld）和 task_id 的类型严格匹配；
3. 终极保障：用临时变量 + 显式类型转换 + 判空，彻底杜绝任何 NULL 情况。

按这个方案改，加不加 taskid，时间都不会再显示 null 了。

# 架构模式

> **前置**: 架构模式 vs 设计模式 — 见文末 [区别速查](#区别速查架构模式-vs-设计模式)。具体设计模式笔记见 [[07_C++设计模式]]。

## 1. 什么是架构模式

架构模式（Architecture Pattern）是**系统级别**的组织方案，解决"模块/子系统/进程之间如何拼装、如何通信"的问题。

与设计模式的关键区别：

| 维度 | 设计模式 | 架构模式 |
|------|---------|---------|
| **粒度** | 类/对象级别 | 模块/子系统/进程级别 |
| **关注点** | 对象如何创建、组合、交互 | 系统如何分层、组件如何通信 |
| **影响力** | 局部代码结构 | 全局系统骨架 |
| **决策阶段** | 详细设计/编码期 | 概要设计/架构设计期 |

**类比**：盖楼
- 架构模式 = 大楼结构图（几层、承重墙在哪、管道怎么走）
- 设计模式 = 标准化施工技法（门窗怎么装、钢筋怎么绑）

**关系**：架构模式内部会用到设计模式。比如管道架构里每个阶段可能用 Strategy 模式，但"管道"本身是架构模式。

## 2. 常见架构模式

### 2.1 分层架构 (Layered Architecture)

**核心思想**：将系统划分为若干层次，每层只依赖下一层，上层不关心下层实现。

```
┌─────────────────┐
│   表示层 (UI)    │  ← 用户交互
├─────────────────┤
│   业务逻辑层      │  ← 核心规则
├─────────────────┤
│   数据访问层      │  ← DB/文件操作
├─────────────────┤
│   基础设施层      │  ← 硬件/OS/网络
└─────────────────┘
```

**SG698 实例**:

```
gui (LCD菜单) → commun (通信管理) → gatherexe (抄表引擎)
     ↓                                    ↓
  liblcd (framebuffer驱动)          dlmsdb (数据存储)
```

- `gui/` 不直接操作串口,通过 `commun/` 中转
- 上层换 UI 框架不影响底层抄表逻辑

**优点**：职责清晰、替换某一层不影响其他、新人容易理解
**缺点**：层数过多增加延迟、跨层修改可能改多层

---

### 2.2 管道架构 (Pipeline Architecture)

**核心思想**：数据流经一系列处理阶段，每个阶段完成特定转换，前一阶段输出 = 后一阶段输入。

```
[原始数据] → [Stage 1] → [Stage 2] → ... → [Stage N] → [最终结果]
```

**SG698 实例** — 抄表数据流：

```
gathermng(生成任务实例)
    ↓ GuageFile(持久队列)
gatherexe(组帧+发送+收响应)
    ↓ 共享内存
parser(协议解析)
    ↓
dlmsdb(数据库存储)
    ↓
infoproc(数据处理)
    ↓
expthandle(导出/上报)
```

每个阶段独立运行，可并行处理不同批次数据。

**优点**：阶段解耦、易扩展新处理阶段、适合流式数据
**缺点**：整体延迟 = 各阶段延迟之和、前一阶段出错影响后续

---

### 2.3 事件驱动架构 (Event-Driven Architecture)

**核心思想**：系统行为由事件触发，组件间通过事件通知而非直接调用通信。

```
[事件源] ──emit──→ [事件总线] ──dispatch──→ [处理器1]
                     │                        [处理器2]
                     │                        [处理器3]
                     └──────────────────────→ [...]
```

**SG698 实例** — `gatherexe` 事件系统：

```cpp
// 14 种事件通过 CScheduler 事件总线分发
o_scheduler.Attach(&s_softdog);       // 喂狗
o_scheduler.Attach(&s_initMetering);  // 初始化抄表
o_scheduler.Attach(&s_impMetering);   // 重要任务抄表
o_scheduler.Attach(&s_broadMetering); // 广播抄表
o_scheduler.Attach(&s_schedMetering); // 定时抄表
// ... 共 14 个 Handler

// 主循环: 100ms 轮询,有事件则分发
void CScheduler::Update() {
    for (auto& slot : m_slots) {
        if (slot->m_event.BeActive())
            slot->m_handler.Proccess();  // 事件触发 → 处理
    }
}
```

**事件类型** (完整 14 种):
| 事件 | 触发条件 | 处理动作 |
|------|---------|---------|
| TaskUpdate | gathermng 发 IPC | 更新任务队列 |
| TrasTask | 透传任务到达 | 优先级最高,立即执行 |
| ImpTask | 重要任务就绪 | 普通抄表 |
| BroadTask | 广播任务就绪 | 广播抄表 |
| SchedTask | 定时触发 | 周期巡检 |
| InitMetering | 启动/组网完成 | 初始化状态机 |
| ... | | |

**优点**：松耦合、易扩展（加 Handler 不改 Scheduler）、天然支持一对多通知
**缺点**：执行顺序不直观、调试困难（事件链追踪）、同步处理阻塞问题

### 2.4 微内核架构 (Microkernel Architecture)

**核心思想**：最小化核心内核，功能通过插件扩展。内核只负责插件生命周期管理和通信。

```
        ┌──────────┐
        │   插件1   │
        ├──────────┤
 ───────┤   插件2   ├───────
  内核   ├──────────┤  插件管理
 ───────┤   插件3   ├───────
        ├──────────┤
        │   ...    │
        └──────────┘
```

**SG698 实例** — 协议解析器：

```
parser/ (内核: 协议帧路由)
  ├── 698_45/     (插件: DL/T 698.45 协议)
  ├── 645/        (插件: DL/T 645 协议)
  └── dot42/      (插件: HPLC 42协议)
```

新协议只需新增插件模块,不改路由内核。

**优点**：高扩展性、内核稳定、插件独立开发
**缺点**：插件间通信成本、内核接口设计难度大

---

### 2.5 多进程架构 (Multi-Process Architecture)

**核心思想**：系统拆分为多个独立进程，通过 IPC（消息队列/共享内存/管道）通信。

**SG698 实例** — 完整进程拓扑：

```
                    ┌─────────────┐
                    │  gathermng  │  任务调度进程
                    │ (1个实例)    │
                    └──┬──────┬───┘
              MSG_MTR_TASK_UPDATE│(消息队列)
                       │       │
         ┌─────────────┼───────┼──────────────┐
         ▼             ▼       ▼              ▼
   ┌──────────┐  ┌──────────┐ ...  (每物理通道一个进程)
   │gatherexe │  │gatherexe  │
   │ (RS485-I)│  │ (RS485-II)│     抄表执行进程
   └────┬─────┘  └────┬─────┘
        │共享内存      │
        ▼             ▼
   ┌─────────────────────────┐
   │        SHM_TERM_DATA     │  共享内存(全局数据区)
   └────┬────────────────────┘
        │
   ┌────┼────┬──────┬─────────┐
   ▼    ▼    ▼      ▼         ▼
┌────┐┌────┐┌────┐┌────┐
│evt ││inf ││exp ││comm│ ...  业务处理进程
│proc││proc││hdl ││un   │
└────┘└────┘└────┘└────┘
```

**IPC 机制**:
| 机制 | 用途 | 示例 |
|------|------|------|
| System V 消息队列 | 事件通知 | `MSG_MTR_TASK_UPDATE` → gatherexe |
| 共享内存 | 大数据交换 | `SHM_TERM_DATA` — 实时数据/参数 |
| GDBM/GuageFile | 持久任务队列 | gathermng 写入 → gatherexe 读取 |

**优点**：进程隔离(崩溃不互相影响)、资源隔离(内存/CPU 可限制)、自然支持多通道并行
**缺点**：IPC 复杂度、进程启动顺序依赖、调试跨进程问题困难

## 3. SG698 架构全景图

```
┌──────────────────────────────────────────────────────────┐
│                     配置层                                │
│  paramshm(参数共享内存) ← DlmsParam ← TermDoc(硬件参数块) │
├──────────────────────────────────────────────────────────┤
│                     调度层                                │
│     gathermng ──── GuageFile ──── gatherexe              │
│      (任务分解)   (持久队列)     (抄表执行)                │
├──────────────────────────────────────────────────────────┤
│                     处理层                                │
│  parser(协议解析) → dlmsdb(存储) → infoproc(数据处理)     │
│                     → eventproc(事件处理)                 │
├──────────────────────────────────────────────────────────┤
│                     通信层                                │
│  commun ──→ RS485/UDP/Ethernet/PLC                       │
├──────────────────────────────────────────────────────────┤
│                     表示层                                │
│  gui(160x160 LCD) → menu(菜单系统) → screen(安全屏)       │
└──────────────────────────────────────────────────────────┘
```

**数据流向**:
```
1. 配置参数 → paramshm → gathermng (读采集方案)
2. gathermng → GuageFile → gatherexe (任务实例持久化)
3. gathermng → MSG_MTR_TASK_UPDATE → gatherexe (实时通知)
4. gatherexe → RS485/PLC → 电表 (发送协议帧)
5. 电表 → RS485/PLC → gatherexe (响应)
6. gatherexe → SHM_TERM_DATA → parser (解析)
7. parser → dlmsdb → infoproc → expthandle (存储→处理→导出)
```

## 4. 架构决策考量

### 为什么用多进程而不是多线程?

| 考量 | 多进程 | 多线程 |
|------|--------|--------|
| 崩溃隔离 | ✅ 抄表进程崩溃不影响主进程 | ❌ 线程崩溃=整个进程死 |
| 资源限制 | ✅ cgroup 限制 per 进程 | ❌ 线程共享资源配额 |
| 串口独占 | ✅ 每进程独占一个串口 | ⚠️ 需加锁 |
| 内存开销 | ❌ 每进程独立内存,开销大 | ✅ 线程共享内存 |
| IPC 成本 | ❌ 消息队列/共享内存,复杂 | ✅ 共享内存即可 |

嵌入式场景 → 稳定性优先 → 多进程。

### 为什么用事件驱动而不是直接调用?

| 考量 | 事件驱动 | 直接调用 |
|------|---------|---------|
| 扩展新 Handler | ✅ 不改 Scheduler | ❌ 改调用方代码 |
| 一对多通知 | ✅ 天然支持 | ❌ 需手动遍历 |
| 执行顺序 | ❌ 依赖注册顺序,不直观 | ✅ 调用顺序即源码顺序 |
| 调试 | ❌ 事件链难追踪 | ✅ 调用栈清晰 |

16 种事件且持续增加 → 扩展性优先 → 事件驱动。

## 5. 架构反模式 (SG698 实例)

### 5.1 轮询当事件

```cpp
// 反模式: 10 秒轮询检查任务更新 — 不如下发时立即通知
int SchedTask_485::CheckTaskUpdateMsg() {
    static time_t last_check = time(NULL);
    if (fabs(time(NULL) - last_check) > 10) { ... }
}
// 已有 MSG_MTR_TASK_UPDATE 消息队列,应该直接监听而非轮询
```

### 5.2 同步阻塞事件总线

```cpp
// 反模式: 事件处理器同步调用 — 一个慢处理拖慢全部
void CScheduler::Update() {
    for (auto& slot : m_slots) {
        slot->m_handler.Proccess();  // 慢 Handler 阻塞后续所有事件
    }
}
```

### 5.3 全局状态耦合

```cpp
// 反模式: 全局变量 g_metering_stauts 被所有 Handler 读写
int g_metering_stauts = INI_METERING;
// 隐式耦合 → 改一个 Handler 影响其他 → 状态转换难推理
```

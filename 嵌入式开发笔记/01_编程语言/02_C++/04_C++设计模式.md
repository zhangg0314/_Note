# 观察者模式

> **前置**: 设计模式 vs 架构模式 — 设计模式解决"类与类之间怎么组织", 架构模式解决"模块与模块之间怎么拼装"。详见 [[08_架构模式#区别速查架构模式-vs-设计模式|区别速查]]。

## 1.前言介绍

观察者模式面向的需求是：A对象（观察者）对B对象（被观察者）的某种变化高度敏感，需要在B变化的一瞬间做出反应。

举个例子，新闻里喜闻乐见的警察抓小偷，警察需要在小偷伸手作案的时候实施抓捕。在这个例子里，警察是观察者、小偷是被观察者，警察需要时刻盯着小偷的一举一动，才能保证不会错过任何瞬间。

程序里的观察者和这种真正的【观察】略有不同，**观察者不需要时刻盯着被观察者（例如A不需要每隔`1ms`就检查一次B的状态）**，而是**采用注册(Register)或者成为订阅(Subscribe)的方式告诉被观察者**：我需要你的某某状态，你要在它变化时通知我。采取这样被动的观察方式，既**省去了反复检索状态的资源消耗，也能够得到最高的反馈速度**。

## 2.概念定义

观察者模式（Observer），又叫发布-订阅模式（Publish/Subscribe），定义对象间一种一对多的依赖关系，使得每当一个对象改变状态，则所有依赖于它的对象都会得到通知并自动更新。该模式属于**行为型**模式。

## 3.核心内容

### 1.两类四角色

有两大类（主题和观察者）一共四个角色：

- **抽象主题**/抽象被观察者(Subject)角色
  **<u>将所有被观察者对象保存在一个集合中</u>**，可以有任意数量的被观察者。
  抽象主题提供一个接口，可以增加和删除被观察者对象。
- **具体主题**/具体被观察者(Concrete Subject)角色
  该角色将有关状态存入具体被观察者对象，在具体主题的内部状态发生改变时，给所有注册过的观察者发送通知。
- **抽象观察者(**Observer)角色
  它定义了一个更新接口，使得在得到主题/被观察者更新时通知自己
- **具体观察者**(Concrete Observer)角色
  实现抽象观察者定义的更新接口，以便在得到主题/被观察者更新时通知自己更新自身状态

### 2.代码示例

**被观察对象自身应该包含一个容器来存放观察者对象，当被观察者自身发生改变时通知容器内所有的观察者对象自动更新**。

观察者对象可以注册到被观察者的中，完成注册后可以检测被观察者的变化，接收被观察者的通知。当然观察者也可以被注销掉，停止对被观察者的监控。

#### 1.抽象被观察者

```c++
#include <bits/stdc++.h>
//观察者模式
class Observer;

//抽象被观察者
class Subject {
    public:
    Subject() : m_nState(0) {}
    virtual ~Subject() = default;

    virtual void Attach(const std::shared_ptr<Observer> pObserver) = 0;

    virtual void Detach(const std::shared_ptr<Observer> pObserver) = 0;

    virtual void Notify() = 0;

    virtual int GetState() { return m_nState; }

    void SetState(int state) {
        std::cout << "Subject updated !" << std::endl;
        m_nState = state;
    }
    protected:
    	std::list<std::shared_ptr<Observer>> m_pObserver_list;
    	int m_nState;
};
```

#### 2.抽象观察者

```c++
//抽象观察者
class Observer {
    public:
    virtual ~Observer() = default;
    Observer(const std::shared_ptr<Subject> pSubject, const std::string &name = "unknown")
        : m_pSubject(pSubject), m_strName(name) {}

    virtual void Update() = 0;

    virtual const std::string &name() { return m_strName; }
    protected:
    std::shared_ptr<Subject> m_pSubject;
    std::string m_strName;
};
```

#### 3.具体被观察者

```c++
//具体被观察者
class ConcreteSubject : public Subject {
    public:
    void Attach(const std::shared_ptr<Observer> pObserver) override {
        auto iter = std::find(m_pObserver_list.begin(), m_pObserver_list.end(), pObserver);
        if (iter == m_pObserver_list.end()) {
            std::cout << "Attach observer" << pObserver->name() << std::endl;
            m_pObserver_list.emplace_back(pObserver);
        }
    }

    void Detach(const std::shared_ptr<Observer> pObserver) override {
        std::cout << "Detach observer" << pObserver->name() << std::endl;
        m_pObserver_list.remove(pObserver);
    }

    //循环通知所有观察者
    void Notify() override {
        auto it = m_pObserver_list.begin();
        while (it != m_pObserver_list.end()) {
            (*it++)->Update();
        }
    }
};
```

```c++

    std::shared_ptr<Subject> pSubject = std::make_shared<ConcreteSubject>();// 创建被观察者

    // 创建观察者
    std::shared_ptr<Observer> pObserver1_1 = std::make_shared<Observer1>(pSubject, "1");
    std::shared_ptr<Observer> pObserver1_2 = std::make_shared<Observer1>(pSubject, "2");
    std::shared_ptr<Observer> pObserver1_3 = std::make_shared<Observer1>(pSubject, "3");

    std::shared_ptr<Observer> pObserver2_4 = std::make_shared<Observer2>(pSubject, "4");
    std::shared_ptr<Observer> pObserver2_5 = std::make_shared<Observer2>(pSubject, "5");
    std::shared_ptr<Observer> pObserver2_6 = std::make_shared<Observer2>(pSubject, "6");

    // 注册观察者
    pSubject->Attach(pObserver1_1);
    pSubject->Attach(pObserver1_2);
    pSubject->Attach(pObserver1_3);
    pSubject->Attach(pObserver2_4);

    pSubject->Detach(pObserver1_1);

    return 0;
    //运行结果如下：
```

### 4.总结对比

#### 1.优点

1. 观察者和被观察者是抽象耦合的。
2. 建立了一套触发机制。

#### 2.缺点

1. 如果一个被观察者对象有很多的直接和间接的观察者的话，将所有的观察者都通知到会花费很多时间。
2. 如果被观察者和观察目标间有循环依赖，观察目标会触发它们之间进行循环调用，可能导致系统崩溃。
3. 观察者模式没有相应的机制让观察者知道所观察的目标对象是**怎么发生变化**的，而仅仅**只是知道观察目标发生了变化**。

## 4.适用场景

### 1.需要联动

即一个对象状态变化，需要联动多个对象响应。

- **核心逻辑**
  被观察者（如任务状态、设备状态）的变更，需要触发多个独立功能模块（观察者）的动作，且观察者数量可能动态变化。
- **嵌入式 / AMR 场景示例**
  - 电力终端的 “抄表任务状态变更”：当任务从 “待执行” 变为 “执行完成” 时，需要通知：
    - 日志模块：记录任务执行结果；
    - 上报模块：将抄表数据上传到主站；
    - 存储模块：将数据写入本地 Flash；
    - 告警模块：若执行失败，触发本地告警。
  - 数据采集终端的 “设备连接状态变更”：当某块电表从 “离线” 变为 “在线” 时，需要通知：
    - 任务调度模块：恢复该电表的定时抄表任务；
    - 通信模块：建立与电表的通信连接；
    - 状态显示模块：更新 LCD 屏上的设备状态。

### 2.需要解耦

即观察者与被观察者需要解耦，便于扩展和维护。

- **核心逻辑**
  被观察者不需要知道具体是哪些观察者在监听，只需依赖观察者的统一接口；新增 / 删除观察者时，无需修改被观察者的代码（符合 “开闭原则”）。
- 嵌入式 / AMR 场景示例
  - 电力终端新增 “远程控制模块”
    需要在 “抄表任务完成” 时接收通知，执行远程指令（如远程拉闸）。此时只需让该模块实现`TaskTrigger`接口，通过`Attach`注册到主题，无需修改`TaskSubject`的核心逻辑。
  - 多地区差异化需求
    不同地区（如江苏、北京）的终端可能需要额外的观察者（如江苏地区的 “阶梯电价计算模块”），通过观察者模式可灵活添加，不影响其他地区的代码。

### 3.需要动态性

即观察者需要动态注册 / 注销（运行时灵活调整响应关系）

- **核心逻辑**
  观察者可能在程序运行时启动、退出，需要动态加入或退出通知列表，避免无效通知或资源浪费。
- 嵌入式 / AMR 场景示例
  - 数据采集终端的 “调试模块”
    仅在调试模式下启动，注册为观察者，接收任务状态通知用于调试输出；调试结束后注销，不再接收通知，节省系统资源。
  - 热插拔设备的状态通知
    当外接的通信模块（如 4G 模块）被拔出时，注销其对应的观察者，避免通知不存在的模块导致野指针崩溃。

### 4.需要不同处理

 即多个观察者对同一事件有不同处理逻辑（职责单一）

- **核心逻辑**
  每个观察者专注于自己的职责（如日志、上报、告警），被观察者仅负责 “通知事件”，不关心观察者的具体处理逻辑，符合 “单一职责原则”。
- 嵌入式 / AMR 场景示例
  - 终端的 “通信异常事件”：
    - 日志观察者：记录异常时间、异常码；
    - 告警观察者：触发蜂鸣器告警、LED 闪烁；
    - 恢复观察者：尝试重新连接通信模块；
    - 上报观察者：将异常信息上传到主站。

### 5.任务调度系统

- 被观察者：任务调度器；
- 观察者：各个业务线程（如抄表线程、通信线程、维护线程）；
- 触发事件：任务就绪、任务取消、任务优先级变更。

## 6. 实践总结

> 以下内容来源于 SG698 集中器项目 `gatherexe` / `gathermng` 进程的代码评审讨论。

### 1.四步判断口诀

```
看代码时问三个问题:
  Q1: 一个事件发生, N个地方需要知道?          → Observer
  Q2: 新增"知道后做什么"要不要改触发源头?      → 要改=不适合, 不改=Observer
  Q3: 触发者和执行者的生命周期是否独立?        → 独立=Observer
  Q4: 需要事后把同步改成异步而不动业务代码?    → 必须用Observer
```

### 2 四种适用的代码

#### 1.`while(1) + sleep(N) + if(check)` 轮询

```cpp
// 坏: CPU空转或响应延迟
while (1) {
    if (CheckNewFile()) ProcessFile();
    if (CheckNewTask())  ProcessTask();
    usleep(100000);  // 100ms 轮询 — CPU浪费 vs 响应延迟的两难
}
```

→ 用 Observer: 事件源主动通知, 无需轮询。

#### 2.一个状态变化 → 通知 N 个模块, N 会增长

```cpp
// 坏: 加一个新功能就加一行调用
void MeterDoc::Update(int id, Data d) {
    m_docs[id] = d;
    m_ui->Refresh(id);        // 每次加新功能
    m_logger->LogChange(id);  // 都要改这个函数
    m_sync->SyncToRoute(id);
}
```

→ 用 Observer: `OnMeterChanged.Emit(id)`, 新功能只需新增 `Connect`, 不改 `MeterDoc`。

#### 3.一个事件 → 多种处理路径, 路径持续增加

```cpp
// 坏: 帧类型→处理分支, 无限膨胀
void OnMeterResponse(uint8_t* buf, int len) {
    if (buf[0] == 0x68)      ParseMeteringData(buf, len);
    else if (buf[0] == 0xFE) ParseEvent(buf, len);
    else if (IsHeartbeat(buf)) UpdateAliveTime(id);
    // 透传、ESAM、广播响应...一直加
}
```

→ 用 Observer: `Dispatcher.Register(frameType, handler)`, 开闭原则。

#### 4.多层嵌套回调

```cpp
// 坏: 5 层嵌套
void DoMetering(Meter m, function<void(Result)> onDone) {
    SendFrame(m, [=](Frame f) {
        WaitResponse(f, [=](Buf b) {
            ParseData(b, [=](Data d) {
                StoreDB(d, [=]() { onDone(Result::OK); });
            });
        });
    });
}
```

→ 用 Signal 链: 每步独立, `onFrameSent.Connect(...) → onResponse.Connect(...)`, 扁平化。

### 3.同步 Observer 

同步 Observer 运行时行为跟直接调用一模一样— A 还是被 B 阻塞:

```cpp
// 直接调用:
void A::DoWork() {
    B::Handle(x);  // 阻塞
    C::Handle(x);  // 阻塞
}

// 同步 Observer:
void A::DoWork() {
    m_sig.Emit(x);  // 阻塞 — 内部逐个调 B, C, D
}
```

区别在编译期, 不在运行时

| 维度 | 直接调用 | 同步 Observer |
|:----:|:---:|:---:|
| A 依赖 B 的头文件? | ✅ 必须 | ❌ 不需要 |
| B 不存在能编译 A? | ❌ 链接失败 | ✅ 编译通过 |
| 加新观察者要改 A? | ✅ 改 A 源码 | ❌ 只加 Connect |
| 单元测试 A 要 mock B? | ✅ 必须 | ❌ 不关心 B |
| 想改成异步? | 🔧 改 A 源码 | 🔧 只改 Signal 实现 |

**本质**: 同步 Observer = **编译期解耦** (谁处理) + 为**运行时解耦** (何时处理) 留了后门。阻塞是继承的毛病, 不是 Observer 引入的。

#### 2.参数变更检测

#### 3.直接调用导致无法异步

```cpp
// CScheduler::Update() 同步遍历, 如果某个 Handler::Proccess() 执行 3 秒
// (抄一个表), 其他 13 个事件全部排队等待 — 这是非抢占状态机的根因
void CScheduler::Update() {
    for (auto& slot : m_slots) {
        if (slot->m_event.BeActive())
            slot->m_handler.Proccess();  // ← 同步阻塞, 无法跳过
    }
}
```

# 工厂模式

## 1.工程模式介绍

> [!CAUTION]
>
> 这种类型的设计模式属于创建型模式，它提供了一种创建对象的最佳方式。
> 在工厂模式中，我们在创建对象时不会对客户端暴露创建逻辑，并且是通过使用一个共同的接口来指向新创建的对象。

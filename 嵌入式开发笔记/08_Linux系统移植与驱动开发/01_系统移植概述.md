



# 系统移植概念

## 1.系统移植本质

系统移植本质就是安装系统，在基于 ARM 处理器的开发板上安装 Linux 操作系统。

## 2.系统移植必要

- 不同架构的处理器指令集不兼容，即便是相同的处理器架构，板卡不同，驱动代码也不兼容。
- 当 Linux 系统装上后，去移植一些应用层的东西，凡是二进制的文件包括 ELF 格式的，都区分 x86 和 ARM 架构，因此涉及到二进制文件的都需要进行移植（比如移植第三方库如 sqlite3）。
- Linux 是一个通用的内核并不是为某一个特定的处理器架构或板卡设计的，所以从官方获取 Linux 源码后要先经过相应的配置使其与我们当前的硬件平台相匹配后才能进行编译和安装。

# 系统移植过程

以SD卡启动加载为例：

1. 准备 Linux 内核镜像、SD 卡启动盘。
2. 通过拨码开关选择启动方式（SD 启动）。
3. 通过 SD 卡中的引导程序安装系统。
4. 安装 Linux 驱动程序。
5. 安装 Linux 应用程序。

# 传统操作流程

## 1.背景介绍

​	传统操作流程中，开发板的 Linux 系统移植开发会回到"**零散资源手动整合、逐个环节从零调试**"的传统流程。这个过程需要开发者自己搞定从"硬件适配"到"软件编译"的所有细节，门槛高、耗时长，且容易因资源不匹配或配置错误导致失败。

## 2.查阅硬件信息

​	`SDK`会提前适配好开发板的硬件细节，但没有`SDK`时，必须先自己"摸清硬件底细"，否则后续软件开发会完全"无的放矢"。

1. **查芯片手册**
   找到开发板主芯片的官方 `datasheet` 和 reference manual，明确 CPU 架构、内存接口、存储控制器、外设接口的硬件地址和配置方式。
2. **查开发板原理图**
   确认外设的实际连接（比如网口芯片型号是 `DM9000` 还是 `RTL8189`、LCD 屏的引脚接在芯片哪个` GPIO` 上），避免后续驱动配置与硬件不匹配。
3. **确认硬件参数**
   记录关键参数（如 `DDR` 内存大小/频率、Flash 容量/分区、串口波特率等），直接影响后续 U-Boot、内核的配置。

## 3. U-Boot 适配

U-Boot 是嵌入式系统的"引导程序"，负责初始化硬件、加载 Linux 内核。

1. **下载通用 U-Boot 源码**
   从 U-Boot 官方仓库下载对应芯片架构的基础版本，但官方源码通常只支持"芯片评估板"，不直接支持定制开发板。
2. **手动修改 U-Boot 适配硬件**
   - 编写板级配置文件：在 `board/` 目录下为开发板新增文件夹，实现内存初始化、串口初始化、存储设备识别等逻辑。
   - 配置设备树（`DTS`）：编写对应开发板的设备树文件，描述硬件资源。
   - 解决编译错误：逐一查手册、改代码调试。
3. **烧录 U-Boot 并验证**
   用专用工具将编译好的 U-Boot 镜像烧录到存储设备，通过串口查看启动日志。

## 4.定制Linux 内核

1. **下载内核源码**
   从 Linux 官方仓库或芯片厂商官网下载对应版本的内核源码。
2. **内核配置**
   - 通过 `make menuconfig` 手动勾选架构、驱动、文件系统支持等选项。
   - 修改或新增内核的设备树文件，确保内核启动后能识别所有硬件。
3. **编译内核**
   执行 `make zImage` 和 `make dtbs`，过程中反复调整配置或修改驱动代码。
4. **验证内核**
   将编译好的内核镜像和设备树镜像通过 U-Boot 加载，查看串口日志。

## 5.构建根文件系统

1. **选择构建工具**
   - 轻量选择
     用 `BusyBox`，通过 `make menuconfig` 勾选需要的命令，编译后手动创建目录结构。
   - 复杂选择
     用 `Buildroot` 或 `Yocto Project`（自动化构建工具）。
2. **完善文件系统**
   添加库文件、配置初始化脚本、安装测试工具。
3. **制作文件系统镜像**
   用 `mkfs.ext4` 等工具将根文件系统目录打包成镜像文件。

## 6.获取并配置具链

1. **下载工具链**
   从芯片厂商官网下载对应架构的工具链，或用 `crosstool-ng` 手动编译。
2. **配置环境变量**
   通过 `export PATH=$PATH:/path/to/toolchain/bin` 配置工具链路径。
3. **验证工具链兼容性**
   确保工具链版本与内核、根文件系统匹配，否则会出现` ABI `不兼容错误。

## 7.烧录与调试

1. **分区规划**
   手动对存储设备分区（如分区1-U-Boot、分区2-内核、分区3-根文件系统）。
2. **手动烧录**
   用 `dd` 命令或专用工具将各镜像烧录到对应分区。
3. **调试启动逻辑**
   通过 U-Boot 命令行设置启动参数，根据串口日志定位问题。
4. **外设测试**
   启动成功后手动测试每个外设，若不可用需回头修改内核驱动或设备树。

# SDK 方式

## 1.`SDK`的概念

`SDK` 全称是 Software Development Kit，即"软件开发工具包"。它是为了方便开发者开发特定软件或硬件相关程序而打包好的一系列工具、资源的集合。比如创龙开发板的 Linux SDK，里面就包含了开发该开发板 Linux 系统所需的各种关键东西：启动程序（U-Boot）、内核代码（Kernel）、文件系统（Filesystem），还有编译工具、配置脚本等。

## 2.传统流程 vs `SDK` 对比

| 环节 | 无 SDK（传统流程） | 有 SDK |
|:----:|:-------------------:|:------:|
| 资源获取 | 手动从官网/仓库下载 U-Boot、内核、工具链，分散且版本难匹配 | SDK 打包好所有适配资源，解压即可用 |
| 硬件适配 | 自己编写板级代码、设备树，反复查手册调试 | SDK 已提前适配好开发板，设备树、驱动均现成 |
| 编译配置 | 手动 `make menuconfig` 逐项配置，易出错 | SDK 提供现成配置文件，一键编译 |
| 调试效率 | 每个环节出错需逐一排查，周期可能长达数周 | 基础功能已验证，聚焦上层开发 |

## 3.总结

没有 `SDK` 的传统流程，本质是"**还原嵌入式开发的底层细节**"——需要开发者同时掌握硬件原理、底层软件（U-Boot、内核驱动）、交叉编译等技能，且耗时耗力。而 SDK 的核心价值就是"**把这些重复、复杂的底层工作提前做好**"，让开发者跳过"适配硬件、整合资源"的环节，直接聚焦上层应用开发。

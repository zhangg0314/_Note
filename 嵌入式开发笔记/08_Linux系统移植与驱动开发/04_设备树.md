# 设备树起源

设备树是一种描述硬件的数据结构，它起源于`OpenFirmware`。在Linux 2.6中， ARM架构的板极硬件细节过多地被硬编码在`arch/arm/plat-xxx`和`arch/arm/mach-xxx`中，采用设备树后，许多硬件的细节可以直接通过它传递给Linux，而不再需要在内核中进行大量的冗余编码。设备树具有以下特征：

- 减少垃圾代码

- 减轻驱动开发工作量

- 驱动代码和设备信息分离

- 参考`Open Fireware`设计

- 用来记录硬件平台中各种硬件设备的属性信息

------

# 概念组成

## 1. 核心概念

- 硬件描述文件：用树形结构描述CPU、内存、总线、外设等硬件信息
- 不依赖编程语言：采用人类可读的文本格式（类似JSON）
- 独立于操作系统：由Bootloader（如U-Boot）传递给内核

## 2. 设备树文件类型

|               扩展名                |       类型       |             说明             |
| :---------------------------------: | :--------------: | :--------------------------: |
|     `.dts`(device tree source)      |   设备树源文件   |      人类可读的文本描述      |
| `.dtsi`(device tree source include) |   设备树头文件   | 可被多个`.dts`包含的通用配置 |
|     `.dtb`(device tree binary)      | 设备树二进制文件 | 由`.dts`编译生成，供内核使用 |

------

# 设备树文件组织与分层

## 1. 为什么源文件有多个

设备树是树状结构，支持 `#include`。分层的目的在于**复用**：避免同一份芯片描述在几十块开发板间重复拷贝。最终一个板子对应**一个 `.dtb`**，但源文件是 **1 个 `.dts` + 多个被包含的 `.dtsi`**，编译时由 DTC 合并（flatten）为单个二进制。

典型的 include 链（以 Exynos4412 为例）：

```txt
exynos4412-origen.dts            ← 板级（具体开发板）
    → exynos4412.dtsi            ← 芯片专属
        → exynos4x12.dtsi        ← 芯片子系列
            → exynos4.dtsi       ← 芯片家族基座
            → exynos4x12-pinctrl.dtsi   ← 引脚复用
```

## 2. SoC 级 `.dtsi` 与板级 `.dts` 的分工

|              | SoC 级 `.dtsi`             | 板级 `.dts`                     |
| ------------ | -------------------------- | ------------------------------- |
| 描述对象     | 芯片内部硬件               | 具体开发板如何用芯片            |
| 决定者       | 芯片厂商                   | 板子设计者                      |
| 典型内容     | 控制器基址、中断号、时钟、`compatible` | `status`、引脚选择、板载外设 |
| 复用         | 几十块板共用一份           | 一块板一份                      |

### 2.1 SoC 级 `.dtsi` 一般定义

- 根节点 `compatible`（芯片型号标识）
- `cpus` 节点（核数、频率、cache）
- 中断控制器 GIC、时钟控制器
- `soc` 总线节点（片内外设地址范围）
- 各外设控制器节点（UART / SPI / I2C / MMC / DMA / 定时器 / watchdog / RTC），默认 `status = "disabled"`
- `pinctrl` 引脚复用组（内容多时单独拆成 `-pinctrl.dtsi`）

一个典型的外设控制器节点：

```dts
serial@13800000 {
    compatible = "samsung,exynos4210-uart";  /* 驱动绑定的 key */
    reg = <0x13800000 0x100>;                /* 寄存器基址 */
    interrupts = <0 52 0>;                   /* 中断号 */
    clocks = <&clock 316>;                   /* 时钟 */
    status = "disabled";                     /* 默认关，板级再开 */
};
```

基址、中断号、时钟、驱动绑定这些是芯片决定的，所有板子相同，故放 SoC 级；板级只管开关和引脚。

### 2.2 板级 `.dts` 一般定义

- `#include` SoC 级 dtsi
- 开/关外设（`status = "okay"`）
- 选择引脚（`pinctrl-0`）
- 板载外设、`memory`、`chosen` 等

## 3. U-Boot 与 Linux 各有一份设备树

U-Boot 和 Linux 是两个独立项目，各自维护一份设备树，物理上是不同的文件，编译出各自的 `.dtb`。U-Boot 那份通常从内核同步后按需裁剪。

|        | 目录（ARM）                                        | 特点                             |
| ------ | -------------------------------------------------- | -------------------------------- |
| Linux  | `arch/arm/boot/dts/`（64 位 `arch/arm64/boot/dts/`） | 完整，含全部外设与 pinctrl       |
| U-Boot | `arch/arm/dts/`（新版含 `dts/upstream/src/`）       | 精简，只保留 U-Boot 需要的外设   |

U-Boot 用不到完整引脚复用表（引脚复用常直接写寄存器），因此不复制 `pinctrl.dtsi`；它支持的板子才放板级 dts。裁剪原则：**谁用得到就放谁那**。

## 4. 文件命名规律

| 类型       | 命名                        | 例                            |
| ---------- | --------------------------- | ----------------------------- |
| 板级       | `<soc>-<板名>.dts`          | `exynos4412-origen.dts`       |
| SoC 级     | `<soc>.dtsi`                | `exynos4412.dtsi`             |
| 引脚复用   | `<soc>-pinctrl.dtsi`        | `exynos4x12-pinctrl.dtsi`     |

## 5. 修改设备树的方法（三步定位）

1. **定项目**：改启动早期 / 串口打印 / DDR / 启动介质 → U-Boot；改内核驱动外设 / 引脚 / 设备功能 → Linux。
2. **定层级**：开外设、换引脚、加板载外设 → 板级 `.dts`；改芯片控制器基址 / 中断 / 时钟 → SoC `.dtsi`。
3. **定文件**：进入对应 dts 目录，按板名 grep 定位板级 `.dts`，再顺 include 链找到相关 `.dtsi`。

```bash
grep -r "板名或芯片名" arch/arm/boot/dts/
```

## 6. pinctrl 的正确改法

优先在**板级 `.dts`** 中覆盖或新增引脚组，不要直接修改 SoC 的 `pinctrl.dtsi`。

- dtsi 已有现成引脚组 → 直接引用：

```dts
&serial_0 {
    status = "okay";
    pinctrl-0 = <&uart0_data>;   /* 用 dtsi 现成的组 */
};
```

- dtsi 无所需引脚组合 → 在板级 `.dts` 新增引脚组并引用：

```dts
&pinctrl_0 {
    uart0_board: uart0-board {          /* 板级新增 */
        samsung,pins = "gpb0-2", "gpb0-3";
        samsung,pin-function = <2>;
    };
};
&serial_0 {
    status = "okay";
    pinctrl-0 = <&uart0_board>;
};
```

## 7. 移植板子要改什么

设备树层面以**板级 `.dts`** 为主，pinctrl 次之（且加在板级 `.dts` 里）。但整体移植不止设备树，还包括：

| 事项             | 位置                              |
| ---------------- | --------------------------------- |
| 设备树（外设/引脚） | 板级 `.dts`                       |
| 内核驱动开关     | `defconfig`（menuconfig 开驱动）  |
| U-Boot 板级适配  | `board/<厂商>/<板名>/`            |
| 芯片不支持的驱动 | 在 `drivers/` 中新增驱动          |

# 基本语法

## 3. 特征介绍

- `.dts`文件主体内容由多个节点组成。

- 每个节点可以包含0或多个子节点，形成树状关系。

- 每个`.dts`文件都有一个根节点，其它节点都是它的子孙。

- 根节点一般来描述整个开发板硬件平台，其它节点用来表示具体设备、总线的属性信息。

- 各个节点可以有多个属性，每个属性用key-value键值对来表示。


## 4. 节点语法

```shell
[label:] node-name[@unit-address] {    
	[properties definitions];    
	[child nodes];
};

label: 可选项，节点别名，为了缩短节点访问路径，后续节点中可以使用&label来表示引用指定节点
node-name: 是设备节点的名称，为ASCII字符串


#unit-address: 设备地址，一般填写该设备寄存器组或内存块的首地址，如果某个节点没有地址或者寄存器的话 “unit-address” 可以不要，node-name相同的情况下，可以通过不同的unit-address定义不同的设备节点。


properties definitions：属性定义，（键值对）
child nodes:子节点
```

## 5. 属性语法

```shell
[label:] property-name = value;
[label:] property-name;


#属性可以无值
#有值的属性，可以有三种取值：
1. arrays of cells(1个或多个32位数据, 64位数据使用2个32位数据表示，空格分隔),用尖括号表示< >
2. string(字符串), 用双引号表示" "
3. bytestring(1个或多个字节，空格分隔),用方括号表示[]
4. 用,分隔的多值即
    value = "gpx1-0","gpx2-0","gpx3-0";
	value = <11000c40 00000456>,<00000789,00000123>,......,
	value = [11 00 0c 40 00 00 04 56],[00 00 07 89 00 00 01 23]
```

# 常用属性

## 6. `phandle`

> [!CAUTION]
>
> DTS中的大多数设备树将不包含显式的`phandle`属性，当DTS被编译成二进制DTB格式时，DTC工具会自动插入`phandle`属性。

数字形式的节点标识，在后续节点中属性值性质表示某节点时，可以引用对应节点，它的取值必须是唯一的(不要跟其他的`phandle`值一样)，例如：

```c
pic@10000000 {    
	phandle = <1>;   // 数字1相当于身份证号，代表pic这个结点
	interrupt-controller;
};
another-device-node {    
	interrupt-parent = <1>;   // 使用phandle值为1来引用上述节点，说明中断控制器用的是1号中断控制器即pic@10000000
};
```

## 7. `status `属性

status 属性看名字就知道是和设备状态有关的， status 属性值也是字符串，字符串是设备的状态信息，可选的状态如下表所示：

|  status值  |         描述         |
| :--------: | :------------------: |
| "disabled" |  禁用，不会绑定驱动  |
|   "fail"   | 初始化失败（不常用） |
|   "okay"   |         启用         |

### 7.1 **⚠️ 常见坑**

- 没写 `status`，默认可能是 `"disabled"`
- 父节点被禁用，子节点也会被递归忽略
- 字段拼写错误如 `statuss` → 驱动永远不调用！

**建议：** 对所有新增设备节点都显式写上 `status = "okay";`。

## 8. 地址属性

### 8.1 `reg`

`reg`属性的值一般是 (address， length) 对，`reg `属性一般用于描述设备地址空间资源信息，一般都是某个外设的寄存器地址范围信息。例如：一个设备有两个寄存器块，一个的地址是0x3000，占据32字节；另一个的地址是0xFE00，占据256字节，表示如下：

```c
reg = <0x3000 0x20 0xFE00 0x100>;
//注：上述对应#address-cells = <1>; #size-cells = <1>;。
reg = <address1 length1 [address2 length2] [address3 length3]>;
//address：起始地址
//length：大小
```

### 8.2 `#address-cells`和`#size-cells`

`#address-cells`和 `#size-cells`的值都是无符号 32 位整型，可以用在任何拥有子节点的设备中，用于描述子节点的地址信息。`#address-cells`属性值决定了子节点 `reg `属性中地址信息所占用的字长(32 位)，` #size-cell` 属性值决定了子节点 `reg `属性中长度信息所占的字长(32 位)。`#address-cells` 和` #size-cell`s 表明了子节点应该如何编写` reg `属性值，一般` reg` 属性都是和地址有关的内容，和地址相关的信息有两种：起始地址和地址长度，reg 属性的格式一为：

```text
reg = <address1 length1 address2 length2 address3 length3……>
```

`reg`属性中, 使用多少个u32整数来描述地址(address)，语法：

```text
#address-cells = <数字>;
```

`reg`属性中, 使用多少个u32整数来描述大小(size)，语法：

```text
#size-cells = <数字>;
```

例如一个64位的处理器：

```text
soc {
    #address-cells = <2>;
    #size-cells = <1>;
    serial {
        compatible = "xxx";
        reg = <0x4600 0x5000 0x100>;  /*地址信息是：0x00004600 00005000,长度信息是：0x100*/
        };
};
```

## 9. `compatible`属性

驱动和设备（设备节点）的匹配依据，compatible（兼容性）的值可以有不止一个字符串以满足不同的需求，语法：

```c
compatible = "字符串1","字符串2",...;
```

compatible 属性也叫做 “兼容性” 属性，这是非常重要的一个属性！**compatible 属性的值是一个字符串列表**， compatible 属性用于将设备和驱动绑定起来。字符串列表用于选择设备所要使用的驱动程序。compatible 属性值的推荐格式：

```shell
"manufacturer,model"
#manufacturer : 表示厂商；
#model : 一般是模块对应的驱动名字

compatible = "fsl,mpc8641", "ns16550";
```

上面的compatible有两个属性，分别是` "fsl,mpc8641"` 和 `"ns16550"`；其中` "fsl,mpc8641"` 的厂商是` fsl`；设备首先会使用第一个属性值在 Linux 内核里面查找，看看能不能找到与之匹配的驱动文件；如果没找到，就使用第二个属性值查找，以此类推，直到查到到对应的驱动程序 或者 查找完整个 Linux 内核也没有对应的驱动程序为止。

## 10. `model `属性

model 属性值也是一个字符串，一般 model 属性描述设备模块信息，比如名字什么的，例如：

```text
model = "Samsung S3C2416 SoC";
```

## 11. `ranges`属性

ranges属性值可以为空，`ranges` 属性设置为空（`ranges;` 或 `ranges = <>;`）具有特殊含义：表示**子总线地址空间与父总线地址空间完全一致，无需地址转换**（即子地址直接等同于父地址）。

或者按照 (child-bus-address,parent-bus-address,length) 格式编写的数字矩阵， ranges 是一个地址映射/转换表， ranges 属性每个项目由子地址、父地址和地址空间长度这三部分组成：

- child-bus-address：子总线地址空间的物理地址，由父节点的 #address-cells 确定此物理地址所占用的字长。当前节点 `i2c@12340000` 所代表的总线（I2C 总线），其地址空间是 I2C 设备在该总线上的本地地址（如 I2C 设备地址 0x48）。
- parent-bus-address：父总线地址空间的物理地址，同样由父节点的 #address-cells 确定此物理地址所占用的字长。`i2c@12340000` 的父节点 `soc` 所代表的总线（AHB 总线），其地址空间是 CPU 可直接访问的物理地址（如 0x12340000）。
- length：子地址空间的长度，由父节点的 #size-cells 确定此地址长度所占用的字长。

```text
soc {
    compatible = "simple-bus";
    #address-cells = <1>; 
    #size-cells = <1>;
    ranges = <0x0 0xe0000000 0x00100000>; // 子→父地址映射表
    serial {
        device_type = "serial";
        compatible = "ns16550";
        reg = <0x4600 0x100>;
        clock-frequency = <0>;
        interrupts = <0xA 0x8>;
        interrupt-parent = <&ipic>;
        };
};
```

节点 `soc`定义的 ranges 属性，值为 <0x0 0xe0000000 0x00100000>，此属性值指定了一个 1024KB(0x00100000) 的地址范围，子地址空间的物理起始地址为 0x0，父地址空间的物理起始地址为 0xe0000000。

三个参数分别对应：

- `child-bus-address = 0x0`：`soc` 子总线的起始地址（子总线的本地地址起点）。
- `parent-bus-address = 0xe0000000`：映射到父总线（如 CPU 系统总线）的物理地址起点（CPU 可直接访问的地址）。
- `length = 0x00100000`：映射的地址空间大小（1MB，即子总线地址 `0x0~0xFFFFF` 对应父总线 `0xe0000000~0xe00FFFFF`）。

serial 是串口设备节点，

`reg` 属性定义了 serial 设备寄存器的起始地址为 0x4600，寄存器长度为 0x100。

经过地址转换， serial 设备可以从 0xe0004600 开始进行读写操作，0xe0004600=0x4600+0xe0000000。

## 12. `name`属性

name 属性值为字符串， name 属性用于记录节点名字， name 属性已经被弃用，不推荐使用name 属性，一些老的设备树文件可能会使用此属性。

## 13. `device_type`属性

device_type 属性值为字符串， IEEE 1275 会用到此属性，用于描述设备的 `FCode`，但是设备树没有 `FCod`e，所以此属性也被抛弃了。此属性只能用于` cpu`节点或者` memory `节点。

```text
memory@30000000 {
    device_type = "memory";
    reg =  <0x30000000 0x4000000>;
};
```

# 特殊节点

## 14. 根节点

根节点表示整块开发板的信息

```c
#address-cells   // 在子节点的reg属性中, 使用多少个u32整数来描述地址(address)
#size-cells      // 在子节点的reg属性中, 使用多少个u32整数来描述大小(size)
compatible       // 定义一系列的字符串, 用来指定内核中哪个machine_desc可以支持本设备，即描述其兼容哪些平台                         
model            // 比如有2款板子配置基本一致, 它们的compatible是一样的，那么就通过model来分辨这2款板子
```

## 15. /memory

所有设备树都需要一个memory设备节点，它描述了系统的物理内存布局。如果系统有多个内存块，可以创建多个memory节点，或者可以在单个memory节点的`reg`属性中指定这些地址范围和内存空间大小。例如：一个64位的系统有两块内存空间：RAM1：起始地址是0x0，地址空间是 0x80000000；RAM2：起始地址是0x10000000，地址空间也是0x80000000；同时根节点下的 #address-cells = <2>和#size-cells = <2>，这个memory节点描述为：

```text
memory@0 {
    device_type = "memory";
    reg = <0x00000000 0x00000000 0x00000000 0x80000000
           0x00000000 0x10000000 0x00000000 0x80000000>;
};

或者

memory@0 {
    device_type = "memory";
    reg = <0x00000000 0x00000000 0x00000000 0x80000000>;
};
memory@10000000 {
    device_type = "memory";
    reg = <0x00000000 0x10000000 0x00000000 0x80000000>;
};
```

## 16. /chosen

传递内核启动时使用的参数parameter

```text
bootargs  //字符串，内核启动参数, 跟u-boot中设置的bootargs作用一样
chosen {
    bootargs = "root=/dev/nfs rw nfsroot=192.168.1.1 console=ttyS0,115200";
};
```

## 17. /cpus  多核CPU支持

`/cpus`节点下有1个或多个`cpu`子节点, cpu子节点中用reg属性用来标明自己是哪一个cpu。所以 /cpus 中有以下2个属性:

```text
#address-cells   // 在它的子节点的reg属性中, 使用多少个u32整数来描述地址(address)
#size-cells      // 在它的子节点的reg属性中, 使用多少个u32整数来描述大小(size) 必须设置为0

cpus {
    #address-cells = <1>;
    #size-cells = <0>;
    cpu@0 {
        device_type = "cpu";
        reg = <0>;
        cache-unified;
        cache-size = <0x8000>; // L1, 32KB
        cache-block-size = <32>;
        timebase-frequency = <82500000>; // 82.5 MHz
        next-level-cache = <&L2_0>; // phandle to L2
        L2_0:l2-cache {
            compatible = "cache";
            cache-unified;
            cache-size = <0x40000>; // 256 KB
            cache-sets = <1024>;
            cache-block-size = <32>;
            cache-level = <2>;
            next-level-cache = <&L3>; // phandle to L3
            L3:l3-cache {
                compatible = "cache";
                cache-unified;
                cache-size = <0x40000>; // 256 KB
                cache-sets = <0x400>; // 1024
```

# 设备树文件目录位置

Linux 与 U-Boot 的设备树目录不同：

| 项目   | 目录（ARM）                                     | 定位                               |
| ------ | ----------------------------------------------- | ---------------------------------- |
| Linux  | `arch/arm/boot/dts/`（64 位 `arch/arm64/boot/dts/`） | 启动数据，与内核镜像同属 boot       |
| U-Boot | `arch/arm/dts/`（新版含 `dts/upstream/src/`）    | U-Boot 驱动模型自身使用             |

Linux 将设备树放在 `boot/` 下的原因：设备树本质是**启动时传给内核的硬件描述数据**，与内核镜像（`Image`/`zImage`）、启动参数同属“引导流程”，故归入 `arch/<架构>/boot/`，而非 `drivers/`、`kernel/`。编译产物 `.dtb` 在源码同目录生成，便于与镜像一起打包部署。

U-Boot 的设备树供其自身驱动模型（DM）使用，按功能直接放在 `arch/arm/dts/`，不设 `boot/` 层。

# GPIO 端口（bank）与引脚命名

## 1. 端口（bank）概念

芯片的成百上千个 GPIO 引脚按组管理，每组称为一个 **GPIO bank（端口/组）**。每个端口有独立名字，由芯片 datasheet 定义。以 Exynos4412 为例：

```txt
GPA0, GPA1, GPB, GPC0, GPC1, GPD0, GPD1, GPF0, ..., GPX0, GPX1, GPX2, GPX3
```

每个端口一般 8 个引脚（编号 0~7），部分 4 个或 16 个。

## 2. 引脚命名格式

```txt
"<端口名>-<引脚号>"
"gpa0-0"  = 端口 GPA0 的第 0 号引脚
"gpa0-1"  = 端口 GPA0 的第 1 号引脚
"gpx2-7"  = 端口 GPX2 的第 7 号引脚
```

端口名与每个引脚的复用功能，查 datasheet 的 GPIO 章节。

# pinctrl 引脚组属性解读

pinctrl 节点描述“某外设用哪些引脚、复用成什么功能”，是设备树中引脚配置的核心。不同 SoC 的 pinctrl 绑定不同，但思路一致。

## 1. 三星 Exynos 绑定

```dts
uart0_data: uart0-data {
    samsung,pins = "gpa0-0", "gpa0-1";   /* 用哪些引脚 */
    samsung,pin-function = <0x2>;         /* 复用功能号 */
    samsung,pin-pud = <0>;                /* 上拉/下拉 */
    samsung,pin-drv = <0>;                /* 驱动强度 */
};
```

| 属性                | 含义                                             |
| ------------------- | ------------------------------------------------ |
| `samsung,pins`      | 引脚列表：`<端口>-<引脚号>`                      |
| `samsung,pin-function` | 复用功能号（查 datasheet pin mux 表）         |
| `samsung,pin-pud`   | 上拉/下拉：`0` 无、`1` 下拉、`3` 上拉           |
| `samsung,pin-drv`   | 驱动强度：`0` 最低档（1x），越大越强            |

- 标签（如 `uart0_data`）是引用名，外设节点用 `pinctrl-0 = <&uart0_data>` 引用。
- 同一外设常拆多组，如 UART0：`uart0_data`（RXD/TXD 数据线）、`uart0_fctl`（CTSn/RTSn 流控线）。

## 2. Rockchip 绑定

```dts
uart0_xfer: uart0-xfer {
    rockchip,pins = <0 RK_PC2 16 &pcfg_pull_none>;
};
```

| 字段               | 含义                                      |
| ------------------ | ----------------------------------------- |
| `0`                | GPIO bank 编号                            |
| `RK_PC2`           | 引脚名                                    |
| `16`               | 复用功能号                                |
| `&pcfg_pull_none`  | 引脚配置（上下拉等），引用公共配置节点    |

# U-Boot 私有属性与 -u-boot.dtsi

## 1. 共享 vs 私有

|                 | 通用 dtsi              | `-u-boot.dtsi`          |
| --------------- | ---------------------- | ----------------------- |
| 内核用不用      | 用                     | 不用                    |
| U-Boot 用不用   | 用                     | 用                      |
| 存在于哪个项目  | 内核、U-Boot 都有      | 仅 U-Boot               |

- **通用 dtsi**（如 `rk3506.dtsi`、`rk3506-pinctrl.dtsi`）描述硬件事实（基址、引脚复用），内核与 U-Boot 各持一份拷贝，是**共享**的。
- **`-u-boot.dtsi`** 内容只有 U-Boot 需要，内核项目里不存在，是**私有**的。

“私有”指内容只属于 U-Boot，而非“只有 U-Boot 读整个设备树”——U-Boot 读所有 dtsi，但通用部分内核也在读，`-u-boot.dtsi` 部分仅 U-Boot 读。

## 2. 典型私有属性

```dts
&uart0 {
    u-boot,dm-pre-reloc;   /* 重定位前就要初始化，好打印 */
};

&sdmmc {
    u-boot,dm-pre-reloc;   /* SPL 阶段就要读 SD 卡 */
};
```

U-Boot 的驱动模型（DM）不会自动 probe 所有设备，早期（SPL、重定位前）内存/栈受限，只能初始化必需外设。`u-boot,dm-pre-reloc` 即标记“该设备重定位前必须初始化”。

| 属性                                       | 含义                          |
| ------------------------------------------ | ----------------------------- |
| `u-boot,dm-pre-reloc` / `bootph-pre-ram`   | 重定位前（SPL）初始化         |
| `bootph-some-ram`                          | 搬入 DDR 后、完整启动前初始化 |
| `bootph-all`                               | 所有阶段                      |
| `u-boot,dm-spl`                            | 仅 SPL 阶段                   |

## 3. 为何拆成独立文件

- 属性名带 `u-boot,` 前缀 → 内核解析时忽略，不污染内核那份 dts。
- 构建时 U-Boot 自动 include 同名 `-u-boot.dtsi`，生成 U-Boot 自己的 `.dtb`；内核编译不碰它。

# Rockchip 设备树文件与 RMIO

以 RK3506 为例，U-Boot 目录下的设备树文件分类：

```txt
rk3506.dtsi                ← SoC 主 dtsi（在 dts/upstream）
rk3506-pinctrl.dtsi        ← 标准引脚复用
rk3506-pinctrl-rmio.dtsi   ← RMIO 可重映射 IO（二级 pinmux）
rk3506-u-boot.dtsi         ← U-Boot 私有属性
        ↑ 以上为 SoC/公共层
rk3506-evb.dts             ← 板级（评估板）
rk3506-evb-tb.dts          ← 板级变体
```

| 文件                       | 层             | 说明                  |
| -------------------------- | -------------- | --------------------- |
| `-u-boot.dtsi`             | U-Boot 私有    | 构建时自动 include    |
| `-pinctrl.dtsi`            | SoC 引脚复用   | `pin2dts` 工具生成    |
| `-pinctrl-rmio.dtsi`       | SoC 二级 pinmux| `pin2dts` 工具生成    |
| `-evb.dts` / `-evb-tb.dts` | 板级           | 板厂手写              |

## 1. RMIO 概念

**RMIO（Rockchip Matrix I/O，矩阵 I/O）** 是 RK3506 引入的**二级 pinmux 控制器**。

- 普通 pinmux：一个引脚固定复用若干功能。
- RMIO：主 mux 把信号路由到 RMIO 矩阵，再由二级选择决定最终功能，**同一矩阵内任意功能可软件映射到任意引脚**，灵活度极高。

`rk3506-pinctrl-rmio.dtsi` 文件巨大（约 2.5 万行），本质是引脚功能组合的通用库，按 phandle 直接选用节点即可，无需查寄存器手册；文件中用 `/omit-if-no-ref/` 标记，未被引用的不编译进 DTB，不增加体积。

# 线程互斥总结

---

## 1. 加锁顺序与死锁避免

### 死锁产生条件

两个线程以不同顺序获取相同的多把锁，形成循环等待。

```cpp
// 错误示例：死锁
std::mutex mtxA, mtxB;

void thread1() {
    mtxA.lock();
    usleep(1000);           // 加大死锁概率的时间窗口
    mtxB.lock();            // thread1 先锁 A 再锁 B
    // 临界区 ...
    mtxB.unlock();
    mtxA.unlock();
}

void thread2() {
    mtxB.lock();
    usleep(1000);
    mtxA.lock();            // thread2 先锁 B 再锁 A → 死锁
    // 临界区 ...
    mtxA.unlock();
    mtxB.unlock();
}
```

### 解决方案：严格加锁顺序

**所有需要多把锁的地方，按固定顺序加锁。** 这是避免死锁最核心的规则。

```cpp
// 正确示例：统一加锁顺序（按地址比较是一种通用做法）
std::mutex mtxA, mtxB;

void safe_lock(std::mutex &a, std::mutex &b) {
    if (&a < &b) {
        a.lock();
        b.lock();
    } else if (&a > &b) {
        b.lock();
        a.lock();
    } else {
        a.lock();           // 同一把锁，只锁一次
    }
}

void thread_func(std::mutex &m1, std::mutex &m2) {
    safe_lock(m1, m2);
    // 临界区 ...
    m2.unlock();
    m1.unlock();
}
```

更好的方式是用 `std::lock` 或 `std::scoped_lock`（C++17），一次性锁多把，内部保证无死锁：

```cpp
std::mutex mtxA, mtxB;

void thread_func() {
    std::scoped_lock guard(mtxA, mtxB);  // C++17，自动推导顺序，异常安全
    // 临界区 ...
}   // 自动解锁
```

### 补充原则

| 原则 | 说明 |
|:----:|:----:|
| 避免嵌套锁 | 持有一把锁时尽量不再申请第二把，无法避免就用固定顺序 |
| 减小锁粒度 | 锁只保护必要的数据，耗时代码（IO、计算）移出临界区 |
| 使用 try_lock + 回退 | `try_lock()` 失败则释放已持锁，重试，但效率低，用于复杂场景 |

## 2. 槽位数组的锁粒度设计

### 场景

一个数组，每个元素是一个槽位。多个线程各自抢占一个槽位，在槽位上执行耗时操作。

### 设计思路：锁分离

**槽位竞争（抢占阶段）用一把锁，槽位内操作（耗时阶段）用每槽位一把锁。** 这样耗时操作不阻塞其他线程抢占空闲槽位。

```cpp
#include <mutex>
#include <vector>
#include <thread>
#include <atomic>

struct Slot {
    std::mutex        mtx;       // 保护本槽位
    std::atomic<bool> busy{false};
    int               data;

    bool try_occupy() {
        bool expected = false;
        return busy.compare_exchange_strong(expected, true);
    }
    void release() { busy = false; }
};

class SlotArray {
public:
    std::mutex              array_mtx;   // 仅保护槽位分配过程
    std::vector<Slot>       slots;

    SlotArray(size_t n) : slots(n) {}

    // 返回占用的槽位索引，-1 表示全部被占
    int occupy_slot() {
        std::lock_guard<std::mutex> guard(array_mtx);  // 短临界区，只做分配
        for (size_t i = 0; i < slots.size(); ++i) {
            if (slots[i].try_occupy()) {
                return i;
            }
        }
        return -1;
    }

    // 耗时操作——此时不持有 array_mtx，其他线程可以 allocate
    void do_work(int idx) {
        std::lock_guard<std::mutex> guard(slots[idx].mtx);  // 只锁本槽位
        // 耗时操作，其他线程不受影响 ...
        slots[idx].data = 42;
    }

    void release_slot(int idx) {
        // release 不需要锁 busy 本身是原子的
        slots[idx].release();
    }
};
```

### 锁粒度对比

| 方案 | 并发度 | 复杂度 | 适用场景 |
|------|--------|--------|----------|
| 整数组一把锁 | 差，一个槽忙整个数组不可用 | 低 | 操作极短，槽位数少 |
| 每槽一把锁 + 分配锁 | 好，耗时操作互不影响 | 中 | 槽位耗时操作，分配频繁 |
| 每槽一把锁无分配锁 | 易出现竞争条件 | 高 | 不推荐 |

### 要点

1. **分配阶段用轻量锁**（锁住数组、选槽位、标记占用、解锁——几微秒）。
2. **槽位内操作用自己的锁**，不阻塞其他线程的分配和操作。
3. **不要拿着槽位锁去锁数组**，反之亦然——回到第 1 节的死锁问题。

## 3. 将锁封装在类中（RAII + 锁与数据绑定）

### 核心思想

把 mutex 和受保护的数据放在同一个类里，所有访问数据的公开方法内部自动加锁解锁。**外部调用者看不到锁，就不会用错。**

```cpp
#include <mutex>
#include <queue>
#include <condition_variable>

// 线程安全的队列
template<typename T>
class ThreadSafeQueue {
    std::queue<T>           queue_;
    mutable std::mutex      mtx_;
    std::condition_variable cv_;
public:
    void push(T val) {
        std::lock_guard<std::mutex> guard(mtx_);
        queue_.push(std::move(val));
        cv_.notify_one();
    }

    T pop() {
        std::unique_lock<std::mutex> lock(mtx_);
        cv_.wait(lock, [this]{ return !queue_.empty(); });
        T val = std::move(queue_.front());
        queue_.pop();
        return val;
    }

    bool try_pop(T &val) {
        std::lock_guard<std::mutex> guard(mtx_);
        if (queue_.empty()) return false;
        val = std::move(queue_.front());
        queue_.pop();
        return true;
    }

    bool empty() const {
        std::lock_guard<std::mutex> guard(mtx_);
        return queue_.empty();
    }
};
```

### RAII 锁守卫一览

```cpp
std::mutex mtx;

// C++11：基础守卫，不可移动，不可拷贝
void f() {
    std::lock_guard<std::mutex> guard(mtx);   // 构造加锁，析构解锁
    // ...
}

// C++11：可移动，可手动 unlock/lock，配合 condition_variable 必须用它
void g() {
    std::unique_lock<std::mutex> lock(mtx);
    lock.unlock();   // 需要时可以提前释放
    // ... 无锁操作 ...
    lock.lock();
}

// C++17：可变参数模板，可同时锁多把 mutex
void h() {
    std::scoped_lock guard(mtx1, mtx2, mtx3);  // 无死锁，析构全部解锁
}
```

### 封装原则

| 做法 | 理由 |
|------|------|
| mutex 声明为 `mutable` | 使 const 方法也能加锁（如 `empty()`） |
| 不要返回内部数据的指针或引用 | 锁只在函数作用域内有效，走出函数锁已释放，外部拿到引用可无锁访问 |
| 避免在持有锁时调用外部回调 | 回调中可能再次申请同一把锁 → 死锁；或长时间占用锁降低并发 |
| 不要将锁暴露为 public | 对外只提供动作（push/pop），不提供锁本身 |

### 反例：不要这样做

```cpp
// 反模式：锁暴露在外
class BadCounter {
public:
    std::mutex mtx;    // public——调用者忘加锁就出错
    int        count;
};

void increment(BadCounter &c) {
    // 调用者自己加锁——容易忘，容易死锁
    c.mtx.lock();
    c.count++;
    c.mtx.unlock();    // 如果中间异常，锁永不释放
}

// 正确做法
class GoodCounter {
    std::mutex mtx_;
    int count_ = 0;
public:
    void increment() {
        std::lock_guard<std::mutex> guard(mtx_);
        count_++;
    }
    int get() const {
        std::lock_guard<std::mutex> guard(mtx_);
        return count_;
    }
};
```

### 总结

1. **加锁顺序固定**：多把锁时用 `std::lock` / `std::scoped_lock` 或统一顺序，杜绝循环等待。
2. **锁粒度恰当**：槽位数组场景，分配锁与槽内锁分离，耗时操作不阻塞他人。
3. **锁封装在数据类中**：mutex 不暴露，锁守卫 RAII 自动管理生命周期，调用者无法用错。

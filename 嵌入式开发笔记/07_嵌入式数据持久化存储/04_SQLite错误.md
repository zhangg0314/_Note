# `DataBase Is Locked`

# 1.多并发

​	在使用 `sqlite3` 命令行执行数据库操作时，有时会遇到 “database is locked” 的错误提示。这种错误通常是由于多个进程或线程同时访问数据库而引起的。当一个进程或线程正在修改(写入)数据库时，`SQLite`会对数据库进行独占锁定，禁止其他进程或线程对该数据库进行写操作，从而保证数据的完整性。

​	然而，如果其他进程或线程也要进行写操作，并同时请求对数据库对象进行锁定，那么就会出现“database is locked”的错误提示。这是因为 `SQLite `在默认情况下只允许一个进程或线程进行写操作。

------

# 2.可能原因

　　`SQLite`只支持库级锁，库级锁意味着什么？——意味着同时只能允许一个写操作，也就是说，即事务`T1`在A表插入一条数据，事务`T2`在B表中插入一条数据，这两个操作不能同时进行，即使机器有100个CPU，也无法同时进行，而只能顺序进行。表级都不能并行，更别说元组级了——这就是库级锁。但是，`SQLite`尽量延迟申请X锁，直到数据块真正写盘时才申请X锁，这是非常巧妙而有效的。

1. **事务未提交 / 回滚**
   如果开启了一个事务（如 `BEGIN TRANSACTION`），但没有执行 `COMMIT` 或 `ROLLBACK`，数据库会一直保持锁定状态。
2. **多个连接同时写操作**
   `SQLite` 等数据库在写入时会锁定整个数据库文件，若多个连接同时尝试写操作，会导致锁定冲突。
3. **长时间运行的查询**
   复杂查询或长时间运行的操作会占用锁资源，阻止其他操作。

------

# 3.解决方法

要解决“database is locked”错误，我们可以采取以下方法。

## 1.关闭其他打开的数据库连接或事务

在使用`sqlite3`命令行时，务必确保已经关闭了其他正在使用同一个数据库的连接或事务。可以通过检查是否有其他 `sqlite3 `进程运行并关闭它们，或者等待其他进程或线程完成对数据库的操作后再执行操作。

## 2.延迟等待

在执行数据库操作时，我们可以使用 `PRAGMA busy_timeout = milliseconds;` 语句来设置` SQLite` 的忙等待时间。该语句设置了等待其他进程或线程释放数据库锁的时间，单位为毫秒。如果在指定的时间内锁定依然无法释放，则会继续报错。通过设置一个较长的等待时间，可以增加数据库锁定的等待时间，从而减少“database is locked”错误的发生。

例如，我们可以执行以下语句，将等待时间设置为5秒：

```sql
sqlite> PRAGMA busy_timeout = 5000;
```

## 3.使用 `WAL` 模式

`WAL`（Write Ahead Logging）模式是一种` SQLite` 数据库的日志模式，可以提高数据库的并发写入性能。在 WAL 模式下，写入操作将被追加到一个名为 WAL 的日志文件中，而不是直接写入数据库文件。这样，其他读取操作就可以并发进行，不再需要等待写操作的完成。要启用` WAL `模式，我们可以在连接到数据库之后，执行以下语句：

```sql
sqlite> PRAGMA journal_mode = WAL;
```

## 4.使用连接池

使用连接池可以避免多个线程或进程同时访问数据库的问题。连接池会维护一组数据库连接，并且只有当需要时才会创建新的连接。在数据库操作完成后，连接会被归还至连接池，以供其他线程或进程使用。

心在于**SQLite 的锁机制在不同日志模式下的行为差异**，以及 “并发” 的具体场景（是 “读写并发” 还是 “写写并发”）。我们需要分两种日志模式来拆解：

# 4.不同日志模式比较

## 1. 传统日志模式（默认的 DELETE 模式）

“锁定整个数据库”，导致**读写、写写都冲突**，在` SQLite `默认的日志模式（`PRAGMA journal_mode=DELETE`）下，数据库的锁机制是 “全量锁定”：

- **读操作**需要获取**共享锁（SHARED LOCK）**，此时所有读操作可以并行，但会阻塞写操作。
- **写操作**需要获取**排他锁（EXCLUSIVE LOCK）**，此时会阻塞所有其他读 / 写操作（包括其他连接的读），直到写操作完成并释放锁。

这种模式下，**任何写操作都会 “锁定整个数据库文件”**，导致：

- 多个连接同时写：必然冲突（因为排他锁只能被一个连接持有）。
- 一个连接写，其他连接读：也会冲突（读的共享锁会被写的排他锁阻塞）。

这就是 “写入时锁定整个数据库文件，多个连接同时写会冲突” 的场景。

## 2.` WAL` 模式（Write-Ahead Logging）

打破 “读写互斥”，但 “写写仍互斥“。当启用` WAL `模式（`PRAGMA journal_mode=WAL`）后，`SQLite` 的锁机制发生了根本变化：

- **写操作**不再直接修改主数据库文件，而是先写入一个独立的 “`WAL` 日志文件”，此时只需要获取**`WAL` 文件的排他锁**（而非整个数据库的排他锁）。
- **读操作**直接从主数据库文件读取（主数据库在 `WAL` 模式下不会被写操作直接修改），不需要等待写操作完成，因此读操作可以和写操作并行。

但注意：**多个写操作之间仍然互斥**。因为写操作需要向` WAL `文件写入，而 `WAL `文件的写入必须串行（同一时间只能有一个连接写 `WAL`），否则会导致日志混乱。

## 3.关键结论

- 前面说的 “写入时锁定整个数据库，导致多连接写冲突”，**默认指的是传统日志模式**，或 “多个写操作之间的冲突”（无论哪种模式，写写都互斥）。
- 后面说的 “多线程独立连接配合` WAL` 提升并发”，**指的是 “读写并发”**（`WAL` 模式下读和写可以同时进行），但 “写写并发” 仍然会冲突（这一点从未否认）。

两者的适用场景不同，因此并不矛盾：

| 场景       | 传统模式（DELETE） | `WAL` 模式                 |
| ---------- | ------------------ | -------------------------- |
| 读操作之间 | 可并发（共享锁）   | 可并发                     |
| 读与写之间 | 不可并发（互斥）   | 可并发（读主库，写 `WAL`） |
| 写操作之间 | 不可并发（互斥）   | 不可并发（互斥）           |

## 4.例子理解

- 传统模式：就像一个房间，读的人可以一起进（共享），但只要有人在写（修改房间），所有人都必须出去，写完才能再进。
- `WAL `模式：房间本身不允许直接修改，写的人只能在旁边的笔记本（`WAL`）上记录修改，读的人继续在房间里看（主库），互不干扰。但笔记本一次只能一个人写（写写互斥）。

因此，`WAL `模式解决的是 “读写冲突”，但没有解决 “写写冲突”。

# 5.方案总结

## 1.一个进程读同时一个进程写

开启`WAL`模式，解决读写互斥

## 2.同一进程内多个线程同时写

自定义定义全局互斥锁`std::mutex db_mutex`，在读写操作时加入锁。

## 3.同一连接被共享,消除线程间的状态干扰

 **“独立连接解决的是线程安全问题，而非` SQLite `本身的写写互斥限制”**。

大多数数据库连接对象（包括 `SQLite` 的`sqlite3`连接）**不是线程安全的**。如果多个线程共享同一个连接对象，并同时调用其方法（如执行 `SQL`），会导致：

- 内部状态混乱（比如一个线程正在执行查询，另一个线程突然中断并执行插入，可能导致数据错乱或崩溃）。
- 即使没有锁定冲突，也可能出现不可预期的错误（如结果集混乱、事务异常）。

因此，“为每个线程分配独立连接” 的首要目的是：**避免多个线程共享非线程安全的连接对象，确保每个线程的操作在独立的连接中执行，从根本上消除线程间的状态干扰**。

- “多个连接同时写会导致锁定冲突”：这是` SQLite` 的**固有锁机制**决定的（写写必须串行），与连接是否独立无关。
- “为每个线程分配独立连接”：这是解决**线程安全问题**的手段（避免共享连接导致的状态混乱），不能消除 `SQLite` 的写写互斥，但能为 “优雅处理冲突”（如重试）提供基础。

两者指向的问题不同，因此并不矛盾。若要彻底避免 `SQLite` 的写写冲突，唯一的办法是**让所有写操作串行化**（如通过全局队列统一调度写请求），而独立连接只是确保这个串行化过程中不会出现线程安全问题。

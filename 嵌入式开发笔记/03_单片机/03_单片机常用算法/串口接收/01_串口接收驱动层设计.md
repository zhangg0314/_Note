

# 1.术语解释

| 术语 | 准确含义 |
|---|---|
| **字节时间** | 一个字符在线上占用的时间：`t_byte = 每帧位数 / 波特率`。115200 8N1 约 86.8µs；1Mbps 8N1 约 10µs。 |
| **阻塞** | 裸机：调用者停在原地等，后面的代码不执行。<br />RTOS：任务进入 Blocked 状态，CPU 可以跑别的任务。<br />中断：ISR 里忙等/死等，会挡住所有更低优先级中断。 |
| **CPU 空转 / 忙等** | CPU 没有进低功耗，而是在循环里反复读标志位，做无用功 |
| **漏字节** | UART 侧：RDR/FIFO 满，新字节完成 → ORE，硬件丢字节。<br />DMA 侧：通道没重装 / NDTR=0 / 回绕覆盖。<br />软件侧：环形/队列满后按策略丢新/丢旧，或消费者还在读时被生产者覆盖。 |
| **中断延迟** | 中断标志置位到 ISR 第一条指令执行的时间，包含硬件响应、优先级抢占、关中断临界区。 |
| **服务时间** | 从字节到达到被读走/搬走的时间。它必须小于字节时间（或 FIFO 深度 × 字节时间），否则 ORE。 |

# 2.驱动层职责

驱动层只做四件事：**搬运、缓冲、组帧、交帧**。也就是从 UART 寄存器 / FIFO / DMA / 中断，到向上层交付一帧或一段字节为止。
而CRC 校验、序号、ACK、重传、业务字段解析都不算驱动层；但有时候驱动为了算帧总长，通常需要知道 CRC / 尾字节占几个字节。

# 3.驱动层分层

```text
UART 硬件
   │
   ▼
① 搬运层：字节怎么从硬件进内存
   │        轮询 / 中断 / DMA
   ▼
② 缓冲层：字节放在哪
   │        单缓冲 / 环形 / 双缓冲 / 帧队列
   ▼
③ 组帧层：怎么知道一帧多少字节
   │        定长 / 长度字段 / 分隔符 / 空闲 / 超时 / 转义
   ▼
④ 交帧层：怎么把完整帧给上层
   │        回调 / 队列 / 阻塞读 / 零拷贝
   ▼
上层
```

| 名词 | 属于哪一级 |
|---|---|
| 轮询、RXNE 中断、DMA、DMA Circular | ① 搬运层 |
| 环形缓冲区、双缓冲区、帧队列 | ② 缓冲层 |
| 定长 / 不定长、长度字段、分隔符、空闲中断、超时中断、COBS / SLIP | ③ 组帧层 |
| 回调、队列、阻塞读、零拷贝 | ④ 交帧层 |
| 粘包、半包 | ③ 组帧层要处理的现象 |
| 丢包、ORE | ① 搬运层 + ② 缓冲层 |

- **定长 / 不定长不是两种接收方式**，只是组帧层帧长从哪来的两种答案。
- **环形 / 双缓冲不解决粘包**，只管存放和交接。
- **空闲 / 超时不是搬运方式**，是组帧层的边界信号。

# 4.常用组合

```text
“DMA + 空闲中断 + 环形缓冲区接收不定长”
= ① DMA
+ ③ 空闲中断（长度字段 / 超时兜底 判断一阵）
+ ② 环形缓冲区
```

```text
“中断 + 双缓冲 + 定长接收”
= ① 中断
+ ② 双缓冲
+ ③ 定长
```

# 5.字节搬运层

只解决字节到了怎么搬走，但这一级只有这 4 个选项。`IDLE` 不在这里，它是第 ③ 级。

## 1.方法介绍

| 方式 | 工作 | 适用                 | 缺点 |
|---|---|---|---|
| 轮询 | 主循环读 DR | 低速、单任务、调试口 | 阻塞、易丢 |
| 中断 | 每字节进 ISR，读 DR 存缓冲 | 低中速、数据量小 | 高波特率中断太频繁 |
| DMA Normal | DMA 收固定 N 字节，TC 中断 | 帧间有空闲的一问一答且定长或长度可预测 | 每帧重装，重装间隙丢字节；不定长时 TC 不代表帧尾 |
| DMA Circular | DMA 永远在收，HT / TC / IDLE 通知 | 高速、连续流、变长 | 帧会跨段，必须配组帧层 |

## 2.方法演进链

```text
轮询
  │ 不足：调用者卡在 while(RXNE) 里忙等；离开去干别的，UART 继续收，RDR/FIFO 满就 ORE
  ▼
中断
  │ 不足：每字节一次 ISR；ISR 执行 + 关中断 + 被高优先级抢占的时间 > 字节时间就 ORE ； 频繁中断CPU负载高
  ▼
DMA Normal
  │ 不足：NDTR=0 后 DMA 通道停；从 TC 到重装完成，UART 仍在收，RDR/FIFO 满就 ORE
  ▼
DMA Circular
  │ 不足：只给 HT/TC/IDLE/NDTR（Number of Data to Transfer Register） 位置，不给帧边界；帧跨段、回绕覆盖、NDTR 竞争
  ▼
（进入组帧层）
```

| 方法 | 它改进的是 | 上一个方法的不足（具体机制） | 它自己带来的新问题 |
|---|---|---|---|
| 轮询 | — | — | 调用者占用 CPU 忙等；离开轮询去干别的，RDR/FIFO 满后 ORE；功耗高 |
| 中断 | 轮询 | 轮询时调用者不能干别的；离开轮询又会漏字节 | 每字节一次中断，CPU 花在 ISR 上的时间随波特率线性上升；ISR 或关中断超过字节时间就 ORE |
| DMA Normal | 中断 | 中断频率高，CPU 被 ISR 切碎；ISR 长了直接 ORE | TC 后 DMA 通道停，重装间隙内 UART 继续收，RDR/FIFO 满就 ORE；N 固定，帧长变化时 TC 不对应帧边界 |
| DMA Circular | DMA Normal | 重装间隙；背靠背帧（连续发送具有**最小合法帧间隔**的N个数据帧）在间隙里被 ORE 丢掉 | 只有位置/块事件，没有帧边界；帧跨段、DMA 回绕覆盖、NDTR 读取竞争 |

注意：**DMA Normal 没有被淘汰**。定长、一问一答仍然常用；Circular 主要解决连续流和重装间隙。

## 3.DMA Normal

### 1.特点特性

DMA Normal 适合的不是定长，而是帧与帧之间有足够长的空闲/换向时间。而**一问一答**刚好天然提供了这个空闲：

```text
主站发请求 → 等从站响应 → 从站发一帧 → 主站处理 → 再发下一次请求
                                      │
                                      └─ 这段空闲通常是 ms 级
DMA TC → 软件重装只需要 µs 级
```

所以重装间隙被藏在主站处理/等待下一次请求的空闲里，不会撞上下一帧。

### 2.不定长帧

一问一答但响应不定长，还一样能使用DMA Normal，但不能靠 TC 单独判断帧结束。这个分四种情况：

#### 1.响应长度可预测

比如 Modbus：请求里写了读几个寄存器，主站能算出响应应该多少字节。

```c
N = 3 + 2 * reg_count + 2;   /* addr + func + bytecount + data + crc */
HAL_UART_Receive_DMA(&huart, buf, N);
```

- TC 触发 = 这一帧收完。
- 异常响应（5 字节）要单独处理。
- 这是最舒服的 DMA Normal 用法。

#### 2.响应长度不可预测

```c
//N 设为最大帧长 + IDLE/超时
HAL_UART_Receive_DMA(&huart, buf, MAX_FRAME);
```

- 帧短于 `MAX_FRAME` 时，TC 不会触发。
- 靠 IDLE 或接收超时判断这一帧结束了。
- 实际长度：

  ```c
  received = MAX_FRAME - __HAL_DMA_GET_COUNTER(hdma);
  ```

- 然后在空闲期 `abort + rearm`。
- 这时 TC 只当溢出保护
  收到 `MAX_FRAME` 还没结束，说明超长/异常。

这其实就是 **DMA Normal + IDLE**，不是纯 Normal。

#### 3.两段式 DMA

```text
先收头，解析长度，再收体
DMA 收固定头 → 解析 LEN → 重新装 DMA 收剩余字节

### 2.DMA Normal + IDLE 的坑

- IDLE 时  实际长度 = MAX - NDTR。
- 必须 abort DMA 再 rearm；rearm 期间来的字节会 ORE。
- 只适合低速 / 请求-应答；背靠背帧会丢。
- 高速优先 Circular。
```

- 适合
  帧头固定、长度字段位置固定。
- 问题
  **头收完到体重装之间有一个帧内间隙**。
- 低波特率（9600，1 字节约 1ms）没问题；1Mbps（1 字节约 10µs）就很危险。
- 只有发送方在头体之间有停顿，或 FIFO 够深，才稳。
- 否则老老实实 DMA Circular + framer。

#### 4. DMA Circular + 组帧层

- 不定长、背靠背、高速，最稳。
- TC/HT/IDLE 只给位置，帧边界由长度字段/分隔符/超时决定。
- 没有重装间隙，不存在一问一答才安全的限制。

### 3.DMA Normal丢的情况

不是“不定长”导致丢，而是**帧间没有足够空闲**：

- 从站响应完，主站立刻发下一次请求，间隙只有几个 µs。
- 多个响应背靠背发送，没有等待。
- 连续流传感器，根本不存在“问答间隙”。
- 两段式 DMA 的头体间隙 > 硬件能兜的时间。
- IDLE 后 `abort + rearm` 太慢，下一帧已经开始。

### 4.结论

| 说法 | 对不对 |
|---|---|
| DMA Normal 适合定长 | 不准确。它适合的是**帧间有空闲/换向时间**。 |
| 一问一答适合 DMA Normal | 对，因为问答之间通常有 ms 级空闲，重装间隙被藏起来了。 |
| 一问一答但不定长就不能用 DMA Normal | 不对。可以用 `N=max + IDLE/超时`，或先头后体，或长度可预测时直接算 N。 |
| 不定长且背靠背 | 不要用纯 DMA Normal，用 DMA Circular + framer。 |

DMA Normal 怕的不是长度不定，是下一帧来得太快，没时间重装。一问一答给了这个时间；

不定长只是决定用 TC 还是用 IDLE/超时/长度字段来结束这一帧。

## 4.DMA Circular + IDLE

```c
pos = RX_BUF_SIZE - __HAL_DMA_GET_COUNTER(hdma);
if (pos >= last_pos)
    len = pos - last_pos;
else
    len = RX_BUF_SIZE - last_pos + pos;

last_pos = pos;
```

- `pos == last_pos` 可能是空，也可能是刚好绕一圈；要靠是否有新数据判断。
- 读 `NDTR` 与 DMA 回绕有竞争
  读两次确认、或关通道、或依赖 HT / TC / IDLE 快照。
- DMA 一圈内必须被消费完，否则旧数据被覆盖。
- IDLE 只说明发送方停了 1 个字符时间，**不是帧边界**。
- 连续流不触发 IDLE，要靠 HT / TC + 组帧层。

# 6.字节缓冲层

只解决字节放哪、怎么解耦。缓冲大小按最坏突发算：B ≥ 速率 × (最大阻塞时间 + 最大处理时间) + 最大帧长

## 1.方法介绍

| 方式 | 作用 | 适用 |
|---|---|---|
| 单缓冲 | 一个数组 | 轮询、极简项目 |
| 环形缓冲 | 字节流解耦，ISR 写、任务读 | 绝大多数裸机项目 |
| 双缓冲 / 乒乓 | 一块收、一块处理，零拷贝 | 高速、处理时间 > 帧间隔 |
| 帧队列 | 完整帧排队 | 帧驱动、RTOS、多任务 |

## 2.方法演进链

```text
单缓冲
  │ 不足：ISR 写、主循环读同一块；主循环处理慢时 ISR 直接覆盖未读数据；读写无同步
  ▼
环形缓冲
  │ 不足：只解耦字节流；消费者慢于生产者时环满，按策略丢新/丢旧；没有帧边界；大帧仍要拷贝
  ▼
双缓冲 / 乒乓
  │ 不足：只有两块；处理一块的时间 > 生产一块的时间时没有空闲块，只能丢/等；切换要原子、所有权要管
  ▼
帧队列
  │ 不足：队列满时生产者 ISR 不能阻塞，只能丢；有拷贝/内存管理开销；动态分配可能失败
  ▼
帧池 / 零拷贝
```

| 方法 | 它改进的是 | 上一个方法的不足（具体机制） | 它自己带来的新问题 |
|---|---|---|---|
| 单缓冲 | — | — | ISR 和主循环无同步；处理慢时 ISR 覆盖未读数据；读到一半被改写会撕裂 |
| 环形缓冲 | 单缓冲 | 主循环处理慢时，ISR 继续写会覆盖主循环还没读的数据 | 只解决字节流；生产快于消费时环满，丢新/丢旧；<br />满/空判断和索引并发；<br />大帧仍要拷贝 |
| 双缓冲 / 乒乓 | 环形缓冲（针对帧块） | 环形里消费者处理大帧时，生产者可能绕圈覆盖还没处理的数据 | 只有两块；消费者处理一块的时间超过生产一块的时间时，没有空闲块；切换要原子；所有权要管 |
| 帧队列 | 双缓冲 | 只能两块，不能排多帧/多任务；消费者一慢就没块可用 | 队列满时 ISR 不能阻塞，只能丢；有拷贝/内存开销；动态分配可能失败 |
| 帧池 / 零拷贝 | 帧队列 | 大帧 memcpy 开销；队列拷贝延迟 | 所有权/释放/生命周期；池耗尽时只能丢；cache 一致性 |

注意：**环形和双缓冲不是严格替代**。环形面向字节流，双缓冲面向帧块交接；实际项目常组合使用。

## 3.帧队列具体实现

### 1.基本结构

帧队列不是字节环形缓冲的别名：它的元素是一帧，不是一个字节。帧队列通常也用环形数组实现，所以帧队列和环形不是对立的。

```text
字节环形缓冲：  [b0][b1][b2][b3]...        元素是 byte
帧队列：        [帧0][帧1][帧2]...          元素是 {data, len, status}
```

### 2.拷贝式帧队列

每个槽自带一块帧缓冲；生产者把整帧 `memcpy` 进槽，消费者取槽。

```c
#define FQ_DEPTH   8
#define FRAME_MAX  256

typedef struct {
    uint16_t len;
    uint16_t status;
    uint32_t tick;
    uint8_t  data[FRAME_MAX];
} frame_slot_t;

typedef struct {
    frame_slot_t slot[FQ_DEPTH];
    volatile uint16_t head;   /* 生产者写 */
    volatile uint16_t tail;   /* 消费者写 */
    volatile uint32_t drop;
} frame_queue_t;

/* 生产者：ISR / framer */
bool fq_push(frame_queue_t *q, const uint8_t *data, uint16_t len, uint16_t status)
{
    uint16_t next = (uint16_t)((q->head + 1u) % FQ_DEPTH);
    if (next == q->tail) {          /* 队列满了，即队列存的帧数满了 */
        q->drop++;
        return false;
    }
    frame_slot_t *s = &q->slot[q->head];
    s->len = len;
    s->status = status;
    s->tick = get_tick();
    memcpy(s->data, data, len);
    __DMB();                        /* 先写数据，再发布 head */
    q->head = next;
    return true;
}

/* 消费者：任务 */
frame_slot_t *fq_pop(frame_queue_t *q)
{
    if (q->tail == q->head) return NULL;   /* 空 */
    return &q->slot[q->tail];
}

void fq_release(frame_queue_t *q)
{
    q->tail = (uint16_t)((q->tail + 1u) % FQ_DEPTH);
}
```

- 简单、生命周期清晰，消费者拿着槽多久都行。
- 多一次 `memcpy`。
- 容量是 `FQ_DEPTH - 1`，因为要留一个空槽区分满/空。
- 队列满时 ISR 不能阻塞，只能丢新并计数。

### 3.直接组装式帧队列

不先写到临时帧缓冲再拷贝，而是 **framer 直接往 `slot[head]` 里写**，写完提交。

```c
frame_slot_t *fq_begin(frame_queue_t *q)
{
    uint16_t next = (uint16_t)((q->head + 1u) % FQ_DEPTH);
    if (next == q->tail) {      /* 满 */
        q->drop++;
        return NULL;
    }
    frame_slot_t *s = &q->slot[q->head];
    s->len = 0;
    return s;                   /* 直接在这个槽里组帧 */
}

void fq_commit(frame_queue_t *q, uint16_t len, uint16_t status)
{
    frame_slot_t *s = &q->slot[q->head];
    s->len = len;
    s->status = status;
    s->tick = get_tick();
    __DMB();
    q->head = (uint16_t)((q->head + 1u) % FQ_DEPTH);
    /* 唤醒消费者：xSemaphoreGiveFromISR / vTaskNotifyGiveFromISR */
}
```

framer 的用法：**帧开始时取一次槽，帧结束时提交**，不要每字节都 `fq_begin()`。

```c
/* 帧开始：取一次槽 */
frame_slot_t *cur = fq_begin(&fq);
if (cur == NULL) {
    /* 队列满：丢弃这一帧，计数，重同步 */
}

/* 每收到一个字节 */
if (cur != NULL) {
    cur->data[cur->len++] = byte;   /* 直接写槽 */
}

/* 帧结束：提交 */
if (cur != NULL && frame_complete) {
    fq_commit(&fq, cur->len, OK);
    cur = NULL;
}
/* 帧被中止：不要提交，直接 cur = NULL，槽会被下一帧复用 */
```

- 少一次拷贝，槽本身就是组帧缓冲。
- 生产者只在 `head` 槽写，消费者只在 `tail` 槽读，天然分离。
- 队列满时直接丢当前帧。
- 这是 MCU 上最常用、最平衡的做法。

### 3.零拷贝帧队列

缓冲池 + 描述符队列，队列里只放描述符 `{ptr, len}`，真正的帧数据在缓冲池里。

```c
typedef struct {
    uint8_t *data;
    uint16_t len;
    uint16_t status;
} frame_desc_t;//描述帧长度和数据存放buffer
frame_desc_t ready_q[FQ_DEPTH];   /* 描述符环 */
volatile uint16_t head, tail; //帧槽位
```

流程：

```text
生产者：从 free 池取一块 buf
        → framer 把帧写进 buf
        → 把 {buf, len} 描述符压入 ready 队列
消费者：从 ready 队列取描述符
        → 处理 buf
        → 把 buf 还给 free 池
```

- 大帧不拷贝，吞吐高。
- 必须严格管理**所有权**
  消费者没归还前，生产者不能复用这块 buf。
- 需要 free 队列 + ready 队列，两个都是 SPSC 环形队列。
- DMA 直接写 buf 时还要处理 cache clean / invalidate。

### 3.4 直接组装式 vs 零拷贝式：生命周期差异

一句话：

```text
直接组装：槽的寿命由队列位置决定，tail 一过，队列就不再保护它。
零拷贝：buffer 的寿命由 free 环决定，消费者不归还，生产者就拿不到。
```

#### 直接组装：出队 = 交还槽

直接组装的槽是队列里的固定数组。消费者通常分两步：

```c
frame_slot_t *f = fq_pop(&q);   /* 拿指针，tail 不动 */
fq_release(&q);                 /* tail 前进，槽交还队列 */
```

一旦 `fq_release()` 让 `tail` 前进，队列就不再认为这个槽被占用。看时间线（4 个槽，容量 3）：

```text
初始: head=0 tail=0

生产者: A -> slot[0], head=1
生产者: B -> slot[1], head=2
生产者: C -> slot[2], head=3

消费者: fq_pop() 拿到 A
消费者: fq_release(), tail=1
        // 队列认为 slot[0] 空闲；消费者手里还留着 &slot[0]

生产者: D -> slot[3], head=0   // 环满

消费者: fq_pop() 拿到 B
消费者: fq_release(), tail=2

生产者: E -> slot[0], head=1   // A 被覆盖
```

注意：A 不是 `fq_release()` 完立刻被覆盖，而是“迟早”被覆盖：

- `tail` 一过 `slot[0]`，队列就不再保护它。
- 生产者继续发新帧，`head` 绕一圈就回到 `slot[0]`。
- 中间可能隔着几帧，但没有所有权保证。
- 正确性不能依赖“应该还没那么快”。

所以直接组装有两条安全路径：

**路径一：处理完再 release**

```c
frame_slot_t *f = fq_pop(&q);
process(f);
fq_release(&q);
```

安全，但 FIFO 被卡住：消费者不 release，后面的帧也出不来；生产者很快填满队列，然后丢帧。

**路径二：先拷贝走，再 release**

```c
frame_slot_t *f = fq_pop(&q);
memcpy(my_buf, f->data, f->len);
fq_release(&q);
process(my_buf);
```

安全，但多一次拷贝。

#### 零拷贝：pop = 拿走 buffer 所有权

零拷贝里，队列只放指针/描述符：

```text
free 环:  [buf0][buf1][buf2][buf3]
ready 环: [ ]
```

时间线：

```text
生产者: 从 free 取 buf0，填数据，ready.push(buf0)
        free: [1,2,3]

消费者: ready.pop() -> buf0
        // buf0 归消费者；free 里没有 0，生产者拿不到

生产者: 从 free 取 1、2，继续提交
生产者: 想取 0 -> free 里没有，取不到

消费者: 处理完 buf0
        free.push(0)
        // 生产者现在才能重新拿到 0
```

关键：

- `ready.pop()` 只把描述符从队列拿出来，buffer 没回 free。
- 生产者只能从 free 拿 buffer；消费者没归还，生产者永远碰不到。
- 消费者可以持有到主动 `free.push()`。
- 代价：池是有限的，持有太多，生产者拿不到 buffer，只能丢帧或反压。

#### 对比

| 问题 | 直接组装式 | 零拷贝 |
|---|---|---|
| 出队/释放后指针还能长期用吗 | 不能 | 能，直到归还 |
| 谁决定槽/buffer 何时复用 | 生产者按环回绕 | 消费者 push free |
| 出队语义 | `fq_release` = 交还槽 | `pop` = 拿走 buffer 所有权 |
| 消费者长期处理 | 卡住 FIFO，或必须先拷贝 | 可以持有，池会变小 |
| 同时持有多个帧 | 困难，FIFO 会堵 | 可以，受池大小限制 |
| 忘记释放 | 无此问题 | 泄漏 / 池耗尽 |
| 覆盖风险 | 有 | 无（只要不提前 free） |
| 实现复杂度 | 低 | 高 |

#### 代码对比

直接组装：`release` 后不能留指针。

```c
frame_slot_t *f = fq_pop(&q);
fq_release(&q);          /* tail 前进，槽交还队列 */
process(f);              /* 危险：生产者绕回来会覆盖 */
```

安全写法一：

```c
frame_slot_t *f = fq_pop(&q);
process(f);
fq_release(&q);
```

安全写法二：

```c
frame_slot_t *f = fq_pop(&q);
memcpy(my_buf, f->data, f->len);
fq_release(&q);
process(my_buf);
```

零拷贝：`pop` 后可以留，最后 free。

```c
frame_buf_t *b = ring_pop(&ready_ring);

process(b->data, b->len);   /* 想处理多久都行 */

ring_push(&free_ring, b);   /* 主动归还 */
```

一句话总结：

```text
直接组装：
  release = 把槽交还给队列
  槽的寿命由 head 绕圈决定
  想长期留数据 → 处理完再 release，或先拷贝走

零拷贝：
  pop = 把 buffer 所有权拿走
  buffer 的寿命由消费者决定
  只要不 free，生产者就碰不到
  但池是有限的，不还就会耗尽
```

### 3.5 为什么直接组装式不叫零拷贝

“零拷贝”不是二值属性，而是看整条流水线在哪一段省掉了拷贝。

| 方案 | 数据到最终缓冲 | 队列交接 | 通常叫法 |
|---|---|---|---|
| 拷贝式帧队列 | 源 → 组装缓冲 → 队列槽，2 次 | 有拷贝 | 拷贝式 |
| 直接组装，framer 写槽 | 源 → 槽，1 次 | 0 次 | 直接组装 / 原地组装 |
| 直接组装，DMA 写槽 | 0 次 CPU 拷贝 | 0 次 | 可以叫零拷贝，但属特例 |
| 零拷贝，framer 写池 | 源 → 池，1 次 | 0 次 | 队列零拷贝 |
| 零拷贝，DMA 写池 | 0 次 CPU 拷贝 | 0 次 | 端到端零拷贝 |

直接组装式的本质：

```text
队列槽 = 帧缓冲
队列位置 = 所有权
消费者 release 后，槽迟早会被生产者复用
```

零拷贝的本质：

```text
队列元素 = 描述符 / 指针
帧缓冲 = 独立池
所有权 = free / ready 显式管理
消费者可以持有 buffer，直到主动归还
```

所以：

- 直接组装式是“原地组装”，它省掉了“组装缓冲 → 队列槽”的入队拷贝。
- 零拷贝是“缓冲池 + 描述符”，它省掉了队列交接拷贝，并把 buffer 生命周期从队列位置里解耦出来。
- 如果 DMA 直接写直接组装式的槽，它也可以叫零拷贝；只是这个名字通常留给“池 + 描述符 + 所有权”那一套模式。
- 反过来，零拷贝如果仍从字节环往池里拷，也只是“队列零拷贝”，不是端到端零拷贝。

不要纠结名字，直接数整条链路的 CPU 拷贝次数。

### 3.6 零拷贝帧队列最小实现

核心模型：

```text
free 环：消费者归还 buffer，生产者取 buffer
ready 环：生产者提交 buffer，消费者取 buffer
数据始终留在 pool buffer 里，队列只传指针
```

```c
#define POOL_N      16
#define BLOCK_SIZE  256
#define RING_CAP    (POOL_N + 1)

#define FRAME_VALID 0
#define FRAME_ABORT 1

typedef struct {
    uint16_t len;
    uint8_t  flags;
    uint8_t  data[BLOCK_SIZE];
} frame_buf_t;

typedef struct {
    void *item[RING_CAP];
    volatile uint16_t head;
    volatile uint16_t tail;
} ptr_ring_t;

static frame_buf_t pool[POOL_N];
static ptr_ring_t free_ring;
static ptr_ring_t ready_ring;
static frame_buf_t *cur;
```

`RING_CAP = POOL_N + 1` 是为了留一个空槽区分满/空，实际最多放 `POOL_N` 个元素。

```c
static int ring_push(ptr_ring_t *r, void *p)
{
    uint16_t next = (uint16_t)((r->head + 1u) % RING_CAP);

    if (next == r->tail) {
        return 0;
    }

    r->item[r->head] = p;
    __DMB();
    r->head = next;
    return 1;
}

static void *ring_pop(ptr_ring_t *r)
{
    void *p;

    if (r->head == r->tail) {
        return NULL;
    }

    p = r->item[r->tail];
    __DMB();
    r->tail = (uint16_t)((r->tail + 1u) % RING_CAP);
    return p;
}
```

初始化：

```c
void frame_pool_init(void)
{
    for (int i = 0; i < POOL_N; i++) {
        ring_push(&free_ring, &pool[i]);
    }
}
```

生产者：

```c
void frame_abort(void);

void frame_start(void)
{
    cur = (frame_buf_t *)ring_pop(&free_ring);

    if (cur) {
        cur->len = 0;
        cur->flags = FRAME_VALID;
    }
}

void frame_byte(uint8_t b)
{
    if (!cur) {
        return;
    }

    if (cur->len >= BLOCK_SIZE) {
        frame_abort();
        return;
    }

    cur->data[cur->len++] = b;
}

void frame_commit(void)
{
    if (!cur) {
        return;
    }

    cur->flags = FRAME_VALID;
    ring_push(&ready_ring, cur);
    cur = NULL;
}

void frame_abort(void)
{
    if (!cur) {
        return;
    }

    cur->flags = FRAME_ABORT;
    ring_push(&ready_ring, cur);
    cur = NULL;
}
```

消费者：

```c
void frame_poll(void)
{
    frame_buf_t *b;

    while ((b = (frame_buf_t *)ring_pop(&ready_ring)) != NULL) {
        if (b->flags == FRAME_VALID) {
            process(b->data, b->len);
        }

        ring_push(&free_ring, b);
    }
}
```

关键点：

1. `free_ring` 只有消费者 push、生产者 pop；`ready_ring` 只有生产者 push、消费者 pop，两个环都是 SPSC，可以无锁。
2. 帧中止时不要直接推 `free_ring`，否则 free 环会变成多生产者；推 `ready_ring` 并标 `FRAME_ABORT`，由消费者回收。
3. `POOL_N` 个 buffer 中，组帧期间 `cur` 占一个，所以 `ready_ring` 最多 `POOL_N - 1`，容量 `POOL_N` 保证 commit 不会失败。
4. 消费者处理完必须归还；否则池耗尽，生产者只能丢帧。
5. 上面 `frame_byte()` 仍是 CPU 逐字节写池。要端到端零拷贝，让 DMA 直接写 `cur->data`，IDLE/TC 时算实际长度再 `frame_commit()`。
6. DMA 写池后，消费者读之前要 invalidate D-Cache；CPU 写、DMA 读则先 clean。缓冲区按 cache line 对齐。

## 4.环形和双缓冲怎么组合

先纠正一个常见误解：

> **双缓冲不是环形缓冲的“升级版”，它们解决的不是同一个问题。**

| 结构 | 解决什么 |
|---|---|
| 环形 | 用固定内存容纳“多块/连续”的数据，处理生产消费速度不匹配 |
| 双缓冲 | 一块在写、一块在读，解决“交接时不能覆盖/不能撕裂” |
| 帧队列 | 元素为帧的环形队列，天然就是“多缓冲” |

**双缓冲只是帧队列深度为 2 的特例。** 而且用 head/tail 留一个空槽时，2 个槽只能存 1 帧，消费者一慢就满。

### 4.1 组合 A：字节环 + 帧队列（最常用）

```text
UART → DMA Circular 字节环 → framer → 帧队列（帧槽环）→ 任务
                                      └─ 每个槽是一帧缓冲
```

- DMA 字节环解决“字节搬运不丢”。
- framer 从字节环取新字节，直接写进帧队列当前槽。
- 帧队列解决“多帧排队、任务解耦”。
- 这里不需要额外的“双缓冲”；帧队列的多个槽就是多缓冲。

这是大多数项目的推荐结构。

### 4.2 组合 B：DMA 硬件双缓冲 + 描述符队列

```text
UART → DMA buf A / buf B（硬件乒乓）
         │
         ├─ HT/TC 切换时，把刚填满的 buf 描述符压入 ready 队列
         ▼
      ready 描述符环 → 任务
         ▲
         └─ 任务处理完归还 buf
```

- DMA 在 A/B 之间硬件切换，CPU 处理另一块。
- 队列里放的是描述符，不是数据。
- 但只有 2 块 buf：消费者必须在 DMA 绕回来之前归还，否则覆盖。
- 所以这个队列的“有效深度”很小；要提高深度，必须增加 buf 数量（缓冲池），而不是继续叫“双缓冲”。

### 4.3 组合 C：字节环 + 帧双缓冲 + 描述符队列

```text
UART → DMA 字节环 → framer → 帧 buf A / B → 描述符环 → 任务
                                      └─ 只有两块帧缓冲
```

- framer 在 A 组帧，完成后切到 B，把 A 的描述符入队。
- 消费者处理 A 时，framer 写 B。
- 问题：如果消费者处理 A 的时间超过 framer 填满 B 的时间，framer 要切回 A，而 A 还没处理完 → 覆盖。
- 所以“双缓冲 + 队列”并不能真正排队；它只提供**一帧的重叠**。
- 要排队 N 帧，就用 **N+1 块缓冲的池**，或者用拷贝式帧队列。

### 4.4 一张图总结

```text
推荐（拷贝/直接组装）：
UART → DMA 字节环 → framer → 帧槽环（N 个槽）→ 任务
                              └─ 槽 = 帧缓冲，N 决定能排几帧

零拷贝（高吞吐）：
UART → DMA 字节环 → framer → 缓冲池（N 块）
                              │
                              ├─ ready 描述符环 → 任务
                              └─ free 描述符环 ← 任务归还

双缓冲（只适合能跟得上的场景）：
UART → DMA buf A/B → 描述符环 → 任务
        └─ 只有 2 块，消费者慢就覆盖
```

### 4.5 实现关键点

1. **容量**：head/tail 留一个空槽时，容量 = `DEPTH - 1`；要存 N 帧就开 N+1 个槽。
2. **并发**：单生产者（ISR/framer）+ 单消费者（任务）可以无锁；`head` 只由生产者写，`tail` 只由消费者写；数据写完再更新索引，必要时 `__DMB()`。
3. **满策略**：ISR 不能阻塞，通常丢新并计数；丢旧需要动 `tail`，要临界区/原子操作，慎用。
4. **唤醒**：入队后给信号量/任务通知；只在“空→非空”时给，避免信号量计数溢出。
5. **零拷贝所有权**：消费者未归还前，生产者不能复用；否则覆盖/use-after-free。
6. **cache**：DMA 写缓冲、CPU 读之前要 invalidate；CPU 写、DMA 读之前要 clean。
7. **不要假设 DMA 块 = 一帧**：块只是字节环的一段，帧边界仍由 framer 决定。

一句话：**帧队列就是“元素为帧的环形队列”；环形负责容纳多块，双缓冲负责一块写一块读。实际最常用的是“DMA 字节环 + framer 直接写帧槽环”，双缓冲只在消费者能跟得上时才有意义。**

# 7.字节组帧层

只解决这一帧从哪开始、到哪结束、总共多少字节。

## 1.决策树

```text
帧长在编译期固定吗？
│
├─ 是 → 【定长】
│
└─ 否 → 帧里有长度字段吗？
        │
        ├─ 有 → 【长度字段】
        │        └─ 长度字段被转义？→ 先反转义（SLIP / COBS）
        │
        └─ 无 → 有明确结束符吗？
                │
                ├─ 有 → 【分隔符 / 首尾标志】
                │        └─ payload 可能含结束符？→ 转义 / COBS
                │
                └─ 无 → 只能靠时间
                         ├─ 【空闲中断 IDLE】
                         └─ 【超时中断 / RTO / t3.5】
```

## 2.方式介绍

| 方式 | 帧长                                         | 适用 | 缺点 |
|---|---|---|---|
| 定长 | 帧长 = N | 定长块、寄存器映射 | 丢一字节后永久错位，要能重同步 |
| 长度字段 | `total = 帧头 + 长度字段 + payload + 尾字节` | 二进制变长 | 长度字段语义 / 上限必须校验 |
| 分隔符 | 扫到 `\n` / `\r\n` / ETX 为止 | AT、NMEA、JSON | payload 含分隔符会误切 |
| 空闲 IDLE | 空闲事件给一段，段内再拆帧 | 变长、人机输入 | IDLE 不是帧边界，帧内停顿会误判 |
| 超时 | 静默超过 T 给一段 | Modbus、有帧间隔协议 | T 太短切半帧，太长粘包 |
| 转义 / COBS | 先反转义 / 解码，再读长度 | 任意二进制 | 不先解码会读错长度 |
| 协议回调 | 驱动把头给上层，上层返回总长 | Modbus、TLV | 回调要快、可重入 |

## 3.方法演进链

```text
定长
  │ 不足：丢/多一个字节后，每 N 字节切一次，帧头永久错位；没有帧头/CRC/超时无法知道从哪重同步
  ▼
长度字段
  │ 不足：语义读错会多收/少收；字段损坏会等一个巨大长度或写穿缓冲；字段被转义要先解码；payload 含帧头会假同步
  ├─→ 转义 / COBS（保护特殊字节）
  │
  │ 不足：有些协议没有长度字段
  ▼
分隔符 / 首尾标志
  │ 不足：payload 含分隔符/标志会提前截断；分隔符不来就一直等或缓冲满；长度不可预知，必须设最大行长
  ├─→ 转义 / COBS
  │
  │ 不足：有些协议既无长度也无分隔符
  ▼
空闲 IDLE
  │ 不足：硬件固定 1 字符；发送方帧内停顿 >1 字符就提前判帧；连续流没有空闲就永远不触发；只给“一段”，不给帧长
  ▼
超时 / RTO / t3.5
  │ 不足：T 太短，正常停顿被切半帧；T 太长，粘包/延迟；定时器有抖动和分辨率；仍是启发式，无绝对保证
  ▼
长度字段 + 超时兜底（组合）
```

| 方法 | 它改进的是 | 上一个方法的不足（具体机制） | 它自己带来的新问题 |
|---|---|---|---|
| 定长 | — | — | 丢/多一个字节后，每 N 字节切一次，帧头永久错位；没有帧头/CRC/超时无法重同步 |
| 长度字段 | 定长 | 定长不能变长；丢字节后不知道下一帧从哪开始 | 长度字段语义/端序/偏移读错会多收或少收；字段损坏会等巨大长度或写穿缓冲；字段被转义要先解码；payload 含帧头会假同步 |
| 分隔符 | 长度字段（针对文本/无长度协议） | 文本协议没有长度字段；给文本硬加长度字段不自然 | payload 含分隔符会提前截断；分隔符不来就一直等或缓冲满；长度不可预知，必须设最大行长 |
| 首尾标志 | 分隔符 | 单分隔符边界弱；多字节分隔符/空帧处理麻烦 | 首尾标志也可能出现在 payload；扫描会假同步；仍需转义或长度校验 |
| 转义 / COBS | 分隔符/首尾标志 | payload 含特殊字节会误切；分隔符无法可靠定界 | 编解码有 CPU 开销；最坏情况膨胀（SLIP 约 2 倍，COBS 约 1/254）；缓冲区要按最坏膨胀算；COBS 要等整段收完才能解码 |
| 空闲 IDLE | 定长/长度/分隔符 | 没有长度字段、也没有分隔符时，没有边界可用 | 硬件固定 1 字符；发送方帧内停顿 >1 字符就提前判帧；连续流没有空闲就永远不触发；只给一段，不给帧长 |
| 超时 | IDLE | IDLE 固定 1 字符不可调，不能适应不同波特率/发送方停顿 | T 太短切半帧，T 太长粘包/延迟；定时器抖动/分辨率；每字节重置有开销；仍是启发式 |
| 协议回调 | 长度字段 | 长度由功能码/类型决定，固定偏移的长度字段不够用 | 驱动与协议耦合；回调在 ISR 里必须快、可重入；回调可能阻塞导致 ORE；回调返回错长度会等死/溢出 |

注意：**这些不是一条直线替代关系**。长度字段和分隔符是两条分支；转义 / COBS 是补丁；IDLE / 超时是没有显式边界时的兜底。实际最佳实践常是“**长度字段 + 超时兜底**”。

### 6.3 长度字段，驱动必须配置清楚这 5 件事

1. **偏移**：从帧头第几字节开始？
2. **字节数**：1 / 2 / 4 字节？
3. **端序**：大端还是小端？
4. **语义**：payload 长度？整帧总长？含不含帧头 / CRC？
5. **上限**：`max_len` 是多少？非法长度立即丢弃。

公式：

```text
total = sof_len + len_offset + len_size + payload_len + tail_len
```

例子：

```text
AA 55 | LEN(2, LE) | PAYLOAD | CRC16
LEN = payload 长度
total = 2 + 2 + LEN + 2
```

### 6.4 粘包 / 半包，组帧层只做两件事

- **粘包**：一段数据里有多帧 → 循环喂 framer，交付多帧。
- **半包**：一段数据不够一帧 → 保留状态和已收字节，等下一段。

一句话：**framer 按字节喂，不按块喂；块边界永远不等于帧边界。**

### 6.5 通用 framer 状态机

```c
typedef struct {
    uint8_t  sof[4];        /* 帧头，如 AA 55 */
    uint8_t  sof_len;

    uint8_t  len_offset;    /* 从帧头开始到长度字段的偏移 */
    uint8_t  len_size;      /* 1/2/4 */
    uint8_t  len_big_endian;
    int8_t   len_adjust;    /* total = len + len_adjust */
    uint16_t max_len;       /* 必须设，防溢出 / 等死 */

    uint8_t  eof[2];        /* 可选尾标志 */
    uint8_t  eof_len;

    uint32_t gap_timeout_us;   /* 字节间超时，用于中止 */
    uint32_t frame_timeout_us; /* 整帧超时，用于中止 */
} uart_framing_cfg_t;
```

```text
SYNC -> HEADER -> LEN -> PAYLOAD -> TAIL -> DELIVER
```

```c
void framer_feed(framer_t *f, uint8_t byte)
{
    switch (f->state) {
    case SYNC:
        if (byte == f->cfg.sof[f->sof_idx]) {
            f->sof_idx++;
            if (f->sof_idx == f->cfg.sof_len) {
                f->idx = 0;
                f->state = HEADER;
            }
        } else {
            f->sof_idx = (byte == f->cfg.sof[0]) ? 1 : 0;
        }
        break;

    case HEADER:
        f->frame[f->idx++] = byte;
        if (f->idx >= f->cfg.len_offset + f->cfg.len_size) {
            f->payload_len = read_len(f->frame, &f->cfg);
            f->total = f->payload_len + f->cfg.len_adjust;
            if (f->total < f->idx || f->total > f->cfg.max_len) {
                framer_reset(f);       /* 长度非法，重同步 */
                break;
            }
            f->state = (f->idx < f->total) ? PAYLOAD : DELIVER;
        }
        break;

    case PAYLOAD:
        f->frame[f->idx++] = byte;
        if (f->idx >= f->total) f->state = DELIVER;
        break;

    case DELIVER:
        deliver_frame(f->frame, f->total);
        framer_reset(f);
        break;
    }
}
```

关键点：

- `total` 一旦算出，剩余字节数就是 `total - idx`。
- 一次喂一批字节时，**循环喂**，一帧交付后继续喂，处理粘包。
- 帧没收完就保留状态，处理半包。
- 长度非法 / 超时 / 错误 → 重置到 `SYNC`，丢掉残帧。
- 帧头在 payload 里出现时，单靠状态机可能误判；需要 max、超时、可选的 CRC / 上层确认来兜底。

# 8.数据交帧层

只解决“完整帧怎么给上层”。

| 方式 | 说明 | 适用 |
|---|---|---|
| 帧回调 | 收完一帧调用 `on_frame(data, len)` | 简单、裸机 |
| 帧队列 | ISR 入队，任务出队 | RTOS、解耦 |
| 阻塞读 | `read_frame(buf, timeout)` | 任务主动取 |
| 零拷贝 | 传指针，配所有权 / 释放 | 高速、大帧 |

驱动 API 至少要能返回：**帧指针、帧长度、状态（OK / 超时 / 长度错 / 溢出）**。

帧描述符示例：

```c
typedef struct {
    const uint8_t *data;
    uint16_t len;
    uint32_t timestamp;
    uint16_t status;   /* OK / LEN_ERR / TIMEOUT / OVERFLOW ... */
} uart_frame_t;
```

注意：

- 回调上下文必须写清楚（ISR 还是任务）。
- ISR 回调里不能 `malloc`、不能 `printf`、不能等信号量。
- 拷贝交付安全但多一次 memcpy；零拷贝快但必须明确所有权和释放接口。
- 索引更新用临界区或原子操作；`volatile` 只防优化，不保证顺序。

### 7.1 方法演进链：每个方法补上一个方法的什么坑

```text
阻塞读
  │ 不足：调用任务阻塞；裸机里是 while(没帧) 忙等；阻塞期间来的多帧只能靠缓冲，缓冲满就丢
  ▼
帧回调
  │ 不足：回调在 ISR 上下文；回调里做重活/阻塞会推迟更低优先级中断，UART 可能 ORE；数据指针生命周期短；有重入风险
  ▼
帧队列
  │ 不足：队列满时 ISR 不能阻塞，只能丢帧；有拷贝/内存开销；动态分配可能失败
  ▼
零拷贝
```

| 方法 | 它改进的是 | 上一个方法的不足（具体机制） | 它自己带来的新问题 |
|---|---|---|---|
| 阻塞读 | — | — | 任务阻塞；裸机忙等占 CPU；阻塞期间多帧只能靠缓冲，缓冲满就丢 |
| 帧回调 | 阻塞读 | 调用者阻塞等待，期间干不了别的；多帧处理不及时 | 回调在 ISR 上下文，不能做重活；回调长了推迟更低优先级中断，UART 可能 ORE；指针生命周期短；重入 |
| 帧队列 | 帧回调 | 回调里不能慢慢处理，处理时间直接压在 ISR 上 | 队列满时 ISR 不能阻塞，只能丢；有拷贝/内存开销；动态分配可能失败 |
| 零拷贝 | 帧队列 | 大帧 memcpy 开销；拷贝期间延迟 | 所有权/释放/生命周期；池耗尽只能丢；cache 一致性 |

注意：**回调、队列、阻塞读不是严格的先后替代**，而是不同使用方式；这张表按“解耦程度”从低到高排列。

# 9.错误恢复

1. **清标志**
   ORE / FE / NE / PE / Break 按手册清。
2. **丢残帧**
   当前不完整帧直接丢，不要试图续解析。
3. **回 SYNC**
   组帧状态机回到找帧头，重新同步，计数。

| 错误 | 驱动处理 |
|---|---|
| ORE 溢出 | 按手册清标志；丢当前帧；重置 framer；重新武装；计数 |
| FE 帧错误 | 丢字节 / 帧；重同步；检查波特率 / 停止位 |
| NE 噪声 | 丢字节；计数；硬件整改 |
| PE 校验错 | 丢字节 / 帧；统一校验配置 |
| Break | 按协议当分隔 / 复位；否则重置 framer |
| 长度字段非法 | 立即丢弃；回 `SYNC`；计数 |
| 帧超时 | 丢残帧；回 `SYNC`；计数 |
| 缓冲溢出 | 丢新 / 丢旧；计数；可选流控 |
| DMA 错误 | abort、清标志、重初始化、计数 |
| DMA 重装间隙 | 改 Circular / 双缓冲；或提前重装 |
| Cache 不一致 | 非缓存区或 clean / invalidate |
| RS485 DE 过早释放 | 等 TC 再拉低 DE |
| 半双工回显 | TX 时关 RX 或丢弃回显 |
| USB 转串口延迟 | 调低 latency；不要依赖 read 边界 |

# 10.三步选型法

## 1.具体步骤

```text
第 1 步：选搬运
  低速 / 简单 → 中断
  定长 / 一问一答 → DMA Normal
  高速 / 连续 / 变长 → DMA Circular

第 2 步：选缓冲
  字节流 → 环形缓冲
  帧块零拷贝 → 双缓冲
  RTOS / 多任务 → 帧队列

第 3 步：选组帧
  定长 → 定长
  有长度字段 → 长度字段（+ IDLE / 超时兜底）
  有结束符 → 分隔符
  都没有 → IDLE 或超时
```

## 2.四个典型组合

| 场景 | 组合 |
|---|---|
| 低速命令 / 文本 | 中断 + 环形 + 分隔符 |
| 变长二进制 | DMA Circular + 环形 + 长度字段（IDLE / 超时只做兜底） |
| 高速连续流 | DMA Circular + 双缓冲 / 帧队列 + 长度字段 |
| Modbus RTU | 中断或 DMA + 环形 + t3.5 超时 + 最大帧长 |

## 3.工程实例：USB 6 路虚拟串口 ↔ 6 路 485 透传

需求特征：

- 裸机，无 RTOS。
- 数据转发模块，不关心数据内容，只保证字节顺序。
- 上行 USB 虚拟 6 路串口，下行 6 路 485，每路独立。
- 双向透传：USB→485、485→USB。

### 3.1 选型结论

| 层 | 选择 |
|---|---|
| 485 RX 搬运 | DMA Circular + HT/TC + IDLE（IDLE 只冲尾部，不做帧边界） |
| 485 TX 搬运 | 软件字节环 + DMA Normal + UART TC 释放 DE |
| USB 上行 | CDC OUT 回调入环；CDC IN 用 TX 完成回调续发 |
| 缓冲 | 每路两条 SPSC 字节环：`USB→485`、`485→USB` |
| 组帧 | 无。不做长度字段、分隔符、帧队列 |
| 交帧 | 无。环 → DMA/USB，直接转发 |
| 双缓冲 / 帧队列 | 不需要 |

### 3.2 数据流

```text
USB OUT ──► ring_usb2uart ──► UART TX DMA ──► 485（DE 控制）
485 RX  ──► UART RX DMA Circular ──► ring_uart2usb ──► USB IN
```

6 路就是 6 份独立实例，不要共享全局环。

### 3.3 每路结构

```c
typedef struct {
    UART_HandleTypeDef *huart;
    uint8_t cdc_itf;

    ring_t usb2uart;      /* USB OUT -> 485 TX */
    ring_t uart2usb;      /* 485 RX  -> USB IN */

    uint8_t tx_dma_buf[64];
    uint8_t usb_tx_buf[64];
    volatile uint8_t uart_tx_busy;
    volatile uint8_t usb_tx_busy;
    volatile uint8_t de;
} bridge_t;
```

主循环非阻塞轮询：

```c
for (;;) {
    for (int i = 0; i < 6; i++) {
        bridge_poll(&br[i]);
    }
    usb_poll();
}
```

`bridge_poll()` 只做两件事：

```c
/* USB -> 485 */
if (!b->uart_tx_busy && ring_used(&b->usb2uart)) {
    len = ring_peek(&b->usb2uart, b->tx_dma_buf, sizeof(b->tx_dma_buf));
    ring_drop(&b->usb2uart, len);       /* 已拷贝到 DMA 缓冲 */
    DE_HIGH(b);
    b->uart_tx_busy = 1;
    HAL_UART_Transmit_DMA(b->huart, b->tx_dma_buf, len);
}

/* 485 -> USB */
if (!b->usb_tx_busy && ring_used(&b->uart2usb)) {
    len = ring_peek(&b->uart2usb, b->usb_tx_buf, 64);
    if (CDC_Transmit_FS(b->usb_tx_buf, len) == USBD_OK) {
        ring_drop(&b->uart2usb, len);
        b->usb_tx_busy = 1;
    }
}
```

发送完成：

```c
/* DMA 完成只代表数据搬完，不代表最后一个字节已出线 */
void uart_tc_isr(bridge_t *b)
{
    DE_LOW(b);
    b->uart_tx_busy = 0;
}
```

### 3.4 关键点

1. **485 DE 必须在 UART TC 后释放**，不是 DMA TC 后；否则最后一个字节被截断。
2. **半双工总线**：发送期间关 RX 或丢弃回显；2 线总线发送前等总线空闲，避免和正在收的响应冲突。
3. **USB 也是字节流**：主机可能拆包/合包，不能假设“一次 USB 包 = 一次转发”。
4. **USB busy 不要等**：`CDC_Transmit_FS` 返回 busy 时保留数据，等 TX 完成回调再续发；发送缓冲要保留到 TX 完成，建议每路独立。
5. **环大小按最坏突发算**：115200 8N1 约 11.5KB/s；每路每方向 1~4KB，按 RAM 调整。
6. **没有帧边界就没有重同步**：ORE/FE/NE 只能清标志、计数、丢坏字节，可靠性交给端到端协议。
7. **DMA 通道不够时**：优先给高速/连续的路；低速路可退化为 RXNE/TXE 中断 + 字节环。

### 3.5 不推荐

| 方案 | 为什么不合适 |
|---|---|
| 帧队列 | 不知道帧边界，等帧只增加延迟 |
| 双缓冲 | 没有帧块交接需求，字节环足够 |
| IDLE 当帧边界 | 这是透传；IDLE 只用来冲尾部 |
| DMA Normal 收 485 | 连续/突发数据会撞重装间隙 |
| 每字节中断收 6 路 | 6 × 115200 ≈ 69k 中断/s，裸机压力大 |
| 在 USB 回调里直接转发 | 阻塞 USB 栈，容易丢包/死锁 |

# 11.驱动层常见坑

## 1.搬运层

1. DMA Normal 每帧重装，间隙丢字节。
2. DMA Circular 的 `NDTR` 回绕算错。
3. 高波特率仍用逐字节中断。
4. ISR 里解析 / 拷贝大帧 / 打印。
5. ORE 没清，接收停摆。
6. 中断优先级不当，UART 被长 ISR 饿死。

## 2.缓冲层

7. 环形缓冲满 / 空判断错，或索引并发撕裂。
8. 双缓冲切换不原子。
9. 零拷贝没有所有权 / 释放。
10. 只用平均速率算缓冲，不按最坏突发。

## 3.组帧层

11. 把一次 IDLE / DMA 完成 / read 当一帧。
12. 长度字段语义没确认：payload 长度 vs 总长、含不含 CRC。
13. 长度字段不校验上限，缓冲区被写穿。
14. 长度字段被转义却没先反转义。
15. 固定长度丢字节后不重同步。
16. IDLE 帧内停顿误触发，把半帧交付。
17. 连续流没有 IDLE，驱动一直等。
18. 超时太短切半帧，太长粘包 / 延迟。
19. 帧头出现在 payload 里，状态机假同步。
20. 半包没有保留状态，下一段从零开始。
21. 粘包没有循环解析，只交付第一帧。
22. 帧超过缓冲区没有拒绝策略。

# 12.每个方法的不足

这一节把前面表格里的不足展开成：**谁在等、为什么空转、为什么漏、什么条件触发**。

## 1.搬运层

#### 轮询

- **谁在等**
  调用者（裸机主循环 / RTOS 任务）执行 `while (!(SR & RXNE));`，停在循环里。
- **为什么叫空转**
  CPU 反复读状态寄存器，不进入低功耗，也不做其他有用工作；它不是“没事干”，是“在忙着等”。
- **为什么会漏**
  离开轮询去干别的，UART 仍在收；RDR 只能放 1 字节（有 FIFO 则是 FIFO 深度），满了再来字节 → ORE，硬件丢字节。
- **触发条件**
  其他工作耗时 > 字节时间（115200 约 86.8µs，1Mbps 约 10µs）或 FIFO 深度 × 字节时间。
- **新问题**
  实时性差、功耗高；RTOS 里轮询任务会饿死低优先级任务。

#### 中断

- **谁在等**
  没有调用者阻塞；CPU 被 ISR 打断。
- **为什么不是空转**
  CPU 在做事，但每字节一次中断，入口/出口/保存现场/读 DR/写缓冲都是开销；频率 = 波特率 / 每帧位数。
- **为什么会漏**
  ISR 执行时间 + 关中断时间 + 被更高优先级 ISR 抢占的时间 > 字节时间（或 FIFO 深度 × 字节时间）→ RDR 没及时读 → ORE。
- **数字例子**
  115200 8N1 ≈ 11.5k 次中断/秒；1Mbps ≈ 100k 次/秒。若每次 ISR 3µs，1Mbps 下约 30% CPU，留给其他中断的余量只有 7µs。
- **新问题**
  中断风暴、优先级反转、ISR 里不能做重活；高波特率 CPU 负载高。

#### DMA Normal

- **谁在等**
  没有任务阻塞；DMA 通道在 NDTR=0 后停止，UART 继续收。
- **为什么漏**
  TC 中断延迟 + ISR 处理 + HAL/LL 重装 + 被抢占的时间 = 间隙；间隙内 RDR/FIFO 满 → ORE。
- **触发条件**
  背靠背帧；间隙 > 硬件能兜的时间（通常 1 字节 + FIFO 深度）。
- **另一个问题**
  N 固定。N > 帧长 → TC 不代表帧结束；N < 帧长 → 一帧被拆；N = 帧长但丢字节 → 错位。
- **新问题**
  重装间隙、N 固定；两段式 DMA（先头后体）也有同样间隙。

#### DMA Circular

- **谁在等**
  没有任务阻塞；DMA 一直搬，CPU 只在 HT/TC/IDLE 处理。
- **为什么相对不漏**
  没有重装间隙；只要消费者跟得上，DMA 不会停。
- **为什么仍会漏/错**
  消费者处理速度 < 生产速度，DMA 绕圈覆盖未读数据；`NDTR` 读取与回绕竞争；cache 不一致；帧跨 HT/TC 边界被误当帧边界。
- **谁在等**
  消费者任务可能等数据；消费者慢时不是 UART 丢，是软件覆盖。
- **新问题**
  帧边界、回绕覆盖、`NDTR` 竞争、cache 一致性。

## 2.缓冲层

#### 单缓冲

- **谁在等**
  没有同步机制；ISR 和主循环都直接读写同一数组。
- **为什么丢/错**
  主循环处理慢，ISR 继续写同一位置 → 覆盖未读数据；主循环读到一半被 ISR 改写 → 数据撕裂。
- **空转吗**
  主循环用 `while(!flag)` 等数据就忙等；否则不空转。
- **触发条件**
  ISR 写入速度 > 主循环读取速度；或处理时间 > 下一帧到达时间。
- **新问题**
  无所有权、无边界、不可重入。

#### 环形缓冲

- **谁在等**
  消费者等数据（RTOS 可阻塞，裸机可忙等）；生产者 ISR 从不等。
- **为什么丢**
  环满。生产 > 消费；策略丢新/丢旧；DMA 绕圈覆盖。
- **空转吗**
  消费者用 `while(empty)` 忙等则空转；用信号量/任务通知则阻塞，不占 CPU。
- **触发条件**
  `head - tail == size`；或 DMA 写指针追上读指针。
- **新问题**：
  只解决字节流，不解决帧边界；满/空判断；索引并发；大帧仍要拷贝。

#### 双缓冲 / 乒乓

- **谁在等**：消费者等“有一块满了”；生产者 ISR 不能等。
- **为什么丢**：只有两块；消费者处理一块的时间 > 生产一块的时间，生产者没有空闲块；ISR 不能阻塞，只能覆盖/丢。
- **空转吗**：消费者轮询 ready 标志则忙等；用信号量则阻塞。
- **触发条件**：处理时间 > 填充时间；或切换指针不原子，生产者和消费者同时操作同一块。
- **新问题**：只有两块、切换原子性、所有权。

#### 帧队列

- **谁在等**：消费者等队列非空（可阻塞）；生产者 ISR 不等。
- **为什么丢**：队列满；ISR 不能阻塞，只能丢新/丢旧；动态分配失败。
- **空转吗**：消费者轮询队列则忙等；用阻塞 API 则阻塞。
- **触发条件**：入队速度 > 出队速度；队列深度不足；拷贝耗时。
- **新问题**：队列满策略、内存、拷贝、优先级反转。

#### 帧池 / 零拷贝

- **谁在等**：消费者等空闲块；生产者 ISR 不等。
- **为什么丢/错**：池耗尽；消费者持有块太久；生产者覆盖；释放时机错。
- **空转吗**：消费者轮询空闲队列则忙等。
- **触发条件**：在途帧数 > 池大小；处理时间 > 池周转时间。
- **新问题**：所有权、释放、生命周期、cache。

### 11.3 组帧层

#### 定长

- **谁在等**：framer 等够 N 字节；不够就等（超时或永远）。
- **为什么错位**：丢/多一个字节后，N 字节切分边界移动，后续每帧都跨两帧；没有帧头/CRC/超时，无法知道从哪重同步。
- **空转吗**：如果 `while(count < N)` 忙等，空转。
- **触发条件**：任何 ORE/FE/NE/PE 丢字节；发送方长度变化；上电从中间开始收。
- **新问题**：不能变长；重同步需要额外机制。

#### 长度字段

- **谁在等**：framer 等 `total - idx` 字节；长度字段损坏成巨大值时，等到超时/缓冲满。
- **为什么错**：语义错（payload vs 总长、含不含头/CRC）→ 多收/少收；端序/偏移错 → 读到错误长度；字段被转义 → 读到原始字节；上限不校验 → 写穿；payload 含帧头 → 假同步。
- **空转吗**：framer 在 ISR 里逐字节处理通常不空转；主循环轮询“帧完成”标志可能忙等。
- **触发条件**：长度字段位错、跨块、转义、协议版本变化。
- **新问题**：语义/端序/上限/转义/假同步。

#### 分隔符

- **谁在等**：framer 等分隔符；分隔符不来就一直等，直到最大行长/超时。
- **为什么错**：payload 含分隔符 → 提前截断；剩余 payload 被当成下一帧；多字节分隔符/空帧处理错；没有最大行长 → 缓冲溢出。
- **空转吗**：逐字节扫描本身是工作，不是空转；主循环轮询“收到分隔符”标志可能忙等。
- **触发条件**：二进制 payload、转义缺失、发送方丢分隔符。
- **新问题**：误切、最大行长、转义。

#### 首尾标志

- **谁在等**：等首标志，再等尾标志；尾标志不来就等。
- **为什么错**：payload 含首/尾标志 → 假开始/假结束；首标志在 payload 中 → 从中间开始；尾标志丢失 → 等超时；嵌套/空帧。
- **空转吗**：扫描状态机在 ISR/任务里跑；忙等尾标志则空转。
- **触发条件**：二进制 payload、无转义、噪声。
- **新问题**：转义、长度校验、假同步。

#### 转义 / COBS

- **谁在等**：等完整段/分隔符；COBS 必须等 `0x00` 才能解码；分隔符丢失就等超时/最大长度。
- **为什么错**：解码前读长度 → 读到转义字节；缓冲区按原始长度分配 → 解码后膨胀溢出；COBS 段损坏 → 丢弃直到下一个 `0x00`；SLIP 最坏约 2 倍。
- **空转吗**：编解码是 CPU 工作；主循环轮询解码完成可能忙等。
- **触发条件**：payload 含特殊字节、最坏膨胀、段丢失。
- **新问题**：CPU 开销、膨胀、缓冲 sizing、不可读。

#### 空闲 IDLE

- **谁在等**：驱动等 IDLE 事件；连续流没有 IDLE，就永远等不到“段结束”。
- **为什么错**：IDLE 固定 1 字符；发送方帧内停顿 >1 字符 → 提前判帧，后半帧被当新帧；连续流无空闲 → 不触发；只给一段，不给帧长；IDLE 标志清除/DMA 增量算错。
- **空转吗**：主循环轮询 IDLE 标志则忙等；用中断则不空转。
- **触发条件**：发送方有停顿、USB 转串口、RTOS 调度、连续流。
- **新问题**：误判、连续流、需要长度/超时兜底。

#### 超时

- **谁在等**：驱动/任务等超时；残帧期间一直等。
- **为什么错**：T 太短 → 正常字节间隔（USB latency、发送方处理、RTOS 调度）被误判为帧结束；T 太长 → 背靠背帧合并、延迟大；定时器分辨率/抖动；每字节重置开销；超时期间缓冲可能满。
- **空转吗**：轮询定时器标志则忙等；用中断/定时器回调则不空转。
- **触发条件**：T 与发送方间隔不匹配；高波特率；系统负载。
- **新问题**：参数难调、抖动、启发式。

#### 协议回调

- **谁在等**：驱动等回调返回长度；回调在 ISR 里执行，不能等。
- **为什么错**：回调慢 → 阻塞 UART 中断/更低优先级中断 → ORE；回调重入；回调需要更多头字节但还没收到；回调返回 0 表示继续等，若永远返回 0 就等死；返回错长度 → 多收/少收。
- **空转吗**：回调里忙等 → 空转且阻塞系统。
- **触发条件**：复杂协议、功能码/类型决定长度、回调实现不当。
- **新问题**：耦合、上下文、可重入、错误处理。

### 11.4 交帧层

#### 阻塞读

- **谁在等**：调用任务阻塞（RTOS）或主循环忙等（裸机）。
- **为什么丢**：阻塞期间生产继续，环形/队列满后丢；读的是单缓冲时 ISR 覆盖；超时设置不当。
- **空转吗**：裸机 `while(没有帧)` 忙等；RTOS 阻塞不占 CPU。
- **触发条件**：生产快于消费；多帧到达但只读一帧；超时。
- **新问题**：实时性、缓冲满、在 ISR 里调用会死锁。

#### 帧回调

- **谁在等**：没有任务等；回调在 ISR 上下文执行。
- **为什么丢**：回调执行时间长 → 推迟更低优先级中断/UART 自身 → ORE；回调里阻塞 → 死锁；回调保存的指针在返回后被复用；重入。
- **空转吗**：回调里忙等 → 空转且阻塞系统。
- **触发条件**：回调做重活、打印、`malloc`、等信号量。
- **新问题**：上下文限制、生命周期、重入。

#### 帧队列

- **谁在等**：消费者任务等队列非空（阻塞，不占 CPU）；生产者 ISR 不等。
- **为什么丢**：队列满，ISR 只能丢；拷贝耗时；动态分配失败；优先级反转（互斥锁）。
- **空转吗**：消费者轮询队列则忙等；阻塞 API 则不空转。
- **触发条件**：入队 > 出队；队列深度不足；大帧拷贝。
- **新问题**：满策略、内存、拷贝、优先级反转。

#### 零拷贝

- **谁在等**：消费者等空闲块；生产者 ISR 不等。
- **为什么丢/错**：池耗尽 → 丢；消费者持有块太久 → 生产者覆盖/丢；释放后继续用 → use-after-free；cache 不一致。
- **空转吗**：轮询空闲队列则忙等。
- **触发条件**：在途帧 > 池；处理慢；所有权协议错。
- **新问题**：所有权、释放、生命周期、cache。

# 13.本章总结

```text
① 搬运：字节怎么进来     → 轮询 / 中断 / DMA
② 缓冲：字节放哪里       → 单 / 环形 / 双 / 帧队列
③ 组帧：一帧多少字节     → 定长 / 长度 / 分隔符 / IDLE / 超时
④ 交帧：怎么给上层       → 回调 / 队列 / 阻塞读 / 零拷贝
```

四级演进总览：

```text
搬运：轮询 → 中断 → DMA Normal → DMA Circular
      (忙等/ORE) (ISR开销/延迟) (重装间隙) (帧边界/回绕)

缓冲：单缓冲 → 环形 → 双缓冲 → 帧队列 → 零拷贝
      (覆盖/撕裂) (环满/字节流) (只有两块) (队列满/拷贝) (所有权)

组帧：定长 → 长度字段 → 分隔符 → IDLE → 超时
      (字节错位) (长度语义/损坏) (payload误切) (1字符误判) (T难调)

交帧：阻塞读 → 回调 → 队列 → 零拷贝
      (任务阻塞) (ISR上下文) (队列满/拷贝) (所有权)
```

箭头表示问题驱动，**不表示前者被淘汰**；很多方法是分支或组合。

1. **这四级是流水线，不是四选一。**
2. **块边界永远不等于帧边界；framer 按字节喂，不按块喂。**
